# FP8 options for LoRA training and vLLM serving on RTX 5070 Ti (sm_120)

Labels: **shown** = measured by someone, cited. **suggested** = our inference. **untested** = no evidence found.

Local state (checked 2026-10-25): no `nvidia-smi` on this box, `torchao` not installed. Nothing here was run on the 5070 Ti.

Notes on the numbers:
- torchao docs (shown): "E2E speedups increase as M,K,N increase." For small shapes on H100 with cuBLAS the GEMM-time gain is negative, and speedup < 1. Our 2-4B models have smaller GEMMs than the 8B benchmark, so the gain is likely smaller (suggested).
- torchao requires layer in/out dims divisible by 16 (shown). Check Qwen3.5-2B and K2-Horizon-3.7B shapes.
- LoRA: the base is frozen, so the weight-gradient matmul is skipped. FP8 only touches forward and input-grad (2 of 3 GEMMs). The H100 numbers above include weight-grad. Expect a smaller gain than those figures (suggested).
- FALQON (cited in a search summary, not fetched) argues FP8 speedup is smaller for LoRA because of quantization overhead on low-rank matmuls. Label: shown (claim in paper, not checked).

## sm_120 support status

- torchao float8 docs say only "An NVIDIA H100 GPU or newer is required" (TE docs, shown). No sm_120 statement found in torchao docs.
- Transformer Engine docs (releases 2.13-2.18) say Blackwell has NVFP4 and MXFP8. Not stated for consumer sm_120. Label: untested on sm_120.
- Search results show PyTorch builds without sm_120 kernels cause "no kernel image is available" (vLLM issue #16901, shown). Builds need CUDA 12.8+ and torch that includes sm_120.
- SGLang issue #9233 (shown): block-wise FP8 on SM120 was requested; not supported at time of issue.
- Quality of FP8 LoRA: no published loss/eval deltas for FP8 LoRA on 2-4B models were found. TE/NeMo show "virtually identical" loss curves to BF16 for full training on H100 (shown, no numbers).

## Minimal test plan (suggested pass marks, fixed before running)

Gate 0 (kernel check, 10 min): `torch.cuda.get_device_capability() == (12, 0)`. Run one torchao `Float8Linear` forward+backward on a 2048x2048 layer. Fail = stop; no FP8 training on this card with that stack.

Gate 1 (speed, same script, same data, same seq length, same LoRA rank, torch.compile on):
- Warm up 20 steps, time 100 steps, report median s/step, per model (Qwen3.5-2B, K2-Horizon-3.7B).
- Pass: FP8 median s/step <= 0.90x BF16 (>=10% faster) on both models.
- Fail: < 5% faster on either model, or slower. Result that shows FP8 is not worth it: this.

Gate 2 (quality, 3 seeds each):
- Pass: final eval loss within 0.02 nats of BF16 (mean over seeds), and downstream eval within 1.0 point.
- Fail: any eval delta > 1.0 point, or loss gap > 2% persisting after the first 20% of steps.

Gate 3 (vLLM FP8 KV, only if serving is the bottleneck):
- Run the same eval with `--kv-cache-dtype auto` vs `fp8` (scales at 1.0, then calibrated per the vLLM page). Pass: within 1.0 point of auto, and >=10% more tokens/s at target concurrency.
- Fail: >1.0 point drop. Also fail if the KV gain is <5%.

Decision rule: all of Gate 0-2 must pass for FP8 training to be used. Otherwise keep BF16 LoRA.

## Plain-language summary for Ben
1. FP8 can make training faster on big GPUs (about 25% in one H100 test on an 8B model), but that test was full training, not LoRA.
2. For our small models on one 16 GB card, the gain is likely smaller, and nobody has measured it on this card.
3. We could not confirm the software supports RTX 5070 Ti (sm_120) for FP8 training. Check that first.
4. FP8 KV cache for vLLM is the most likely real win, and it is a serving change, not a training change.
5. Run the 10-minute kernel check, then the speed test. If FP8 is less than 10% faster or hurts eval by more than 1 point, drop it.
