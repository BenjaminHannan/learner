## Fixes applied before any LT-2 row is used (from the panel)
- F1 (D1) test_sampler is dropped from every mark. Every eval file used here is balanced by label within each reported slice, and unknown
  rows carry the depth of the chain they were built from (never None).
- F2 (D2) dangling-word cue: logic rows (R4, R5) are rebuilt so that, within each depth, the per-label distribution of "predicate words
  that occur exactly once in the prompt" is equal (rejection matching on train and eval). Check: the panel's lookup attack on
  (distinct predicates, singleton predicates, sentence count) must score <= 37% on every eval file of R4/R5.
- F3 (D3) every eval file reports the train-fitted count baseline (negation-word count + sentence count lookup) next to the model number.
  PASS below also needs model >= that baseline + 25 points.
- F4 (D4) any label-shuffled control uses new row ids (the target cache is keyed by id).
- F5 item-pairing of logic/placebo contexts is NOT done (cosmetic in the panel).

## Row format (all rungs; format v2 as in LT-1)
Prompt = context sentences + question sentence + options suffix " (a/b/c)" (rows.options_suffix(id): per-row hash-shuffled order of
true/false/unknown), <= 208 chars including the suffix, only chars of the checkpoint vocab. Answer in {true, false, unknown}, labels exactly
balanced in thirds per file (and per depth for R4/R5). Words from the LT-1 lexicon (149 entities, 1,407 predicate words); no
(entity, predicate) literal of the query appears in a distractor. Each row carries meta.program so an independent solver can verify it.
130,000 train rows per rung; eval files 1,200 rows each. The labels are re-derived from the TEXT by an independent solver for every
row of every file before use (must agree on 100%).

| rung | context | question | label rule | eval files |
|---|---|---|---|---|
| R0 stated answer | 2-4 filler facts about random (entity, predicate) pairs plus the sentence "The answer is W." (W in true/false/unknown) at a random position; filler uses train FP/FN templates | a Q template about a random literal that is NOT related to W (a decoy) | gold = W | dev (train templates), wording (held-out Q/FP/FN templates) |
| R1 one fact | exactly one fact, plain forms only: "E is P." or "E is not P." | "Is E P?" or "Is E not P?" (plain form) | same (E, P) and same polarity -> true; same (E, P) opposite polarity -> false; different E or different P -> unknown (the unknown class is split equally: other entity / other predicate / both) | dev |
| R2 + distractors | R1 plus 1-3 distractor facts (other entities and/or predicates, never the query's (E, P)); position random; plain forms | as R1 | as R1 | dev |
| R3 + wording | the existing depth-0 placebo rows (72 train templates, 1-4 decoys, rule sentences as distractors), files from LT-1 (lt2/rows placebo_train, placebo_dev, placebo_test_wording; hashes in rows-summary-v2) | as placebo | as placebo | placebo_dev (dev), placebo_test_wording (wording) |
| R4 depth 1 | logic generator, depth 1 only (one rule step), with F2 | as logic | as logic | dev (train wording, depth 1), gate-d1 (held-out wording, depth 1) |
| R5 depths 0-3 | logic generator, depths 0-3 label-first, with F2 (the LT-1 gate rebuilt) | as logic | as logic | dev, gate (held-out wording, depths 0-3 x 134), deeper (depths 4-5, reported only) |

## Training recipe (the LT-1 marked recipe, unchanged)
Continue the parent for at most 8,000 updates: 25% of every batch from the rung's train file, 75% from the sk200k curriculum, lr 1e-4
constant after 100 warm-up updates, batch 64, AdamW as the original, grad clip as the original, mix_frac 0.25; course seed s in {1, 2}.
Eval on the full dev (and wording) files every 250 updates on GPU; on CPU a 400-row prefix every 250 updates plus a full-file eval at
the stop point. A run STOPS EARLY when its marks (below) are met at two consecutive evals and the full-file eval confirms them.

## Marks (fixed now)
Run passes rung r when, at some eval at or before 8,000 updates, ALL of: dev accuracy >= 90% (R5: the LT-1 G-PASS bars instead: gate depth 0-1 >= 80%,
depth 2 >= 65%, depth 3 >= 55%); wording accuracy >= 80% where the rung has one (R4: gate-d1 >= 75%); model >= count baseline + 25 points.
- Rung PASS: >= 5 of 6 runs pass. Rung FAIL: <= 1 of 6 pass at 8,000 updates. MIXED: 2-4 of 6 (no conclusion; recorded as such).
- R0 falsifier: < 50% dev accuracy at 2,000 updates in >= 5 of 6 runs -> the answer-pointer interface itself cannot learn a label at
  this share; stop, fix the interface first, read no other rung as a learnability result.
- The learning limit of the 3M model under this recipe = the first FAILing rung. Reported per rung: mean, spread (min / max) and worst run of
  dev accuracy at 2,000 / 4,000 / 8,000 updates; updates to pass; count baseline; non-logic in_dist of the stop checkpoint within 1.0 point of the parent
  (PASS only needs it reported; a drop > 3 points is flagged).
- Reported, never gated: new-words eval (held-out entity and predicate words), per-label recall, the panel's counterfactual probes
  (swap the queried name / delete the supporting sentence) on every passing checkpoint (a pass must move with the content).

## Next steps, decided by the outcome (one change at a time; the change is pre-registered after the read)
- R0 falsifier fires: fix the interface (single hypothesis, own marks), no further rung.
- First FAIL at rung k (k >= 1): the single next change is dose (share 25% -> 50%), then updates, then lr, each its own read; mixtures of rungs
  (rung k-1 + k) as a curriculum after that.
- R5 PASS: the LT-1 transfer test (arms C / L / P, V / N / J marks, >= 5 seeds per arm) is re-sealed and run. Not before.

## Addendum 1 (2026-10-14 ~7:50 AM ET, written BEFORE any LT-2 training result existed; rung-0 runs had started but logged no eval)
Implementation details fixed now. None changes a threshold or a rule above; each only makes a sentence above exact.
- Venue of rung 0: the cloud container's CPUs (3 runs at a time, 1 thread each), not the Mac. Same code, same marks, same free CPU; it removes the wait for Ben's
  Mac session. The Mac is not used for LT-2 unless it is needed later.
- Stop/pass thresholds are computed per eval file from that file's train-fitted count baseline (negation-word count + sentence count lookup, fitted on the
  rung's train file): dev >= max(90, baseline + 25), wording >= max(80, baseline + 25). Example: on rung 1 the lookup scores 2/3 (it cannot see "unknown"), so
  the dev mark there is ~91.7%.
- R5 reading of "+25": gate by-depth bars (0-1 >= 80, 2 >= 65, 3 >= 55) AND whole-gate accuracy >= gate baseline + 25. The dev file is reported, not gated.
- Eval files: R0 dev + wording (gated), newwords (reported); R1 and R2 dev (gated), newwords (reported; their "wording" file only repeats the dev wording
  because plain sentences have no templates, so it is built but not used); R3 placebo_dev + placebo_test_wording (the LT-1 files, same seeds 12/25/26, so
  byte-identical to the sealed hashes); R4 dev + gate (gate = held-out wording, depth 1, 1,200 rows); R5 gate (1,608 rows = 134 per depth x label), dev and
  deeper (800 rows, depths 4-5) reported. R4/R5 have no new-words file (the logic lexicon hold-out is not built).
- F2 as built: joint matching of (distinct predicates, singleton predicates, sentence count) per depth across the three labels, which is stronger than matching the
  singleton count alone; the lookup attack on that triple is asserted <= 37% on every R4/R5 eval file at build time. Eval files also exclude every train prompt.
- Falsifier (R0): read on the dev eval at exactly 2,000 updates (CPU: the 400-row prefix); a run that stopped early on its marks counts as above 50%. The driver
  fires it as soon as 5 of 6 runs are below 50% at 2,000 updates (or it is certain they cannot be).
- Per-run PASS counts only evals on the WHOLE file (CPU: the confirm at the stop point and the final eval). A run that meets its marks once on a 400-row prefix but is
  never confirmed is recorded as "near", not as a pass.
- GPU agreement check, made exact (same intent as "same seed, 200 updates, eval within 1 point"): after training, chaotic float divergence between devices
  makes mid-learning evals differ by many points even when both paths are correct, so the check is (a) the SAME checkpoint decoded on CPU and on GPU over the
  same 400 dev rows: accuracy gap <= 1.0 point and >= 98% identical predictions; and (b) the GPU run's training-loss window at update 250 within 3% (relative) of the
  CPU run's window at the same update, same seed, same rows. Both must hold before any GPU result counts.
- Seeds for the row files: rung r base = 100 + 10 r: train base, dev +1, wording +2 (R4/R5 gate), newwords +3 (R5 deeper).
- Counterfactual probes (reported only; logic_transfer/probes.py) for rungs 0-2: R0 swap the stated answer word / delete the answer sentence; R1-R2 swap the
  queried entity to an unseen one (gold unknown) / flip the query's "not" / delete the supporting fact (gold unknown). Gold of every edited row is re-derived by the
  independent reader.
- Money: this thread appends its row to /mnt/project-files/vast/SPEND.md before any rental (none rented as of this addendum). The Mac-venue sentence in "Compute and
  money" above is superseded by the first bullet here.

## Addendum 2 (2026-10-14 ~9:20 AM ET; written BEFORE any rung 1-5 result is read)

Shortcuts found (all SHOWN by train-fitted lookups, scripts in the review; the new audit module logic_transfer/cues.py reproduces them):
- R1/R2 (v1): the predicate word TYPE (made-up word vs common word) alternated on every draw, so a different query predicate almost always had the opposite type.
  Type + polarity alone scored 85.8% on R1 dev (86.1% wording); +8 points from "same length" gives 93.8%, above the R1 mark (91.67%). R2: 55%. R1's train file also
  exhausted the ~22k common-word true/false prompts per label, so type carried label information in dev too. A model could pass R1 without comparing any two words.
- R4/R5 (v1): F2 matched only the predicate triple; unknown rows swap in the other ENTITY, so entity counts predicted the label (R5 gate 51% by lookup, 61% by a
  count-feature regression; depth 3: 54-56% / 60%, against a depth-3 bar of 55%).

Changes (rows only; rung 0 and rung 3 are byte-identical to before, hashes re-checked):
- R1/R2 v2: fact-predicate type is a plan slot, exactly half and half inside every (label, unknown-subtype) cell; the query predicate always has the type of the fact
  predicate; a replacement entity/predicate in an unknown row has the SAME LENGTH as the word it replaces (so length and "same length" prove nothing; only reading the
  words does); R2 distractor predicates take a coin-flipped type. R1 train file is 36,000 rows (was 130,000: the common-word true/false space is ~22k per label and
  must not be exhausted); 128,000 slice draws per run = ~3.6 passes. Seeds: train/dev/wording/newwords = 1110.. (R1), 1120.. (R2), so ids differ from v1.
- R4/R5 v2: the F2 matching key is a 5-tuple: (distinct predicates, singleton predicates, sentence count, distinct entities, singleton entities), jointly equal across
  the three labels within each depth. Seeds 1140.. (R4), 1150.. (R5). The 5-tuple lookup attack is asserted <= 37% at build (it scores 33.3% on every file).
- Audit (cues.py, run on the built files; thresholds fixed now): R1/R2: gain from the word-type keys over the same lookup without them <= 3 points + 2 standard errors
  per eval file and <= 1.5 on 20% of the train file held out of the fit; the label share of "fact predicate is a common word" within 4 points across labels (6 on
  small files). R4/R5: every count lookup (K45 in cues.py) <= 50% on every eval file; the per-depth worst lookup is REPORTED next to its bar.
  Results on the built rows: R1 type gain 0.0-0.2 points (v1: 19), class share 50.0 / 50.0 / 49.8 (v1: 20.8 / 20.2 / 62.2); R2 type gain 0.5 (hold-out) and
  1.0 / 2.1 / 5.4 on dev / wording / newwords (v1: 10.2 / 11.5 / 8.1), shares within 3.2 points; R4 worst count lookup 47.5 dev / 48.1 gate; R5 (20k-row sample)
  worst count lookup 45.7 dev / 44.2 gate, by depth on the gate 56.7 / 40.3 / 44.8 / 49.0 (depths 0-3), count-feature regression 57.3% gate (v1 61.0), depth 3

  (depths 1-3: 80 / 65 / 55) sit 6-30 points above their cue levels (50 / 52 / 49). A depth-3 or whole-gate number is never cited as chaining unless the full set of
  bars holds. The R5 audit on the full 130k-row train file is repeated and pasted in the results file.
- ladder-hashes.json now seals the BYTES of every file of every rung (lt2.ensure_rows hashes the files on disk when a rung starts, refuses a rung the file does not
  list, and the box rebuilds rows from this code). Rungs 4-5 are added when their local builds finish; their orders are not sent before that.

Reading changes (instruments, not thresholds):

## Addendum 3 (2026-10-14 ~11:20 AM ET; written BEFORE any rung 1-5 result is read; no box had reported anything)
State at writing: box 4 (a slow Xeon Phi host) has been on rung 1 since 9:57 AM ET with no result; five more boxes (one per rung, 4090/3090-class, fast CPUs) are being

R2: the binding gate (rows unchanged). SHOWN by the review: a lookup that never checks "one fact has BOTH the query entity and the query predicate" reaches 90.6 / 90.3 /
91.3 on R2 dev / wording / newwords (a hand-written 10-line rule: 90.6 dev), against the dev mark of 90, because distractor polarity is an independent coin flip. The
rows that need binding are the HARD NEGATIVES: answer "unknown", the query entity occurs in one fact and the query predicate in a DIFFERENT fact (164 of the 1,200 dev
rows = 13.7%; 170 wording, 92 newwords). A binding-free reader scores 31-37% on them. New rule, fixed now:
- R2 passes when, at some pair of consecutive evals (the stop rule), BOTH dev >= 90 AND hard >= 80, where `hard` = accuracy on the hard-negative subset of the dev file
  (logic_transfer/hard.py derives hard.jsonl from the sealed dev file by one function; its bytes are sealed in ladder-hashes.json: sha256 1c415b9285ba...). The stop
  marks, the PASS count and the FAIL count all use both. A run that reaches dev >= 90 but stays below 80 on `hard` is NOT a pass; it is reported as "binding-free level"
  (the reading: it learned the polarity statistics, not the binding).
- Reported next to the R2 count baseline (45.33): the strong count baselines of the review (K45-style count keys 65-71% on R2 files; polarity-aware keys ~90%, the same
  cue). R2's "+25 over baseline" is read against the dev mark 90 AND the hard-negative gate, not against the 45.33 alone.
- R1 note (reported, not gated): a first-letter / first-syllable comparison is enough to pass R1 (99.5% by lookup on prefix equality). An R1 PASS shows "compares the
  words somehow"; the swap-the-queried-name probe is the whole-word evidence.

R5: the shallow-reader ceiling (REPORT-ONLY; verdict words unchanged). SHOWN by the review, reproduced here on the sealed full rows (cues.py `--shallow`, 130k train rows):
a lookup on the LOCAL structure around the query (rules whose head is the query predicate, a status per premise: given / complement given / some rule concludes it /
absent, plus facts about the query entity and predicate), that never follows a derivation chain, scores on the R5 gate
by depth 0 / 1 / 2 / 3 = 100.0 / 99.5 / 81.8 / 76.6 (whole gate 89.5), on dev 100.0 / 100.0 / 80.0 / 75.8 (86.8), on deeper (depth 4 / 5) 71.8 / 66.7 (69.2).
That is above every sealed bar (80 / 80 / 65 / 55). Reading rules, fixed now:
- The R5 verdict (PASS / MIXED / FAIL) stays defined by the sealed bars. A PASS is worded "clears the sealed bars; a local-rule-matching reader clears them too" and is NOT
  worded as chaining.
- CHAIN-EVIDENCE tier (reported beside the verdict): >= 5 of 6 runs have, at their last whole-file gate eval, depth 2 >= 91.8 AND depth 3 >= 86.6 (the shallow ceilings
  + 10 points); deeper (depth 4-5) is read against 79.2 (69.2 + 10), reported only.
- The next step after R5 changes accordingly: PASS with the chain-evidence tier -> re-seal and run the LT-1 transfer test (arms C / L / P, >= 5 seeds). PASS without it ->
  NOT yet "a logician": the next object is an R5v3 whose bars sit above the shallow ceiling (new rows, new marks, written before it is read), not the transfer test.
  R4 (depth 1) is one rule step: a local reader IS the task there, so R4 is read as "one-step rule use", with its shallow ceiling printed in the results file.
- The same rule protects the FAIL side: a FAIL below the shallow ceiling is the stronger statement ("does not even match local structure").
