# Fast sleep: results of the 2-parent screen (10-06, finished 11:08 PM ET)

Ben asked (8:58 PM ET 10-06) for a sleep step that learns quickly without many FLOPs. Marks: `PASS-MARKS.md` in this folder, written at
9:09 PM ET, before any run. Code: `creative/fastsleep.py`. Raw numbers: `creative/results/fastsleep/` (both on branch `claude/project-thread-2kevpk`).
Everything here is DEV (the C2 tuning split). The test and labelled splits were never opened. All runs used this cloud CPU, so no PC, Mac or Vast time was spent.

## The answer in plain words

Give the model a **notebook** instead of making it study. The new sleep writes each night's good tries into a memory. When the model meets a
similar step later, it looks up its nearest notes and nudges its choice toward what worked. No weights change, so it can't overwrite skills.

## What "fast" means here (the coordinator's default, used throughout)

Fast means a large DEV first-try gain per sleep FLOP. A first try counts when it fits every example AND is right. The gain is measured against
job 6's plain fine-tune at the dose job 6 chose: s100 lr 1e-3 x 16 visits, s101 lr 3e-4 x 16 visits. Both doses were re-run here on the same parent
N, rebuilt exactly as job 6 builds it. The warm and stepping-stone losses match the Mac to 4 digits: s100 1.4936 / 0.6594 and s101 1.6073 / 0.3631.
Both runs used the same pool temperatures (3.0 and 4.0) and the same record counts (|W| = 365 and 210).

written in, it keeps them, and even beats N, which itself had already lost most of add/mult in the stepping-stone sleep. More old notes trade
new-kind gain for old-kind keeping (2,048: +28.1 new, 40.2 old). Mac job 7 tests the fine-tune's version of this, replaying 2,048 old rows. If
that works, the forgetting edge narrows but the FLOP gap does not.

## How the memory works (for the build thread)

- After the night's search, run one teacher-forced forward pass per kept record with the weights frozen. At each forced step t, store the
  thinker state that feeds `op_head` as the key. The value is the forced op plus the slot ids of its two operands (B2's own pointer targets,
  27 slots), and a separate answer note (answer-query state, answer slot).
- At inference, the model finds the 16 nearest keys at the same step by cosine similarity, weights them by softmax(sim / 0.05), and adds
  50 x (vote share) to the op and slot logits. This happens only when the best similarity clears a per-step gate.
- The gate is the 0.99 quantile of the best similarity over as many skills TRAIN replay rows as records (never DEV, never the harm set), with
  a floor of 0.9. That is why skills harm is 0: skills states almost never come close enough.
- The FLOPs counted are the record forwards, the calibration forwards and the 512 old-programme forwards. With frozen weights the old notes are
  made once per parent, so a real night pays about 0.4-0.7 TFLOP, or 0.16-0.29 TFLOP without calibration.

## Caveats and disclosures

- **Tuning.** DEV is the tuning split. Three things were added after seeing s100 numbers: the v2 slot votes, the calibrated gate and the old
  programmes (addenda 1 and 2, written before the s101 numbers). s101 was the untuned test. Two parents is a screen. The marks say a pass goes
  to a 6-seed confirm with the setting frozen.
- **Composition.** The memory is a nearest-neighbour lookup and does not compose. It wins on kinds whose programme shape repeats: square
  0 -> 92%, and last_digit 0 -> 47-86%. sq_plus and affine stay near 0 for every method, the fine-tune included.
- **Weight changes.** The memory needs fixed weights. Any later weight sleep must rebuild the keys, which costs one forward pass per stored record.
- **Growth.** The memory grows each night: 877 notes on s100 and 722 on s101 here. Lookup cost grows with it, but stays small next to a forward
  pass at this size (a dot product per note per step). A periodic weight consolidation would fold old notes into the weights.
- **Machine differences.** Job 6's s100 practised reach@32 was 7.0 on the Mac and 9.8 here, with the same code and seed but a different machine.
  The differences between machines are inside the noise of 256 questions.

## Proposal (sent to the creative roadmap thread through the coordinator)

1. **Nightly sleep = memory sleep.** Write the night's W records, plus a fixed set of old solver programmes, into the memory. The weights do not
   change and it costs about 1/25 to 1/50 of today's FLOPs.
2. **Weight consolidation** = job 6's fine-tune, run rarely, for example when the memory passes a size. After it, rebuild the keys.
3. **Next step: a 6-seed confirm** with memory + old frozen as in addendum 2, on the B2 parents of seeds 200-205. Those checkpoints live on the
   PC from the q33 confirm. The marks are below, written before the confirm runs.

### Confirm marks (written 11:15 PM ET 10-06, before any seed 200-205 run)

- B is job 6's rule (best DEV first try within 2 points of harm) over lr {3e-4, 1e-3} x 16 visits on PC, re-run on each parent.

  1. Memory + old FLOPs are at most 1/10 of B's on every parent.

## Roadmap ruling (10-06, roadmap commit 0a80e4f007, section 7, relayed by the coordinator)

- Mac job 7 runs unchanged. It tests whether parts kept in the weights compose, which a notebook can't do.
- C2b keeps W (weight sleep) as its marked arm. It adds memory as a reported second arm M, with the frozen setting above, the same old notes,
  an R-notebook placebo, the same marks and the strict near-copy label.
- The 6-seed confirm is endorsed as written (DEV only, no sealed split). It runs on the cloud CPU and must not delay job 7. Its warm-up and
  stepping-stone parents are kept for C2b.
- Nightly design: memory does nightly recall. Weight sleep does the climbing if job 7's climb passes. If the climb retires, memory alone is the
  nightly sleep for near-copy kinds.
