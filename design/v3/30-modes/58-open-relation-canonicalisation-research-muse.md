# 58 — Open relation canonicalisation research (scout, no code)

Status: research only. No code changes. All claims below are from the cited papers/docs or explicitly marked estimates; coverage count is **not computed**.

Context: ears output OPEN relation strings. `scripts/fable_thought49_schema.py:suggest_relation_id` assigns a `relation_id` only on exact normalised match against WebRED's 521 names (`data/open/webred/frames/relations.json`); `scripts/fable_reasoner50.py` hops by exact relation name and abstains (`MISSING_FACT`) on unknown relations. Ben's rule: no large LM at run time; only explainable plain software or tiny learned parts.

## Survey (no large LM at run time)

**1. CESI — embeddings + side information, then cluster.** Learns HolE embeddings of noun/relation phrases with side-information soft constraints (entity linking, PPDB, WordNet, IDF overlap), then hierarchical agglomerative clustering; cluster representative = member nearest the frequency-weighted mean (Vashishth et al., WWW 2018, https://arxiv.org/abs/1902.00172; code https://github.com/malllabiisc/cesi). *Here:* run OFFLINE once to propose alias clusters, freeze the output as a human-checked table; at run time only the table ships. *Precision:* beats prior art on ReVerb45K in the paper, but relation clusters have no gold IDs — expect high-80s/low-90s precision on frequent paraphrases, worse on rare ones. *Breaks:* needs a GPU-ish training step (allowed offline? still a learned embedding, harder to explain than a table); silent merge errors propagate to the reasoner as wrong hops.

**2. CaRe — canonicalisation-infused embeddings.** Adds CESI cluster edges to the graph and parameterises relation-phrase embeddings with a Bi-GRU over the phrase's word sequence, on top of any base KG model (Gupta et al., EMNLP 2019, https://doi.org/10.18653/v1/d19-1036). *Here:* the only reusable part under Ben's rule is the tiny piece — a word-sequence encoder for relation phrases. *Precision:* improves link prediction over non-infused baselines in the paper; as a canonicaliser per se it is not evaluated. *Breaks:* a neural encoder at run time is a learned part needing its own install/gate recipe; overkill when our target set is a fixed 521.

**3. Galárraga et al. + AMIE — entity-link first, mine relation equivalences.** Link subject/object to IDs, then mine Horn subsumptions `r(x,y) ⇒ r0(x,y)` under the Partial Completeness Assumption, merging both directions into equivalences scored by min PCA confidence (Galárraga et al., CIKM 2014, https://suchanek.name/work/publications/cikm2014.pdf; AMIE, https://luisgalarraga.de/docs/amie.pdf). *Here:* run OFFLINE on WebRED train triples to propose equivalences (e.g. `be-named-after ⇔ take-its-name-from` style), hand-verify into the alias table. *Precision:* AMIE rule precision is ~30–40% raw (AMIE paper §6) — usable only as a proposal engine with a confidence/support cutoff plus human review. *Breaks:* needs linked entities; on unlinked open strings the Mumbai/Bombay problem returns (paper §2).

**4. Wikidata property aliases (P-numbers).** Every property has an ID plus a multilingual alias list (e.g. P1376 "capital of" lists "national capital", "is capital of", "county seat of", …; http://wikidata.org/wiki/Property:P1376); all structured data is CC0 (https://www.wikidata.org/wiki/Wikidata:Data_access/en). *Here:* dump aliases once, map each alias to the matching WebRED name (WebRED labels are drawn from Wikidata properties; Ormándi et al., https://arxiv.org/abs/2102.09681). At run time: exact lookup in the frozen table. *Precision:* near-100% on listed aliases (curated synonyms), zero on unlisted paraphrases. *Breaks:* aliases are noun-centric and miss verbal paraphrases ("X is the capital of Y" vs "X serves as Y's capital"); some aliases are ambiguous across properties and need a denylist.

**5. Inverse-relation pairs.** Wikidata declares inverses explicitly (`inverse property` P1696, https://www.wikidata.org/wiki/Property:P1696): P36 "capital" ⇔ P1376 "capital of" (see https://www.wikidata.org/wiki/Property_talk:P36); likewise mother/father/child families. *Here:* a frozen two-column table; the reasoner stores one directed hop and answers queries in either direction. *Precision:* 100% by declaration (constraint violations exist but are data errors, not rule errors). *Breaks:* only covers declared pairs; asymmetric relations (e.g. "follows"/"followed by") need each pair hand-listed; never infer an inverse from co-occurrence alone.

**6. Synonym clustering by (subject, object) co-occurrence.** RESOLVER's Extracted Shared Property model: two relation strings are synonyms if they share many identical (subject, object) instances, scored by an urn-model probability, combined with string similarity (Yates & Etzioni, NAACL-HLT 2007, https://aclanthology.org/N07-1016/): relations 90% precision / 35% recall on 2M assertions. *Here:* OFFLINE proposal only — count shared entity pairs per relation pair on WebRED train, keep high-precision pairs for review. *Precision:* expect ~90% at low recall (per the paper), collapsing on our skewed data (top relations like "country" dominate). *Breaks:* needs exact entity match, so unlinked mentions ("Mumbai" vs "Bombay") hide true synonyms; antonyms sharing pairs ("shares border with" vs "diplomatic relation") false-positive.

**7. String + rule normalisation.** Lowercase, strip, collapse whitespace (already `norm_relation`), plus deterministic rules: strip auxiliaries ("is X of" → "x of"), de-pluralise, fixed prefix/suffix table. *Here:* the cheapest first stage before any table lookup; fully explainable. *Precision:* ~100% on what it touches, tiny coverage. *Breaks:* stemming merges distinct relations ("follows" vs "followed by"); keep an explicit exception list.

## Smallest concrete pipeline (all plain software at run time)

1. **Alias table** `alias → WebRED canonical name`, built once from the Wikidata alias dump intersected with the 521 names, plus hand-reviewed CESI/AMIE/ESP proposals; ambiguous aliases go on a denylist. Lookup is exact-match after `norm_relation`. Coverage of the 521: **not computed** (requires downloading the Wikidata dump; no fetch performed).
2. **Inverse table** `(relation → inverse relation, swap flag)`, seeded from P1696 declarations for properties overlapping WebRED (at minimum: capital P36 ⇔ capital of P1376; mother/father/child/sibling/spouse symmetric-or-paired). The hop loop stores the canonical direction and traverses either way.
3. **UNKNOWN bucket:** anything matching neither table keeps its raw string with `relation_id=None` (today's behaviour) and the reasoner abstains (`MISSING_FACT`/UNSURE) rather than guessing. Unknown strings are logged for the next offline table-building round — never auto-promoted.

## Sealed-mark experiment (plain software, Mac CPU, on `data/open/webred/frames/dev.jsonl`, 3,898 rows)

Dev rows carry gold `relation` + `relation_id` (e.g. P150), so: (a) **alias accuracy** — pipeline output `relation_id` equals gold on all positive rows (pass: 3898/3898 rows agree, integer count); (b) **inverse round-trip** — for rows with capital/capital-of, swap subject/object + relation through the inverse table and require the same canonical hop (pass: all such rows round-trip); (c) **abstention** — 200 fabricated relations ("was born in xyzzy") must all yield `relation_id=None` and reasoner `MISSING_FACT` (pass: 200/200). Seeded, deterministic, one process. Pre-register marks in `PASSMARKS.md` + hash before running.

## What it means / What it does not mean

It means we can canonicalise open relation strings into WebRED's 521 (+ inverses) with fully explainable tables, an abstaining UNKNOWN bucket, and a registration-ready dev.jsonl test. It does **not** mean coverage is known (not computed), that learned methods (CESI/CaRe) run at inference (they are offline proposers only), or that any paraphrase outside the tables will be understood rather than abstained on.
