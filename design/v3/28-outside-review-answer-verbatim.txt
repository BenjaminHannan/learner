The project has a viable engineering goal, but it does not currently have evidence for its central learned-reasoning claim.
Those are different problems. A useful teachable notebook assistant can use a deterministic executor. A claim that a learned
controller discovers a length-general algorithm requires evidence you do not yet have.
I would preserve that distinction rather than keep the entire project dependent on rescuing the dispatcher.
I treat R1–R8 as reported measurements, not independently verified results. The probabilities below are subjective forecasts
for the specified experiments, conditional on correct implementation—not estimates established by three seeds. Proposed
pass marks are new proposals, not reinterpretations of your existing registrations.
The experiments below are a menu, not 44 simultaneous assignments. Use saved-checkpoint probes first. For new training,
establish throughput before registration; fit each diagnostic into your wave limit, and use separate waves for additional
seeds. Report a budget-limited failure as such, rather than silently extending it or calling it architectural impossibility.
A. Reasoning core 1. Should the dispatcher be learned at all?
Severity: Blocking for the learned length-generalisation claim; not blocking for a teachable assistant.
For a question already supplied as an ordered relation path, the desired algorithm is already specified: apply its elements in
order. Discovering that algorithm through terminal-reward RL is unnecessary for the product. It creates a difficult learning
problem without adding a user capability.
Hard-code the loop for the assistant. What you lose is the claim that the model learned sequencing or iteration. What
remains is learned language interpretation, possibly learned memory access, and externally stored factual knowledge. Do
not describe the resulting length generalisation as something the controller learned.
The likely problem is that your controller learned a training-distribution policy rather than an invariant transition rule. I would
change that diagnosis if an unchanged controller generalised reliably on fresh, longer, non-shortcut chains.
Cheapest test: Run the fixed executor and learned dispatcher against the same frozen operator, on identical 1–10-hop
cases, recording every intermediate answer. Include chains deliberately constructed so that skipping a link changes the final
answer.
Forecast: Probability 0.85 that the fixed executor removes most controller-attributable long-chain failures on the two
successful operator seeds; 0.20 that the existing learned dispatcher reaches ≥99% at every tested length.
2. Why “third call = attribute,” and what is the minimal repair?
Severity: Serious; blocking for the present controller.
On training paths of at most three operations, “at the third call, choose the final attribute” is a valid shortcut. The training
data cannot penalise it at the position where it differs from the intended algorithm. A GRU can represent elapsed execution
through its hidden state even without an explicit call counter.
The minimal principled architectural change is to make the operation head depend on position relative to the previously
selected path occurrence, rather than unrestricted recurrent history. Maintain a cursor storing the last selected occurrence;
let a shared scorer learn which relative position comes next. Initialise the cursor before the path. Do not hard-mask
everything except the correct next operation—that would supply the answer.
This is an explicit inductive bias and external state, not discovery from nothing. Also, point to occurrences, not just relation
types: repeated relations otherwise create an ambiguity.
Cheapest test: First probe existing checkpoints with correct two-step prefixes on matched three- and four-operation paths.
Then, in one bounded training contrast, change only the operation head’s positional representation. Leave subject and STOP
mechanisms unchanged.

3. What caused constant-call collapse, and what should replace this RL setup?
Severity: Serious.
My leading explanation is poor success-signal coverage combined with a readily learnable preference for shorter failures,
not RLOO inherently being unsuitable.
With reward R = 1[correct] − 0.01L, a group containing only unsuccessful trajectories still supplies a useful gradient: prefer
the shorter failures. If a successful trajectory has probability 1%, approximately 0.99^16 = 85% of sixteen-sample groups
contain none. This is an illustration, not a measurement of your runs.
Correctly implemented leave-one-out baselines do not by themselves change the expected policy-gradient objective. RLOO
is a variance-reduction method, not an exploration solution. Its published successes do not establish suitability for your
sparse algorithm-learning problem.
Cheapest decisive experiment: Replace only the controller-training objective with supervised cross-entropy on exact
execution traces. Your generator already knows those traces. Compare free-running execution, not merely teacher-forced
action accuracy.
Forecast: 0.80 that trace supervision substantially improves training-length execution or sample efficiency; 0.30 that it alone
achieves ≥95% on every 4–8-hop cell. Representation-induced shortcuts may remain.
Evidence against my diagnosis would be abundant successful long trajectories, sustained operation entropy, and correct
gradient implementation throughout collapse.
My recommendation is imitation first, then training on the learner’s own visited states if necessary. That addresses the
distribution shift between oracle prefixes and actual execution; DAgger is the relevant established framework. Add RL only
when optimising something the available labels do not already specify. Planning-as-inference is unnecessary machinery
here.
4. How should you handle seed variance?
Severity: Serious for reliability claims; not a reason to stop experimentation.
Two successful seeds out of three establish that the procedure sometimes works. They do not establish dependable
training. For the actual 2/3 result, the two-sided exact 95% binomial interval is approximately 0.094–0.992, assuming
exchangeable independent training runs.
Seed sensitivity is evidence that the training procedure as a whole is fragile. It does not isolate architecture from
optimisation, initialisation, data order, or numerical implementation.
Separate two quantities: reliability of an already-trained checkpoint, and probability that the training recipe produces a
reliable checkpoint. Thousands of questions improve knowledge of the first, not the second.
Cheapest experiment: Before retraining, subject all three existing seeds to identical counterfactual and per-hop probes.
Then run one additional, preselected seed under the unchanged recipe. Preserve every result and disclose checkpoint-
selection rules.
Forecast: Under an illustrative uniform Beta prior and genuinely unchanged protocol, my next-seed pass probability is 0.60.
The corresponding probability that the next three all pass is about 0.29, not 0.60^3, because uncertainty about the
underlying success rate is shared.
Do not spend the project trying to certify 90% training reliability. Even 29/29 successes are needed for a one-sided 95%
lower bound just above 90%.

8. Can unseen relations be handled without relation codes?
Severity: Blocking for open-ended teachability.
Distinguish three problems:
New wording for a known relation is language interpretation. A new arbitrary relation with explicitly supplied facts requires a
dynamic key. A genuinely new operation, such as “oldest,” requires semantics beyond key lookup.
Codes are not the only representation. Exact text keys, span pointers, and descriptions compiled into a small executable
language are alternatives. But arbitrary new relations need some contextual binding mechanism. A fixed classifier over
relation labels cannot become open-ended merely by seeing more examples.
The likely cause of R6 is a representation/training regime that treats relation identity as a fixed learned category. I would
revise that if the model already receives usable dynamic keys and still fails exact matching.
Cheapest experiment: After entity copying works, replace only relation identity with a dynamic key representation. Train on
randomly renamed relation labels; evaluate on freshly generated labels, first one hop and then two.
Forecast: 0.65 that a generic key-matching reader achieves ≥95% unseen-relation one-hop accuracy; 0.40 for the same
threshold on two-hop compositions within the initial budget. Neither would establish learning a new computational operation
from English.
9. Which additional reasoning operations break the lookup loop?
Severity: Blocking for general reasoning.
The current single-entity, scalar-valued chain cannot express most of that list without additional state or primitives.
“Same teacher” requires a reverse lookup or join. Counting requires a collection and distinctness policy. Comparison
requires typed values. “Or” requires union or branching. Time requires selecting a version of a fact. Negation requires an
explicit distinction between false and unknown.
These do not defeat a database-backed architecture. They defeat the claim that one scalar lookup loop is a sufficient
reasoning language.
Cheapest experiment: Write ten desired questions and their exact executable meanings before training anything. Use a tiny
deterministic relational executor with operations such as LOOKUP, FILTER, JOIN, UNION, COUNT, and COMPARE. Test each
new primitive separately.
Falsifier: If the current interface already supports collections, branching, and typed predicates, my description of its
limitation is wrong.
Forecast: 0.95 that at least three questions require an interface extension. Do not invent a separate learned “reasoning
module” for arithmetic that a deterministic primitive can perform exactly.

11. Should output be pointer/copy rather than a global code prediction?
Severity: Serious design issue; pointer output is my preferred end state.
When the desired entity already occurs in the memory being read, predicting its identity from a global vocabulary is solving
an unnecessary reconstruction problem. Select a memory value or entity handle and copy it.
Pointer networks were explicitly designed to select positions from variable-sized inputs; pointer-generator models combine
copying with ordinary lexical generation. This is established machinery, not a concession that invalidates the assistant.
For multi-hop execution, resolve the selected occurrence to a canonical entity ID. Feed that exact ID into the next lookup. Do
not feed a diffuse attention-weighted mixture of several name vectors.
Multiple occurrences of the same entity should map to the same ID. Training should accept any equivalent occurrence, or
aggregate their probabilities.
Cheapest experiment: Replace only the entity-output head with a pointer over eligible memory values, preserving the rest of
the reader.
Falsifier: If memory selection itself is wrong and pointer output does not improve links, reconstruction was not the dominant
remaining problem.
Forecast: 0.70 that this outperforms frozen-scale global decoding on unseen-name links under equal training effort; 0.50
that it clears all current name-test cells in three seeds.
12. Where do 48-dimensional random codes break?
Severity: Serious measurement question, not evidence that 48 dimensions are inherently insufficient.
First distinguish exact identity, noisy retrieval, and softmax confidence.
Assume independent, uniformly distributed unit vectors in 48 dimensions. Pairwise cosine similarity has mean zero and
variance 1/48. My spherical-tail calculation gives approximately:
For one specified code among 4,096, roughly one competitor exceeds cosine 0.48.
Across all pairs in that table, roughly one pair exceeds 0.66.
At 10,000 codes, those thresholds rise to approximately 0.51 and 0.69.
These are approximate tail-count thresholds, not measured properties of your table or hard capacity limits.
If the query is exactly the correct unit code, its self-similarity is one: it wins against every distinct code regardless of how
many there are. Failure arises when the query is noisy, codes have problematic norms, or implementation precision destroys
the margin.
For an ideal copied query and logits β qᵀe_j, a Gaussian approximation gives
p_correct ≈ [1 + (M−1)e^(−β+β²/(2d))]^−1.
At M=4096,d=48, this is approximately 0.949 at β=13 and 0.987 at β=15. Thus your estimate is plausible for confident
softmax output under these assumptions—not a guarantee about learned queries. Temperature changes confidence, not an
unchanged argmax.
Cheapest experiment: Round-trip the actual code table through the output rule using ideal copied queries, then separately
test measured model queries and controlled perturbations. Report margin distributions and errors by table seed.
Forecast: 0.95 that ideal normalised copying is essentially perfect; 0.80 that query error or norm handling becomes limiting
before literal vector collision.
A fixed pool of 4,096 unique identifiers also has an obvious separate limit: it cannot name more than 4,096 simultaneous
distinct entities without expansion.

My minimal design is an append-only event log plus a derived current view. Each assertion records entity ID, relation ID,

18. How do you preserve “I don’t know”?
Severity: Blocking for trustworthy factual replies.

D. Talker 20. Is the 416-number thought bottleneck sensible?
Severity: Serious; blocking if treated as an enforceable factual boundary.
It is a possible interface, not evidence of semantic transparency.
The 256-number gist is an obvious bypass, but even continuous “typed” fields can encode unintended information.
Research on concept bottlenecks documents exactly this distinction between an interpretable label and what a continuous
representation actually carries.
Moreover, 256 float16 values have 4,096 raw representational bits. A 48-token sentence from an 8,192-token vocabulary
needs only 624 bits to specify its token indices. This is not an estimate of learned channel capacity, but it demonstrates that
the gist is not intrinsically too small to encode the entire sentence.
The opposite problem is also real: three relation slots impose a three-relation interface ceiling, regardless of a ten-hop
operator.
Cheapest experiment: On factual acts, hold typed fields fixed while swapping or zeroing gist between examples; separately
change the notebook answer while holding the input thought fixed. Check whether factual output follows verified execution
or the latent side channel.
Forecast: 0.80 that unconstrained joint training makes gist causally relevant to factual content.
Falsifier: Factual outputs are invariant to gist interventions and change correctly with verified memory interventions. My
recommendation is a variable-length structured event/program interface, with gist excluded from factual authority.

MISSED PROBLEMS
M1. The output candidate set is ambiguous. You describe 4,096 output candidates but chance performance of 1/16. Those
can coexist if training and evaluation use different masks, but that distinction is consequential. Specify the candidate set
used by the loss, decoding, and chance calculation.
M2. “Never trained” codes may have appeared as negatives. If all 4,096 codes participate in the training softmax, the held-
out half influences the objective even when never used as positive labels or inputs. A stronger zero-shot test generates
fresh codes after training.
M3. Sampling codes with replacement can create actual identity collisions. Sixteen independent draws from 4,096 codes
have about a 2.9% probability of at least one repeated code. Assert uniqueness within each world. Persistent global identity
requires a different allocation policy.
M4. Rebinding codes between worlds is not persistent identity management. A procedure valid for independent training
episodes can corrupt a notebook if reused across sessions.
M5. Long chains in small worlds can collapse semantically. Repeated nodes, cycles, shared destinations, and small final-
answer sets can make an incorrect shorter execution return the same answer. Test deliberately non-shortcut chains and
verify traces.
M6. One-hop accuracy under random queries may overstate multi-hop reliability. Intermediate entities reached during
execution need not follow the same distribution as uniformly sampled subjects. Evaluate atomic accuracy conditional on
being reached at each hop.
M7. Pipeline reliability compounds. Under an illustrative independence assumption, five components each succeeding 99%
of the time yield only about 95% end-to-end success. Do not substitute excellent isolated slot scores for full-turn
correctness.
M8. The unit of evaluation may be wrong. Hundreds of questions drawn from a handful of worlds are not hundreds of
independent tests of world generalisation. Preserve world IDs and report world-level structure.
M9. “Perfect” needs a denominator and dependence caveat. Even 512 independent error-free trials permit a one-sided 95%
error-rate upper bound of about 0.58%. Correlated trials justify less confidence.
M10. The act count needs clarification. You list nine act families and an eight-number act field. That is fine for an eight-
dimensional embedding, but impossible as a one-hot encoding of nine mutually exclusive acts. Verify the actual contract.
M11. Arbitrary literal values need representation. Names are not the only out-of-vocabulary problem. Addresses, quotations,
dates, measurements, filenames, and free-text notes need lossless storage and copying too.
M12. The copy inventory may omit entities introduced by retrieval. A question can ask for someone never mentioned in the
current utterance. Copy targets must include eligible notebook and tool-result values, not only input-side names.
M13. Slot-wise accuracy can conceal unusable joint accuracy. Correct act, subject, relation, and object must occur together.
Register exact whole-event correctness.
M14. Autoencoding can succeed while the latent is largely ignored. Teacher forcing gives the decoder previous gold words.
Evaluate generation from the latent alone and perform latent counterfactuals.

--- page 18 ---
M15. Raw-text skip paths can defeat the advertised bottleneck. Encoder cross-attention, residual routes, cached states, and
auxiliary inputs must be included in the information-flow audit.
M16. Acknowledgement is not transaction success. “I’ll remember that” must only be emitted after a validated durable write,
not merely after predicting the TELL act.
M17. Quotes, hypotheticals, and reported speech are not assertions. “Suppose Mira had a drum” and “Jon falsely said Mira
had a drum” must not write the same fact as “Mira has a drum.”
M18. Working context and durable memory need separate namespaces. A temporary assumption used to answer one
question should not silently become a permanent belief.
M19. Schema changes can invalidate old memories and checkpoints. Version entity records, relation semantics, thought
schemas, and migrations. Round-trip tests should survive restart and upgrade.
M20. Repeated delivery can duplicate mutations. Tool retries and resumed sessions need event IDs or another idempotency
mechanism. Otherwise corrections, counts, and histories can be applied twice.
M21. Deleting a source fact may leave derived answers alive. Track dependency invalidation in caches, inferred facts, and
summaries—not only the main table.
M22. The parameter count is not the complete system size. Report frozen parameters, non-trainable code tables, external

M23. The same model seed can hide several randomness sources. Separate weight initialisation, data order, codebook,

skipped batches is not the continuation you think you ran.
M25. Constant-call policies may exploit answer-frequency imbalance. Evaluate majority-value, most-recent-value, first-row,
and random-active-entity controls. Use the actual candidate distribution when computing chance.

evidence but imply different held-out labels. Check identifiability before treating every failure as an optimisation problem.
M27. Data volume is not distinct information. Track unique source documents, duplicate rates, template families, and
repeated semantic events. “1.2B tokens” can hide a much smaller effective training distribution.
