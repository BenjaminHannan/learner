# V0 CPU probes: pass marks fixed before running (2026-10-03, Opus vision thread)

Frozen SigLIP2-B/16 @256px (`google/siglip2-base-patch16-256`), CPU only, synthetic images, ridge linear probes.
Train and test images come from different random seeds. Probes are linear, so every number is a lower bound
on what a trained adapter + core could extract. This is a check on the *encoder and pooling*, not on reasoning.

Tasks (all synthetic, generated by `make_images.py` logic inside `probe.py`):
- **count**: 1-9 small shapes (8-14 px) on a plain background. 9-way. Chance 11%.
- **relation**: one red and one blue shape; is red left of blue? (2-way, chance 50%).
- **more**: 2-7 red and 2-7 blue shapes (never equal); are there more red? (2-way, chance 50%). Count-then-compare.
- **tiny digit**: one digit 0-9 drawn 9 px tall at a random spot (hotbar-count size on a 256 px view of a screen). 10-way. Chance 10%.

Feature variants: layer {last, penultimate} x pooling {16x16, 8x8, 4x4} x width {full 768, PCA-128, PCA-32 per patch}.
Plus a raw-pixel baseline (32x32 RGB, same probe) to show whether a task is trivial without the encoder.

Decisions (accuracy on test, linear probe):
- **P1 pooling.** Compare 8x8 vs 16x16 (best layer, full width) on count and tiny digit.
  8x8 worse by >=10 pts on either -> default becomes 16x16 tokens (needs the coords bias, not CLIP=4 alone).
  Within 3 pts on both -> keep 8x8. Between -> keep 8x8, flag.
- **P2 layer.** Penultimate vs last (8x8, full width), mean over count, relation, more.
  Penultimate >=5 pts better -> use penultimate. Within 2 -> keep last. Last >=5 better -> keep last.
- **P3 width.** PCA-32 vs full (8x8, best layer), mean over the four tasks.
  PCA-32 worse by >=10 pts -> adapter hidden starts at 128 not 32. Within 3 -> keep 32.
  (PCA is unsupervised, so a learned 32-wide adapter could do better; a big PCA-32 loss is a warning, not proof.)
- **P4 small text.** Tiny digit at 16x16, best layer, full width.
  <50% -> the Minecraft roadmap needs a high-resolution glimpse/crop path for UI text. >=80% -> a global view may do.
- **P5 too easy?** If the linear probe already gets >=90% on **more** (count-then-compare) at 8x8,
  that task cannot show the core's reasoning; S2 must use harder compositions. If raw pixels already >=90% on a task,
  that task is not a vision test.

What would prove the setup itself wrong: if raw pixels beat SigLIP2 features on count or relation by >=10 pts,
the encoder (or how features are read) is not suited to these spatial tasks at all.

## Addendum A (written after P1-P5 results, before running P6)
P1-P5 used one target per image, and every pooling level (even 4x4) kept it. That may be because a frozen ViT
spreads one salient object across all patches. It does not show that *many* small items survive pooling.
- **P6 hotbar.** A row of 9 slots (18 px each) at the bottom, each with its own digit 0-9 drawn 9 px tall, plus clutter.
  Ridge probe per slot (10-way), score = mean over the 9 slots. Chance 10%. Last layer, full width unless noted.
  8x8 worse than 16x16 by >=10 pts -> pooling loses multi-item small text; the glimpse (review R3) is justified.
  Within 3 -> keep 8x8 for UI too. 16x16 itself <50% -> even the full 256-px grid cannot read a hotbar; a
  high-resolution glimpse is needed whatever the pooling.
