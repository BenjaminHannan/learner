## Reading and writing exact numbers without a hand parser

1. **Teaching Arithmetic to Small Transformers** (Lee 2023) https://arxiv.org/abs/2307.03381. Opened: abstract.
   - Shown: small transformers trained from random initialization learn arithmetic; 'simple formatting changes' improve accuracy a lot; sharp phase transitions as a function of training-data scale (sometimes explained by low-rank matrix completion); chain-of-thought data with intermediate results improves accuracy, sample complexity and convergence speed with no pretraining; it also covers model scale and length-generalization difficulties. The abstract does not name reversal or give param counts (that reversed-digit output is the main format change is from memory, not opened).
   - For us: closest to our regime (small, from scratch, small data). Two lessons: data format changes the data needed by large factors, and there are sharp thresholds, so a 'works at N examples' answer will not interpolate smoothly. Writing intermediate results as text (a scratchpad) is exactly the 'tool call as text, result read back as text' route Ben wants.
2. **Tokenization counts: the impact of tokenization on arithmetic in frontier LLMs** (Singh 2024) https://arxiv.org/abs/2402.14903. Opened: abstract.
   - Shown: GPT-3.5/4 use 1-,2-,3-digit tokens; right-to-left grouping (forced by comma-separating numbers) 'leads to largely improved performance' over left-to-right; errors under left-to-right grouping follow stereotyped patterns; the gap shrinks as models scale; models can convert between tokenizations so chain-of-thought can recover performance. Frontier scale, not small.
   - For us: the grouping direction matters because place value is defined from the right. A char-level reader that sees the whole number bidirectionally avoids the issue, since it never commits to a left-to-right grouping. Supports the conclusion that the thing a reader must supply is 'distance from the right end', which is our place code.
3. **Transformers Can Do Arithmetic with the Right Embeddings (Abacus)** (McLeish 2024) https://arxiv.org/abs/2405.17399. Opened: abstract.
   - Shown: the failure is attributed to inability to track the exact position of each digit; fix is an embedding on each digit encoding its position relative to the START of the number; enables input injection and recurrent layers to help more; training on 20-digit numbers on one GPU for a day gives up to 99% on 100-digit addition; gains carry to sorting and multiplication.
   - For us: this is the same idea as our hand-computed place code (with the origin at the left rather than the right end, which is why the number's boundaries must be known). The embedding is computed from number boundaries by code, so Ben would call it a hand-written feature in disguise. It also supports the thinker loop idea (recurrent layers help once positions are resolved).
4. **Position Coupling: Improving Length Generalization of Arithmetic Transformers Using Task Structure** (Cho 2024) https://arxiv.org/abs/2405.20671. Opened: abstract.
   - Shown: gives the same position id to tokens of the same significance (digits of the same place in addition); models trained on 1-30 digit addition generalize to 200 digits; a 1-layer transformer with coupled positions provably solves addition with exponentially many digits, whereas one with no positional information cannot; also applied to Nx2 multiplication and a 2-D task.
   - For us: confirms the place/alignment signal is what does the work, and that without it the model fails. It is task-structure injected by code, so it is a hand-written feature. It is only needed if the model itself must align digits to compute; if arithmetic is delegated to a tool, our model needs only copy, not alignment.
5. **Positional Description Matters for Transformers Arithmetic** (Shen 2023) https://arxiv.org/abs/2311.14737. Opened: abstract.
   - Shown: models rely naively on absolute position for few-digit arithmetic and fail on larger numbers; modifying the positional encoding or the task representation fixes this. Numbers: 100M-param model with 300k samples gets 15-digit multiplication (essentially perfect to 12 digits) with no scratchpad, where usual training fails at 4 digits; addition with 120k samples extrapolates from 10 to 12 digits and reaches almost perfect accuracy up to 5 digits in a natural-language context, where usual training is right only to 3 digits ('essentially memorization').
   - For us: the best small-data number I found (100M params, 300k samples) but it is for arithmetic, not reading, and it is ~30x our parameter count. Warns that absolute positions become memorization at small data: reading a number by absolute index will not transfer across where in the question it sits, a risk for a 208-char reader.
6. **NumeroLogic: Number Encoding for Enhanced LLMs' Numerical Reasoning** (Schwartz 2024) https://arxiv.org/abs/2404.00459. Opened: abstract.
   - Shown: a causal model reading or writing a digit does not know its place value until the whole number is processed; fix is to put the digit count before the number ('42' becomes '{2:42}'); also acts like a chain of thought when generating; improves arithmetic and MMLU.
   - For us: states the exact problem our place code solves, and shows the text-level fix: let the model WRITE the length as text. For us that is a learned alternative to the hand-made place code if the reader were causal. Our reader is bidirectional (conv +-4), so it only lacks range, not direction. Honest caveat: the format is itself a regex-style rewrite of the input unless the model emits it.
7. **FoNE: Precise Single-Token Number Embeddings via Fourier Features** (Zhou 2025) https://arxiv.org/abs/2502.09741. Opened: abstract.
   - Shown: maps a number straight to Fourier features, two embedding dims per digit, one token per number; on 6-digit decimal addition needs 64x less data than subword and digit-wise embeddings for 99% accuracy, with 3x and 6x fewer tokens per number; the only method with 100% on over 100,000 test examples for addition, subtraction, multiplication. Motivated by Fourier-like features seen in pretrained LLMs.
   - For us: strongest data-efficiency number found (64x), but input numbers must first be segmented and converted to values, which is a regex-and-int parser. This is the same family as our 93-dim exact code, so it is a hand-written parser, not a learned reader. Ben would object to it. Useful only as a target for what a LEARNED reader should output internally.
8. **xVal: A Continuous Numerical Tokenization for Scientific Language Models** (Golkar 2023) https://arxiv.org/abs/2310.02989. Opened: abstract.
   - Shown: numbers represented continuously in the embedding space; trained from scratch on scientific datasets as text; generally beats other numerical tokenizations on out-of-distribution generalization and computational efficiency.
   - For us: needs a number extractor and scalar value (the abstract names no exact-digit result, so it is not evidence for exact 9-digit reading). One scalar cannot hold 9 exact digits in float, so poor for exactness. Same hand-written objection as FoNE.
9. **Efficient numeracy in language models through single-token number embeddings (BitTokens)** (Kreitner 2025) https://arxiv.org/abs/2510.06824. Opened: abstract.
   - Shown: argues that frontier LLMs burn many reasoning tokens on basic calculation, worsened by tokenizers splitting numbers; proposes BitTokens, one token per number from its IEEE 754 binary float representation; 'even small language models' learn algorithms that solve basic arithmetic 'nearly perfectly'. Also frames external tools as the alternative that 'weakens numerical representations'.
   - For us: another value-from-parser encoding (hand-written). Notable because the paper treats tool use and in-model arithmetic as competing approaches, which is the same decision we face. Float64 binary also caps exact integers at 2^53, below int64.
10. **Number Cookbook: Number Understanding of Language Models and How to Improve It** (Yang 2024) https://arxiv.org/abs/2411.03766. Opened: abstract.
   - Shown: benchmark of 17 numerical tasks in 4 categories (41 combinations); trains small models with tokenizers, positional encodings and number formats meant to enhance number understanding, and compares them; finds naive finetuning of practical-scale LLMs helps on many but not all tasks and that the number-specific techniques 'prove ineffective for finetuning pretrained models'.
   - For us: the one paper that tests these tricks side by side at small scale, so its full tables (not read) are worth opening before we choose. Its abstract suggests tricks help models trained from scratch but not pretrained ones, which fits our from-scratch B2 but warns against grafting onto EmbeddingGemma (consistent with the EGE-on-top result).
11. **The Impact of Positional Encoding on Length Generalization in Transformers** (Kazemnejad 2023) https://arxiv.org/abs/2305.19466. Opened: abstract.
   - Shown: compares APE, T5 relative, ALiBi, Rotary and no positional encoding (NoPE) on reasoning and math tasks; NoPE outperforms the others at length generalization; theory says NoPE can represent absolute and relative PE and in practice resembles T5's relative PE; scratchpad does not always help and its format matters a lot.
   - For us: evidence position information can be LEARNED rather than supplied. Counterpoint: this is length generalization of decoder-only models, not exact counting of digits from a boundary.
12. **Transformer Language Models without Positional Encodings Still Learn Positional Information** (Haviv 2022) https://arxiv.org/abs/2203.16634. Opened: abstract.
   - Shown: causal LMs with no explicit positional encoding stay competitive; probing shows they learn implicit absolute positions; the authors conjecture the causal mask lets the model count predecessors.
   - For us: a causal reader can count positions from the start of the sequence (a counting signal from the mask). Our reader is a non-causal conv with no attention, which has no such counter; a learned 'distance to the right end of this number' would need either a causal/recurrent pass run right to left, or attention. UNTESTED that this works at 9 digits.
13. **From Interpolation to Extrapolation: Complete Length Generalization for Arithmetic Transformers** (Duan 2023) https://arxiv.org/abs/2310.11984. Opened: abstract.
   - Shown: targeted attention biasing gives long-length generalization; Attention Bias Calibration (ABC) is a calibration stage that lets the model automatically LEARN the right attention biases, giving near-perfect length generalization on some arithmetic tasks, with similarities to relative position encoding and LoRA.
   - For us: the nearest thing to 'learn the alignment instead of hand-coding it': the bias is learned in a calibration stage. Caveat: the calibration still uses a model that already generalizes on short lengths, i.e. a two-stage recipe, and it is aimed at attention alignment in addition, not boundary finding.
14. **Repeat After Me: Transformers are Better than State Space Models at Copying** (Jelassi 2024) https://arxiv.org/abs/2402.01032. Opened: abstract.
   - Shown: proves a two-layer transformer can copy strings of exponential length, while fixed-state models (GSSMs) are fundamentally limited; empirically transformers beat GSSMs on copy/retrieval synthetics and in pretrained LLMs.
   - For us: copying a digit string needs attention/pointers, not place value or arithmetic. Our pointer-generator copy gate already has the right mechanism; this supports keeping attention in the reader/talker rather than a pure conv or SSM. (Complements Zoology in thinker-absorb-papers.md.)

**Takeaways (helper, ranked):**
- 1. (Largest design impact, SUGGESTED) Split two jobs that are being mixed. If every number is only COPIED into a tool call as text and the result is READ back as text, the model needs no value parser, no place code and no exact-int executor: copying is a pointer task (Jelassi: copying is what attention is for, proven for two-layer transformers; our pointer-generator already does it). The place code matters only when the model must compare or compute on magnitudes itself. This matches the text-model-plus-calculator baseline (94-96 on 5-step chains vs 99.7) and turns Ben's complaint into a measurable gap: that 4-5 point gap is the price of the learned route, and no paper tells us how much of it is reading versus step planning. UNTESTED.
- 2. (SHOWN pattern, SUGGESTED reading) Every trick that wins on small models (Abacus, position coupling, FoNE, xVal, BitTokens, value-aware prefix, NumeroLogic) supplies place value or number value from code that already knows where a number starts and ends. So all of them are hand-written features in disguise by Ben's standard, our place code and 93-dim int code included. Only the NumeroLogic idea (the model writes the digit count as text) and attention-bias learning (Duan ABC) move the work into the model, and neither has been shown at 9 digits from raw characters.
- 3. (SUGGESTED, UNTESTED) The place code can plausibly be learned, but the nearest evidence is indirect: NoPE and Haviv show position and counting are learnable in causal models, Duan shows alignment biases can be learned. The first fix to test is the one that matches our reader: replace the hand 'index from the right end of the word' with a learned right-to-left pass (a small right-to-left recurrent/causal layer, or a few bidirectional attention layers with a learned 'number end' flag), and compare with the hand code on the same rows at 1..9 digits. Pass mark fixed in advance, e.g. per-digit exact copy and exact place-index probe at least 99% at 9 digits on held-out lengths; falsified if it stays under 99% at 9 digits while the hand code reaches 99%. Note the +-4 conv cannot see a 9-digit number's far end, so range matters.
- 4. (SHOWN for scale, SUGGESTED for us) Data needs vary hugely with format: FoNE needs 64x less data than digit-wise for 99% on 6-digit addition, Shen gets 15-digit multiplication from 100M params and 300k samples with a positional fix, Lee shows sharp thresholds in data size. None of these measures reading or copying alone, which is easier than arithmetic. So treat any 'N examples for 99% reading' as unknown for us and measure it with a read/copy-only probe task on our own reader before changing anything else.
- 5. (SUGGESTED) Digit-level (char) input is not what starves the model of information; the evidence points to missing positional structure (where the number's right end is), not missing letters. Singh and Bie-style errors are misalignment, not missing digit identity, and the repo result that removing the +-4 window broke ciphers and EmbeddingGemma-on-top helped (+1.6/+2.1) fits: letters carry exact content, the extra context adds meaning. If Ben still wants more information per position, add context (a learned multi-width pooling channel, per thinker-absorb-papers.md) while keeping the raw letters.
- 6. (SUGGESTED) Number Cookbook's abstract says number tricks do not help pretrained models, which cautions against grafting FoNE/xVal-style features onto EmbeddingGemma; its tables compare tricks side by side at small scale and should be read in full before we pick any trick.

**Gaps:** No paper I opened measures reading or copying of 9-digit numbers from raw characters at under 100M params. The data and parameter question (key question 1) is unanswered: the closest figures are for arithmetic (Shen 100M/300k samples, FoNE 64x less data), not reading. No paper tests a LEARNED place/boundary signal in a non-causal conv-plus-attention reader of the kind we use; evidence for learnable position is from causal LMs (Haviv, Kazemnejad) or two-stage attention calibration (Duan). Index hints (Zhou 2310.16028 is the paper I opened for related work, but its abstract does not mention index hints), reversed-digit order as a reading input (rather than output), and randomized positions (Ruoss 2305.16843, abstract read, about string length not digits) were not verified as helping reading; I make no SHOWN claim on them. Nothing here covers a reader whose output feeds a pointer to an exact int64 executor, or the 'write the tool call as text, read the result as text' design at our scale; the tool-use side is untested in the numeracy literature I opened (BitTokens only contrasts tools with in-model arithmetic). Full-paper tables (model sizes, data sizes, failure modes) were not read; only abstracts. Open Number Cookbook, Abacus and Shen in full before relying on any number beyond the abstracts.

## Learning to call outside tools

1. **Toolformer: Language Models Can Teach Themselves to Use Tools** (Schick 2023) https://arxiv.org/abs/2302.04761. Opened: abstract page.
   - Shown: trained to decide which APIs to call, when, what arguments, and how to use results in later token prediction; self-supervised, needs only a handful of demos per API; tools include calculator, Q&A, search, translation, calendar; improved zero-shot without hurting core LM ability. The abstract gives no model sizes or numbers.
   - For us: answers Q1 (when/what to call) by filtering self-generated calls by whether the result lowers later-token loss. For us the cheap analogue is that our traces already say where a call goes, so we do not need that filter; it matters only if we later drop the hand-written parser. Done at 6.7B+ (from memory, not on this page), so small-scale behaviour is UNTESTED.
2. **TALM: Tool Augmented Language Models** (Parisi 2022) https://arxiv.org/abs/2205.12255. Opened: abstract page.
   - Shown: text-only interface to non-differentiable tools plus iterative self-play bootstrapping from few demonstrations; strong on a knowledge QA task and a math task with simple tools; beats non-augmented LMs at the same scale; works out-of-distribution where non-augmented LMs fail; 'less dependence on scale'.
   - For us: closest match to Ben's rule (tool call as text, result as text, non-differentiable). The self-play loop is a recipe for the 'both' answer to Q4: start with teacher-forced traces, then keep only self-generated traces whose final answer is right. Abstract gives no param counts or numbers; small-scale claim is UNTESTED.
3. **PAL: Program-aided Language Models** (Gao 2022) https://arxiv.org/abs/2211.10435. Opened: abstract page.
   - Shown: LLM writes code as the intermediate reasoning, Python interpreter does the solving; 13 benchmarks; Codex PAL beats PaLM-540B chain-of-thought on GSM8K by an absolute 15% top-1.
   - For us: Q5, open-ended tool language. The split is 'model decomposes, tool computes', same as B2's thinker/executor but with variable names carrying intermediate values instead of slot pointers. Evidence is from a code-trained giant model, so says nothing about a 3M model writing code from scratch (UNTESTED).
4. **Program of Thoughts Prompting: Disentangling Computation from Reasoning** (Chen 2022) https://arxiv.org/abs/2211.12588. Opened: abstract page.
   - Shown: model (mainly Codex) writes the reasoning as a program, external computer executes it; 5 math word-problem sets and 3 financial-QA sets, few-shot and zero-shot; about 12% average gain over chain-of-thought; with self-consistency, SoTA on all math sets.
   - For us: same lesson as PAL: moving arithmetic out of the text gives a large gain for models that otherwise compute in text. Matches our own result that text-CoT plus a calculator reaches 94-96 on 5-step chains, but note B2's internal executor gets 99.7, so the remaining gap is in the model's ability to choose operands, not arithmetic.
5. **ToolkenGPT: Augmenting Frozen Language Models with Massive Tools via Tool Embeddings** (Hao 2023) https://arxiv.org/abs/2305.11554. Opened: abstract page.
   - Shown: each tool is a token with a learned embedding, so a tool call is generated like a word; once triggered the model completes the arguments; uses plentiful demonstration data; tested on numerical reasoning, knowledge QA, embodied planning; beats baselines and picks tools from large sets. Base LM stays frozen.
   - For us: Q1 and Q5. Our 'mode head' (NUM/WORD/GEN) is already a tool-token-like decision; making the op list into 'tool tokens' emitted in the text stream is a small step. Note that it learns only the embeddings with a frozen LM; in our from-scratch setting everything trains, which is easier for the call decision and harder for the argument writing (UNTESTED).
6. **TinyAgent: Function Calling at the Edge** (Erdogan 2024) https://arxiv.org/abs/2409.00608. Opened: abstract page.
   - Shown: end-to-end framework for training and deploying task-specific small language model agents that do function calling; a Siri-like MacBook system where the small models match or exceed GPT-4-Turbo function-calling performance, running locally.
   - For us: evidence that SMALL models (the paper's models are 1.1B and 7B, from memory, not on this page) can learn function calling when the task domain is narrow and data is task-specific, which is our setup. Still 300x our size and pretrained; abstract gives no numbers.
7. **ReTool: Reinforcement Learning for Strategic Tool Use in LLMs** (Feng 2025) https://arxiv.org/abs/2504.11536. Opened: abstract page.
   - Shown: code-interpreter calls interleaved with reasoning; cold-start SFT on synthetic code-augmented traces, then RL with outcome reward on multi-turn real code execution, 'teaches when and how to invoke tools'; 32B model gets 67% on AIME at 400 RL steps versus a text-only RL baseline at 40% after 1080 steps; 72.5% in an extended setting; emergent code self-correction.
   - For us: the cleanest statement of Q4's answer: teacher-forced traces first (cold start), RL on outcome second. Our small, closed task family makes the cold-start half cheap; the RL half is UNTESTED at our size and exact-match reward on our tasks is sparse for a 3M model.
8. **ToRL: Scaling Tool-Integrated RL** (Li 2025) https://arxiv.org/abs/2503.23383. Opened: abstract page.
   - Shown: RL directly from Qwen2.5-Math base models (no SFT stated in the abstract), ToRL-7B gets 43.3% on AIME24, 14% above RL without tools and 17% above the best existing tool-integrated model; emergent behaviours: strategic tool calls, self-regulation of ineffective code, adaptive switching between computation and analysis.
   - For us: tool use can be discovered by reward alone, but only from a strong pretrained base. For a from-scratch 3M model with no prior of what code or an expression looks like, this is UNTESTED and I would not expect it to work without teacher forcing.
9. **Calc-X and Calcformers: Empowering Arithmetical Chain-of-Thought through Interaction with Symbolic Systems** (Kadlcik 2023) https://arxiv.org/abs/2305.15017. Opened: abstract page.
   - Shown: Calc-X is a collection of over 300,000 chain-of-thought samples with calculator calls; Calcformers trained on it roughly double the accuracy of standard language models on computational tasks; data and models released.
   - For us: direct evidence for Q1/Q2 from fine-tuning on calculator-annotated traces with results returned as text (the results-as-text detail is from memory of the paper's tag format, not on the abstract page). The 'roughly double' is a relative claim; the abstract gives no model size. Directly the recipe our text baseline (94-96) follows.
10. **IGC: Integrating a Gated Calculator into an LLM to Solve Arithmetic Tasks Reliably and Efficiently** (Dietz 2025) https://arxiv.org/abs/2501.00684. Opened: abstract page.
   - Shown: a module emulating a calculator on the GPU inside a fine-tuned Llama; single iteration, no external tool, no intermediate tokens; beats SoTA on BigBench Arithmetic including models almost two orders of magnitude larger; 98-99% across runs and all subtasks, including multiplication; avoids side-effects on non-arithmetic tasks.
   - For us: Q3, internal vs external. Internal gated calculator reaches 98-99%, which is the same ballpark as B2's 99.7 on chains. Shows internal executors work, but the abstract does not compare with an external tool trained under identical conditions, so 'internal is better' is UNTESTED.
11. **OccamLLM: Fast and Exact Language Model Arithmetic in a Single Step** (Dugan 2024) https://arxiv.org/abs/2406.06576. Opened: abstract page.
   - Shown: LLM hidden states control a symbolic architecture (OccamNet) that does arithmetic in one autoregressive step; Llama 3 version gets 100% on add, subtract, multiply, divide and trig/log functions; beats GPT-4o on math problem benchmarks.
   - For us: a frozen-LM-controls-symbolic-module design, very close to B2 (hidden state picks op and operands; exact executor computes). Supports keeping the executor exact; but the executor is still hand-built, which is what Ben objects to (the abstract says nothing about learning the executor).
12. **Teaching Arithmetic to Small Transformers** (Lee 2023) https://arxiv.org/abs/2307.03381. Opened: abstract page.
   - Shown: small transformers from random init learn add, multiply, sqrt via next-token prediction; data formatting changes help a lot; sharp phase transitions with data scale; chain-of-thought style data with intermediate results improves accuracy, sample complexity and speed even with no pretraining; length generalization is hard.
   - For us: the most relevant SMALL-scale, from-scratch paper. It shows the pure-text baseline (write steps, no tool) is feasible at small scale if the trace format is good (e.g. reversed digits), which is the fair comparison to a text-plus-calculator model. Warns that length generalization is a weak spot, relevant to B2's fixed 7-step limit.
13. **Neural Programmer-Interpreters** (Reed 2015) https://arxiv.org/abs/1511.06279. Opened: abstract page.
   - Shown: recurrent core with persistent program memory and domain encoders; trained on fully supervised execution traces; learns addition, sorting, canonicalizing 3D models; 'learns from a small number of rich examples' with better sample complexity and generalization than seq2seq LSTMs; can use a scratch pad with read-write pointers.
   - For us: the long-standing evidence for Q4: execution traces (teacher forcing) give small-data sample efficiency. The environment-with-pointers idea is the ancestor of our workspace slots. Note NPI's sub-programs are learned, not a fixed op list.

**Takeaways (helper, ranked):**
- 1. (Biggest change) The weight of evidence in what I opened says to train the call decision and the call text by teacher forcing on traces first (Toolformer/TALM/Calc-X/NPI/ReTool cold start), with RL only as a later polish. That is what B2 already does internally. Ben's rule can therefore be met without new learning theory: turn the traces into text the model WRITES (op name, operand references) and read the result back as text. SUGGESTED. Nothing I opened tested this at 3M params, so it is UNTESTED for us.
- 2. Keep the tool exact and the tool language small at first. IGC, OccamLLM and PAL/PoT all gain from an exact executor and a model that only decomposes. The cheapest step toward Ben's goal is to move the regex number-extraction and the op choice out of Python and into model-written text: the model copies the digits from the question into the call (a copy task it can learn with its pointer-generator), and the tool parses the call. SUGGESTED.
- 3. Open-ended expressions (PAL/PoT) versus the fixed 9-op list: the code papers all use pretrained code models, so none shows a from-scratch tiny model inventing a good expression language. A middle path: a tiny fixed grammar, e.g. 'ADD(a,b)' written as characters, where a and b are copied number strings or 'r3' style result names. That removes the 7-step and 27-slot limits (results come back as text and can be copied) and still is closed-form for a small model to learn. SUGGESTED, UNTESTED.
- 4. Results returned as text: no abstract I opened measures how reliably a small model reads a returned number. Lee 2023 shows formatting (e.g. digit order) changes small-model arithmetic accuracy a lot, so the returned format is a design variable, not a detail: try the tool returning digits in the form the reader already handles best (our place code is a hint that the units digit matters). SUGGESTED.
- 5. Internal versus external: IGC (98-99%) and our B2 (99.7) show an internal executor can match or beat the external route, but no paper I opened compares them under equal training. Our own gap (text plus calculator 94-96 versus 99.7) is more likely about operand copying/selection than about arithmetic, since the calculator is exact; this is a SUGGESTED explanation to check by counting which step of failed text-plus-calculator chains is wrong.
- 6. Use RL only if teacher forcing stalls. ReTool and ToRL used 7B-32B pretrained bases; ReTool itself needed SFT cold start. For a 3M from-scratch model with exact-match reward, expect sparse reward. A cheaper alternative from TALM: self-play filtering, keep self-generated traces with correct final answers and fine-tune on them. UNTESTED at our size.

**Gaps:** "No paper I opened answers any of these at our size (about 3M params, from scratch, about 12M word pieces): (a) whether a tiny from-scratch model can learn WHEN to call and WHAT to write in a call from traces alone, as opposed to a pretrained 1B-7B model; (b) how reliably a tiny model reads a tool result returned as text, and which return formats help; (c) a controlled comparison of the same model with an internal executor versus the same executor behind a text interface; (d) whether RL adds anything on top of teacher-forced traces below ~100M params; (e) an open-ended expression language learned from scratch at small scale versus a fixed op list; (f) the effect of the input reader (letters vs word pieces) on learning to write calls, which is the other half of Ben's question and is covered only in the existing notes gemma-reader-papers.md and thinker-absorb-papers.md (not duplicated here). Caveats on this run: I only opened abstract pages (no full text), so training details such as model sizes, filtering criteria, and ablations are not SHOWN; the arXiv API query returned nothing in my environment, so searching was by web search plus known IDs, and recent 2025-2026 small-model tool-use work may be missed (only SynthAgent 2601.22511, a small-agent paper that I opened, was found, and I left it out because its abstract has no tool-call-learning mechanism relevant here). GSM8K (2110.14168) was opened but its abstract does not mention calculator annotations, so I did not cite it as showing them."

## Input units: letters, bytes, word pieces, byte patches

1. **Toppling the Hierarchy in Byte-level Language Modeling** (Edman, 2026) https://arxiv.org/abs/2609.00463. Opened: abstract (arXiv API).
   - Shown: recent byte-level models use a hierarchy (bytes, downsample to words, upsample to bytes). The authors find the hierarchical design itself limits character-level understanding: pure byte-level models consistently beat hierarchical variants on character-manipulation tasks. Ablating layers shows byte-level attention is the main driver. Result is a stated trade-off between compute efficiency and fine-grained character understanding. No scale numbers in the abstract.
   - For us: most on-point paper for question (3). It says downsampling to chunks costs exact character manipulation (our cipher tasks), and that full-resolution attention over bytes is what does the work. Supports keeping B2's per-letter positions and adding attention at letter resolution, and adding any chunk/Gemma channel as a side input rather than a replacement. Fits our measured fact that dropping the +-4 conv broke ciphers. Not tested at small scale in the abstract (UNTESTED for us).
2. **Dynamic Chunking for End-to-End Hierarchical Sequence Modeling (H-Net)** (Hwang, 2025) https://arxiv.org/abs/2507.07955. Opened: abstract (arXiv API).
   - Shown: learned content-dependent chunking trained jointly with the model. Compute- and data-matched, a 1-stage byte-level H-Net beats a strong BPE Transformer; multi-stage matches a token Transformer of twice its size and scales better with data. Pretrained on English it shows significantly increased character-level robustness. Gains are larger where tokenization heuristics are weak (Chinese, code, DNA: nearly 4x data efficiency on DNA). The abstract gives no parameter count and no copy/cipher result.
   - For us: the 'data-efficiency gain when tokenization is weak' point is the closest to our regime (made-up words, ciphers, digits are all weak-tokenization text). But the abstract does not say whether exact copying survives chunking; read together with Edman 2026 (above), which says hierarchy hurts char manipulation. H-Net is a pretraining LM recipe, large to build; UNTESTED whether it works with 3M params and 12M word pieces.
3. **From Bytes to Ideas: Language Modeling with Autoregressive U-Nets (AU-Net)** (Videau, 2025) https://arxiv.org/abs/2506.14761. Opened: abstract (arXiv API).
   - Shown: reads raw bytes, pools into words, then pairs of words, then up to 4 words (multi-scale); deeper stages predict further ahead. With carefully controlled compute, shallow hierarchies tie strong BPE baselines and deeper ones show a promising trend. Because tokenization lives inside the model the same system can handle character-level tasks. No numbers in the abstract.
   - For us: a concrete 'learned pooling with skip connection at byte level' design (U-Net skips keep the byte-level stream for exact access). That skip is the structural answer to question (3). Same caveat: shown at LM scale, not small data.
4. **SpaceByte: Towards Deleting Tokenization from Large Language Modeling** (Slagle, 2024) https://arxiv.org/abs/2404.14408. Opened: abstract (arXiv API).
   - Shown: byte-level decoder with larger transformer blocks inserted in the middle layers and applied only after certain bytes such as spaces (word boundaries). At fixed training and inference compute it outperforms other byte-level architectures and roughly matches tokenized Transformers. The abstract lists decreased character-level modeling performance as a disadvantage of tokenization.
   - For us: a cheap, non-learned patching rule. Our reader already knows regex word boundaries (the place code), so 'run extra heavy blocks only at word-boundary positions, keep all letters' is the SpaceByte pattern and fits our compute budget at 208 chars. Note it uses a hand-written boundary rule (a space), which Ben may or may not accept; H-Net/MrT5 are the learned versions. UNTESTED at our scale.
5. **MrT5: Dynamic Token Merging for Efficient Byte-level Language Models** (Kallini, 2024) https://arxiv.org/abs/2410.20771. Opened: abstract (arXiv API).
   - Shown: ByT5 variant with a learned delete gate in the encoder after a fixed number of layers; deleted tokens' information is merged into retained ones. Cuts sequence length up to 75% with minimal effect on bits-per-byte and comparable accuracy to ByT5 on XNLI, TyDi QA and character-level tasks. The abstract does not name which character-level tasks or give scores.
   - For us: the 'delete after k layers' ordering is the useful part: process every character at full resolution for the first layers (which is what our conv/attention reader does), then shorten. At 208 chars shortening saves little compute, so the value for us is only as a way to give the thinker a shorter memory to read; UNTESTED that it helps. Built on ByT5 (already in gemma-reader-papers.md); this entry adds the merging idea, not the byte baseline.
6. **Hierarchical Transformers Are More Efficient Language Models (Hourglass)** (Nawrot, 2021) https://arxiv.org/abs/2110.13711. Opened: abstract (arXiv API).
   - Shown: studies downsampling/upsampling layers and builds Hourglass, a hierarchical Transformer; improves on the Transformer baseline at equal compute, sets a new Transformer SOTA on ImageNet32 generation and improves enwik8 (a character-level benchmark) efficiency. Abstract gives no numbers.
   - For us: foundation for CANINE/H-Net/MegaByte-style shortening, and enwik8 is character-level so exact characters survive in that design (via upsample plus residual). CANINE is already covered in thinker-absorb-papers.md; this is the general downsample/upsample study. Small-scale friendly (enwik8-sized), still not under 10M-param data tiny regime.
7. **T-FREE: Subword Tokenizer-Free Generative LLMs via Sparse Representations for Memory-Efficient Embeddings** (Deiseroth, 2024) https://arxiv.org/abs/2406.19223. Opened: abstract (arXiv API).
   - Shown: embeds whole words directly as sparse activation patterns over character triplets, no reference corpus needed; competitive downstream performance with more than 85% fewer parameters in the embedding and head layers; better cross-lingual transfer. The abstract says it exploits morphological similarity.
   - For us: a middle path between letters and subword vocab: one vector per regex word built from hashed character trigrams, so rare or made-up words share parameters with similar words and the word is still a function of its letters. Fits our 'regex words' (the Talker already copies regex-delimited words). A word-level channel next to the letters could supply 'more information per position' without a pretrained model. UNTESTED; the abstract is on pretrained LLMs and says nothing about exact spelling or ciphers.
8. **Decoupling the Benefits of Subword Tokenization for Language Model Training via Byte-level Simulation** (Gigant, 2026) https://arxiv.org/abs/2604.27263. Opened: abstract (arXiv API).
   - Shown: isolates subword tokenization's effects inside a controlled byte-level pretraining pipeline. Finds the critical factors are increased training throughput (more text seen per unit compute) and putting subword boundaries in as explicit priors or inductive biases. Tests sample throughput, vocabulary scaling and the linguistic prior of boundaries. No numbers in the abstract.
   - For us: the best direct answer to question (1): subwords win mostly by (a) letting the model see more text per FLOP and (b) giving boundary information, not by putting more meaning in each position. For us (b) is already supplied cheaply (regex word boundaries and the place code), and (a) does not apply because our sequences are 208 chars and fixed-size, so the throughput advantage is small. Supports 'the limit is not letters per se'. Not about tiny data directly; UNTESTED at 3M params.
9. **Spelling-out is not Straightforward: LLMs' Capability of Tokenization from Token to Characters** (Hiraoka, 2025) https://arxiv.org/abs/2506.10641. Opened: abstract (arXiv API).
   - Shown: LLMs spell out tokens with high accuracy but struggle with harder character tasks (e.g. compositional subcomponents of tokens). The embedding layer does not fully encode character information, especially beyond the first character; the model reconstructs character knowledge in intermediate and higher layers, where a distinct 'breakthrough' appears (probing classifiers, knowledge neurons, attention weights).
   - For us: evidence for question (1) that is on the other side of Ben's worry: in subword models, getting letters back out of tokens costs depth/compute. For a letter model the letters are already in the input embedding, so the depth goes to meaning instead. It also predicts why frozen EmbeddingGemma alone lost (letters not recoverable from its states; our probe plan in gemma-reader-papers.md fix 1 tests this).
10. **CharBench: Evaluating the Role of Tokenization in Character-Level Tasks** (Uzan, 2025) https://arxiv.org/abs/2508.02591. Opened: abstract (arXiv API).
   - Shown: benchmark of character counting/locating tasks, 2 orders of magnitude larger than prior ones; leading models average 43.6% accuracy and 32.3% on some tasks. For counting, tokenization properties correlate only weakly with correctness; the word's length and the true count matter more. For intra-word position tasks, accuracy falls with the length of the token containing the queried character.
   - For us: a caution to our own framing. Counting failures are not simply caused by tokenization; they track task difficulty (long words, large counts), i.e. compute/depth. Position-in-word failure does track token length, which matches the idea that coarse units hide position. Our place code (index from the right of the word) is B2's hand-built answer to the position problem. All frontier-scale models; not small data.
11. **CUTE: Measuring LLMs' Understanding of Their Tokens** (Edman, 2024) https://arxiv.org/abs/2409.15452. Opened: abstract (arXiv API).
   - Shown: benchmark of orthographic tasks (spelling, text manipulation). Most popular LLMs seem to know the spelling of their tokens but fail to use it to manipulate text, calling into question how generalizable that knowledge is.
   - For us: knowing the letters of a token is different from being able to operate on them; cipher-type tasks are exactly 'operate on letters'. Supports keeping a letter-resolution stream for cipher and copy tasks. Same author as Toppling the Hierarchy (2026), which then shows byte hierarchy also hurts.
12. **Tokenization counts: the impact of tokenization on arithmetic in frontier LLMs** (Singh, 2024) https://arxiv.org/abs/2402.14903. Opened: abstract (arXiv API).
   - Shown: for GPT-3.5/GPT-4 (1-, 2-, 3-digit tokens), right-to-left tokenization (forced by comma-separating numbers) largely improves arithmetic over left-to-right; errors under left-to-right follow stereotyped patterns; the models can convert between tokenizations, so chain-of-thought can recover performance; the gap shrinks with scale.
   - For us: right-to-left alignment of digits (units digit first) is exactly B2's place code, so that hand-built feature has literature support, and a learned reader could be asked to learn it (UNTESTED; it needs a way to know where a number ends, which a bidirectional conv can learn from the +-4 window). Also relevant to Ben: this bias matters most for small models because it shrinks with scale.
13. **Bolmo: Byteifying the Next Generation of Language Models** (Minixhofer, 2025) https://arxiv.org/abs/2512.15586. Opened: abstract (arXiv API).
   - Shown: family of open byte-level LLMs made by converting subword models with a two-stage procedure and minimal extra training; outperform prior byte-level approaches, 'excel on character-level reasoning tasks' while staying competitive on standard benchmarks; subword tokenization obscures fine-grained information needed for code and biological sequences. No model sizes or scores in the abstract.
   - For us: closest large-scale analogue to our 'EGE' idea (keep a pretrained subword-meaning model, add a byte path); but it converts the whole model, so it is not a small-data result. Supports 'bytes plus pretrained meaning' as the direction; companion 2602.01007 (Distilling Token-Trained Models into Byte-Level Models, Bao 2026, abstract also opened) reports distilled byte models keep most teacher performance with about 125B bytes, again far beyond our scale.
14. **Byte Latent Transformer: Patches Scale Better Than Tokens (BLT, re-opened for the numbers; already covered in gemma-reader-papers.md)** (Pagnoni, 2024) https://arxiv.org/abs/2412.09871. Opened: abstract (arXiv API).
   - Shown: entropy-based dynamic patches; first FLOP-controlled scaling study of byte models up to 8B parameters and 4T bytes; matches tokenization-based LLMs with better efficiency and robustness, and qualitative gains on reasoning and long-tail generalization. A follow-up, Fast Byte Latent Transformer (Kallini 2026, https://arxiv.org/abs/2605.08044, abstract opened), only addresses generation speed.
   - For us: BLT's patches are variable length chosen by next-byte entropy, so they are in effect a learned 'how much compute here' signal; for ciphers (high entropy, every letter matters) patches would be short, i.e. near char level. That is an inference, UNTESTED.

**Takeaways (helper, ranked):**
- 1. (Biggest change) Do not replace the letter stream with coarser units; add coarser channels next to it. SHOWN (Edman 2026, abstract): byte models with a down/up-sampling hierarchy lose to pure byte models on character manipulation, driven by byte-level attention. SUGGESTED: this matches our own results (conv removal broke ciphers 100 to 2.5-12.5; frozen Gemma replacing letters lost; Gemma added on letters gained +1.6/+2.1). Design rule: keep every letter position and its own attention; any chunk/word/Gemma vector gets added to it (a U-Net-style skip, as in AU-Net/Hourglass), never substituted.
- 2. 'Letters carry too little information per position' is probably not the limit; compute/depth and boundary information are. SHOWN (Gigant 2026): subword models win mainly through training throughput (more text per FLOP) and explicit boundary priors. SHOWN (Hiraoka 2025; CharBench 2025): subword models spend depth to recover letters, and counting failures track word length and true count more than tokenization. SUGGESTED: our 208-char sequences remove the throughput advantage, B2 already supplies boundaries (regex words, place code), so the cheap test of Ben's worry is giving the reader more depth/attention over letters, not new units. UNTESTED: nobody here measured this at under 10M parameters.
- 3. The hand-made place code (index from right end of word) has literature support but is a hard-coded feature Ben dislikes. SHOWN (Singh 2024): right-to-left digit grouping substantially improves arithmetic in GPT-3.5/4 and the gap shrinks with scale, so small models need it most. SUGGESTED: a learned reader can in principle find digit-run ends from the +-4 window plus one attention layer; the clean test is to remove the place code and see if a bidirectional reader recovers it. Pass/fail marks must be fixed before running; wrong if chain-5 drops more than 2 points.
- 4. If a coarser channel is wanted, cheapest first: (a) word-level vector from hashed character trigrams (T-FREE style, no pretrained model, rare words share parameters with similar ones); (b) heavier blocks only at word-boundary positions with all letters kept (SpaceByte style); (c) learned chunking (H-Net/MrT5/AU-Net), which is the most 'everything learned' but the least proven at small size. SUGGESTED ranking by risk is a, b, c. Each as an added channel on top of EGE, one change at a time.
- 5. Compute at 208 positions: SUGGESTED, from my reasoning, not from papers: attention over 208 positions is about 43k pairs per head per layer, tiny next to the 8 thinker rounds, so shortening sequences (MrT5, MegaByte, CANINE) buys almost nothing for us. Their value is only as a better representation, which no abstract demonstrates at our size. Do not adopt a chunking method for speed.
- 6. Evidence that BPE helps or hurts when data is tiny is thin. The BabyLM findings abstract (Warstadt 2025, https://arxiv.org/abs/2504.08165, opened) says winning small-data submissions used LTG-BERT architecture, shorter sequences and teacher distillation; it does not say anything about character vs subword. The French BabyLM paper (Wasserman 2026, https://arxiv.org/abs/2609.17435, opened) reports tokenizer artifacts dominating scoring at child scale. So for the tiny-data question the honest status is: SHOWN only indirectly; UNTESTED for us beyond our own EmbeddingGemma runs.

**Gaps:** "No paper I opened answers: (a) byte/char vs BPE at about 3M parameters and about 12M word pieces on algorithmic reasoning text (every cited result is 100M to 8B parameters, or an abstract without sizes); (b) whether learned chunking (H-Net, MrT5, AU-Net) preserves exact copying and substitution ciphers when trained on tiny data; Edman 2026 says hierarchy hurts character manipulation but at LM scale and from the abstract only; (c) whether a small reader can learn right-to-left digit alignment (the place code) from data alone; (d) how much a single added pretrained subword channel (our EGE) helps on character tasks specifically, beyond our own 2-seed +1.6/+2.1 (the 6-seed confirm is pending); (e) the abstracts give no per-task character-level numbers for MrT5, SpaceByte, H-Net, AU-Net or Bolmo, so 'what each found for character tasks' is only qualitative here; full-paper tables were not read. Also not searched: papers on tool-calling language models with text-in/text-out calculators at small scale, which is Ben's separate point about the no-hard-coding rule. Previously covered and not repeated: CANINE, Charformer, MegaByte, MambaByte, ByT5, CharBERT (see thinker-absorb-papers.md and gemma-reader-papers.md)."

## Letters plus pretrained meaning

1. **Bolmo: Byteifying the Next Generation of Language Models** (Minixhofer 2025 (rev. Feb 2026)) https://arxiv.org/abs/2512.15586. Opened: abstract page.
   - Shown: open byte-level LLMs built by a two-stage conversion of existing subword models with 'minimal additional training'; they beat prior byte-level models, 'excel on character-level reasoning tasks', stay competitive on standard benchmarks, and can be adapted cheaply through the source model's ecosystem. The abstract gives no parameter counts or numbers (I did not open the full text).
   - For us: strongest 2025-26 evidence that a pretrained subword model plus a byte path can keep meaning AND letters. But it is a large-model recipe (convert a whole LM), not a side channel. For us the lesson is the direction of travel (keep pretrained weights, add a byte path), not the recipe. UNTESTED at under 100M.
2. **Universal Cross-Tokenizer Distillation via Approximate Likelihood Matching** (Minixhofer 2025) https://arxiv.org/abs/2503.20083. Opened: abstract page.
   - Shown: a distillation method that works across fundamentally different tokenizers, including 'rapid transfer of subword models to the byte-level'; also distils a large maths LLM into a small model with a different tokenizer, with 'competitive' maths performance. No numbers in the abstract.
   - For us: gives a route to put EmbeddingGemma-like knowledge into a model that reads letters, by distillation rather than by running the 270M at inference. That would shrink the counted size (our whole-model size counts borrowed parts). UNTESTED: nobody shows it at 3M params; teacher outputs are LM likelihoods, EmbeddingGemma is an encoder, so the objective would have to be adapted (a feature-matching loss on a char reader's states is my guess).
3. **Cross-Tokenizer LLM Distillation through a Byte-Level Interface** (Singh 2026) https://arxiv.org/abs/2604.07466. Opened: abstract page.
   - Shown: Byte-Level Distillation converts the teacher's distribution to byte-level probabilities, attaches a lightweight byte-level decoder head to the student, and distills through that. Competitive with or better than more complex cross-tokenizer methods on models from 1B to 8B. The authors say consistent gains across all tasks 'remain elusive'.
   - For us: bytes are the natural common ground between a subword teacher and a letter student, which matches our situation. Scale (1B-8B) is far above ours, and it is about output distributions, not encoder features. Mostly a design hint.
4. **Zero-Shot Tokenizer Transfer** (Minixhofer 2024 (rev. Oct 2025)) https://arxiv.org/abs/2405.07883. Opened: abstract page.
   - Shown: a hypernetwork that predicts embeddings for a new tokenizer's vocabulary; comes close to original performance on cross-lingual and coding tasks (XLM-R, Mistral-7B), shortens token sequences, and the remaining gap closes with continued training on under 1B tokens.
   - For us: shows pretrained models are not bound to their tokenizer and that a small net can map new-tokenizer units to old embedding space. A tiny char-to-embedding hypernetwork predicting Gemma's piece embeddings from letters is a conceivable way to feed Gemma-space features from letters. UNTESTED, and large-model scale only.
5. **CharBERT: Character-aware Pre-trained Language Model** (Ma 2020) https://arxiv.org/abs/2011.01513. Opened: abstract page.
   - Shown: builds a contextual word embedding for each token from sequential character representations, then fuses character and subword representations with a 'heterogeneous interaction module'; adds a Noisy LM pre-training task; improves QA, sequence labelling and classification on original and adversarial-misspelling sets ('significantly' per abstract; no numbers given).
   - For us: nearest published design to our EGE (character channel + pretrained subword channel, fused). Their fusion is a learned two-way interaction, not plain addition, so it is a second option if our additive EGE saturates. Also trained at BERT scale, not small. Prior notes cited it from memory; now opened.
6. **Hierarchical Autoregressive Transformers: Combining Byte- and Word-Level Processing** (Neitemeier 2025) https://arxiv.org/abs/2501.10322. Opened: abstract page.
   - Shown: a lightweight character-level encoder turns characters into word embeddings, a word-level backbone processes them, a compact char decoder writes characters back; matches subword-tokenizer models on downstream tasks at scales up to 7B, with much greater robustness to input perturbations; on continued pretraining in an out-of-domain language it trains almost twice as fast and forgets less.
   - For us: a letter-to-word encoder feeding a word-level model is the pattern B2's reader+thinker already resembles. The result that a char encoder can replace a vocabulary without losing downstream score supports keeping letters as the primary stream and adding word-level meaning on top. Not small scale.
7. **Dynamic Chunking for End-to-End Hierarchical Sequence Modeling (H-Net)** (Hwang 2025) https://arxiv.org/abs/2507.07955. Opened: abstract page.
   - Shown: a learned chunking mechanism inside a hierarchical network; a one-stage byte-level H-Net beats a compute- and data-matched BPE Transformer, two stages match a token Transformer twice its size; shows increased character-level robustness; nearly 4x data-efficiency gain on DNA.
   - For us: evidence that letters + learned grouping can beat fixed subword tokens at matched data, with the best gains where tokenization is weak (code, DNA). Relevant to our made-up-word and cipher text. Replaces the fixed +-4 window idea with learned chunks (overlaps the Charformer note in thinker-absorb-papers.md). Scale not stated in the abstract.
8. **SpaceByte: Towards Deleting Tokenization from Large Language Modeling** (Slagle 2024) https://arxiv.org/abs/2404.14408. Opened: abstract page.
   - Shown: byte-level decoder with bigger transformer blocks inserted after boundary bytes such as spaces; competitive with tokenized models at equal compute.
   - For us: cheap word-boundary-triggered 'word-level' compute inside a letter model. Our regex words and place codes are a hand-coded version of the same boundary idea; a learned boundary would address Ben's hard-coding concern. Large-model setting.
9. **Local Byte Fusion for Neural Machine Translation** (Sreedhar 2022) https://arxiv.org/abs/2205.11490. Opened: abstract page.
   - Shown: LOBEF aggregates local information using byte n-grams and word boundaries; consistent improvement over byte-based models and over subword models on multilingual translation, zero-shot transfer and domain adaptation; byte models 'parameter-efficient' and faster to train.
   - For us: a local byte n-gram fusion is basically our +-4 conv, and it gives published support that the local window is the right idea for byte models (our own ablation: removing it cost 6.3-6.8 points). MT, not reasoning. Modest scale.
10. **Text Embeddings Reveal (Almost) As Much As Text** (Morris 2023) https://arxiv.org/abs/2310.06816. Opened: abstract page.
   - Shown: a multi-step iterative correct-and-re-embed method recovers 92% of 32-token text inputs exactly from a dense embedding (state-of-the-art embedding models), including full names in clinical notes.
   - For us: information about exact tokens survives inside pooled sentence embeddings, but needs a heavy iterative decoder to get it out. That does not show a small linear/MLP reader can read digits from them. This cuts both ways for the probe: the info may be present yet not cheaply usable. Applies to pooled vectors; our use is per-token states (untested).
11. **Revealing the Numeracy Gap: An Empirical Investigation of Text Embedding Models** (Deng 2025) https://arxiv.org/abs/2509.05691. Opened: abstract page.
   - Shown: 13 widely used embedding models, tested on synthetic financial data, 'generally struggle to capture numerical details accurately' (the 2% vs 20% example).
   - For us: direct evidence against relying on frozen sentence encoders for digits; consistent with our EmbeddingGemma-replacing-letters losses. Pooled-embedding test, not per-token states, and EmbeddingGemma specifically may not be among the 13 (abstract does not list them). Already cited in gemma-reader-papers.md; re-opened here.
12. **What do tokens know about their characters and how do they know it?** (Kaushal 2022) https://arxiv.org/abs/2206.02608. Opened: abstract page.
   - Shown: classifiers on embeddings from GPT-J, BERT, RoBERTa and GloVe predict whether a given letter appears in a token; models reliably encode character information, larger models better; holds across non-Latin scripts.
   - For us: gives the probe design for question (2): 'does this token contain letter X' on frozen token states. Note these are input-embedding style probes on single tokens, not contextual EmbeddingGemma outputs.
13. **Models In a Spelling Bee: Language Models Implicitly Learn the Character Composition of Tokens** (Itzhak 2021) https://arxiv.org/abs/2108.11193. Opened: abstract page.
   - Shown: RoBERTa's embedding layer holds enough information to spell up to a third of the vocabulary; but adding explicit character information to a subword LM gave a near-identical learning curve as no enrichment.
   - For us: a caution. In plain language modeling, explicit characters added little, so the benefit of the letter stream is task-specific (exact copy, ciphers), which is what our results show, not a general rule. Small-ish scale but language modeling, not reasoning.
14. **The Strawberry Problem: Emergence of Character-level Understanding in Tokenized Language Models** (Cosma 2025) https://arxiv.org/abs/2505.14172. Opened: abstract page.
   - Shown: tokenization causes 'low mutual information' between tokens and characters; across 19 synthetic tasks, character-level ability emerges 'suddenly and only late in training'; they propose 'a lightweight architectural modification' that significantly improves character-level reasoning while keeping subword inductive advantages (abstract does not describe the modification).
   - For us: the closest abstract-level match to 'subword model plus a cheap char path', and it uses synthetic tasks like ours. I did not open the full text, so I cannot say what the modification is or at what size; worth reading next.
15. **EmbeddingGemma: Powerful and Lightweight Text Representations** (Vera 2025) https://arxiv.org/abs/2509.20354. Opened: abstract page.
   - Shown: 300M model from Gemma 3 via encoder-decoder initialization and geometric embedding distillation, spread-out regularizer, checkpoint merging; state of the art on MTEB (multilingual, English, code) under 500M params; lead persists with quantization or truncated outputs.
   - For us: trained for pooled-vector retrieval; the abstract says nothing about token-level states or digit/letter recoverability. So whether its token states keep letters is unanswered by the paper and must be probed by us. The quantization/truncation robustness suggests the useful signal is low-precision, so int8 or truncated features may be cheap to ship (UNTESTED).

**Takeaways (helper, ranked):**
- 1. (biggest design impact) Keep letters as the primary stream and add pretrained meaning as an extra channel, which is what EGE does. SUGGESTED by CharBERT (char+subword fused), Hierarchical AR Transformers (char encoder is enough to match subword models), Bolmo (keep pretrained weights, add bytes, excels on character tasks), H-Net/SpaceByte/LOBEF (letters plus local or learned grouping). All large-scale or MT; none at 3M params. Our own EGE +1.6/+2.1 on 2 seeds is the only small-scale evidence and the 6-seed confirm is the test. If it holds, try a CharBERT-style two-way fusion (letters attend to Gemma and back) as the one next change, instead of plain addition. UNTESTED.
- 2. No paper shows frozen sentence encoders keep digits/letters recoverable at token level. Evidence in hand: pooled embeddings struggle with numbers (Numeracy Gap, 13 models), yet exact text can be inverted from them with a heavy iterative decoder (Morris, 92% of 32-token inputs). Token-level character info is probe-able (Kaushal 2022, Itzhak 2021) but only on LM token embeddings. So run our own cheap CPU probe on EmbeddingGemma per-token states (digit identity, letter-in-token, place value), middle vs last layer, with a mark fixed in advance. Also consider that EGE gains probably come from meaning, not digits, because numbers already come from the regex/executor; the probe would tell us. (Matches fix 1 in gemma-reader-papers.md; this adds probe recipes.)
- 3. Cost: all byte-ifying and cross-tokenizer work (Bolmo, ALM, BLD, ZeTT) is 1B-8B-scale conversion of whole models. Our size accounting counts borrowed parts, so a 270M frozen encoder is a very large addition to a 3.3M model. The only route in the literature that shrinks that cost is distillation (ALM, BLD): train a small letter reader to reproduce the encoder's features so the encoder is not needed at inference. UNTESTED at our size and with an encoder (not LM) teacher. A reasonable follow-up only if EGE's gain survives 6 seeds.
- 4. Do not expect letters to help everywhere: Itzhak found explicit char info gave a near-identical learning curve in LM training. Our evidence of letter value is task-specific (ciphers 100 vs 2.5-12.5 without the window). Keep evaluating on cipher, copy and made-up-word splits, not only pooled score.
- 5. On Ben's hard-coding concern: the literature (H-Net, SpaceByte, LOBEF, Hierarchical AR) points to learned or boundary-triggered grouping replacing hand rules; H-Net's learned chunking removes heuristics entirely. That is a route for replacing the regex word and place-code features with learned ones, but nothing here says it works at 3M params or for exact digit values; the place code and regex numbers are the part with least published support for removal. SUGGESTED / UNTESTED.
- 6. Read next (not opened beyond abstract): The Strawberry Problem (what is its 'lightweight modification'?) and Bolmo's full text (does its small conversion variant exist, and what does the byte local encoder/decoder look like?).

## Learned boundaries, span copying and learned halting

1. **Dynamic Chunking for End-to-End Hierarchical Sequence Modeling (H-Net)** (Hwang, 2025) https://arxiv.org/abs/2507.07955. Opened: abstract.
   - Shown: learns content- and context-dependent segmentation jointly with the model, no tokenizer. Compute/data-matched, a 1-stage byte-level H-Net beats a BPE Transformer LM; multi-stage matches a token Transformer of twice its size; more character-level robust; learns 'meaningful chunking without heuristics or explicit supervision'; nearly 4x data-efficiency gain on DNA (weak tokenization heuristics). Abstract gives no parameter counts, no number-token results, and no behavior on made-up words.
   - For us: closest thing to replacing word_spans/place codes. A boundary predictor (cosine similarity of adjacent states) would give 'word start' flags and learned place-from-right. Regime is LM pretraining at scale, so small-data synthetic transfer is UNTESTED. The 4x data-efficiency on DNA hints that learned chunks help when handcrafted boundaries are poor, but exact-digit boundaries are a sharper demand than LM perplexity.
2. **Byte Latent Transformer: Patches Scale Better Than Tokens (BLT)** (Pagnoni, 2024) https://arxiv.org/abs/2412.09871. Opened: abstract.
   - Shown: bytes grouped into dynamically sized patches segmented by next-byte entropy; FLOP-controlled scaling to 8B params and 4T bytes; matches tokenized LLMs, with 'qualitative improvements on reasoning and long tail generalization'. (Not covered in the two existing notes' paper lists, which only name it as skipped in thinker-absorb-papers.md.)
   - For us: entropy boundaries need a trained next-byte model and tend to fall at unpredictable points (word starts), not at digit-string ends, so they are a weak fit for exact number spans. Use as the contrast case: boundaries from predictability versus boundaries trained by the downstream loss (H-Net, our case). UNTESTED at our scale.
3. **From Bytes to Ideas: Language Modeling with Autoregressive U-Nets (AU-Net)** (Videau, 2025) https://arxiv.org/abs/2506.14761. Opened: abstract.
   - Shown: reads raw bytes, pools into words, then word pairs, then up to 4 words; shallow hierarchies tie strong BPE baselines under controlled compute; 'can handle character-level tasks'. Abstract does not say how the word split is chosen (it may be a fixed rule); I did not open the body.
   - For us: a multi-scale reader (char -> word -> phrase) is a pattern for replacing our conv-5 window. Caveat: if its word pooling uses a space-split rule, it is still hand-written boundaries. Check the body before borrowing.
4. **SpaceByte: Towards Deleting Tokenization from Large Language Modeling** (Slagle, 2024) https://arxiv.org/abs/2404.14408. Opened: abstract.
   - Shown: byte-level decoder with larger blocks inserted and applied only after certain bytes such as spaces, 'which typically denote word boundaries'; beats other byte-level architectures and roughly matches tokenized Transformers at fixed compute.
   - For us: this is the HAND-WRITTEN-boundary baseline, i.e. what our regex word_spans already is. It shows boundary heuristics work, which is a reason a learned version must be compared to it on the same splits (made-up words, numbers glued to punctuation). It does not support dropping boundaries.
5. **MrT5: Dynamic Token Merging for Efficient Byte-level Language Models** (Kallini, 2024) https://arxiv.org/abs/2410.20771. Opened: abstract.
   - Shown: a learned delete gate after a fixed number of encoder layers drops byte positions and merges their information into the kept ones; sequence length cut by up to 75%; comparable accuracy to ByT5 on XNLI, TyDi QA and character-level tasks; learns language-specific compression rates.
   - For us: a cheap learned 'keep/drop' gate over characters, trained only by the task loss. A cheaper boundary learner than H-Net for a 3M model (one linear gate), though it deletes rather than marks starts and ends. Digits of an exact number must not be deleted, so we would need a pass mark on digit-level accuracy. UNTESTED.
6. **Learning to Discover, Ground and Use Words with Segmental Neural Language Models** (Kawakami, 2018) https://arxiv.org/abs/1811.09353. Opened: abstract.
   - Shown: segmental neural LM discovers word-like units latent in unsegmented character sequences; predicts better than character LSTMs and discovers words competitively with nonparametric Bayesian segmenters (abstract gives no F1 numbers).
   - For us: the older, small-model evidence that word boundaries can be learned from characters by a likelihood objective alone, with a marginalization over segmentations. Relevant to question (2): such models score segments with a character-level model, so unseen words are handled by spelling, not a vocabulary. No numbers or span copying in the abstract.
7. **Pointer Networks** (Vinyals, 2015) https://arxiv.org/abs/1506.03134. Opened: abstract.
   - Shown: attention used as a pointer to select a member of the input as output; generalizes to variable output dictionaries; 'generalize beyond the maximum lengths they were trained on' on convex hull, Delaunay, TSP tasks trained from examples alone.
   - For us: the basis for answering Q1: a start pointer and an end pointer are two softmaxes over the 208 characters. Length generalization of pointing supports using position-free (content-based) pointers. Evidence is not on character spans of text.
8. **Incorporating Copying Mechanism in Sequence-to-Sequence Learning (CopyNet)** (Gu, 2016) https://arxiv.org/abs/1603.06393. Opened: abstract.
   - Shown: CopyNet picks 'sub-sequences in the input' to replicate, integrated with normal generation; works on synthetic and real data; summarization gains. Abstract gives no span-copy accuracy.
   - For us: CopyNet copies SUB-SEQUENCES, i.e. the model decides the span, which is exactly the learned-boundary copy we want instead of regex WORD. Our talker's GEN already is a pointer-generator over characters, so a WORD mode could be GEN with a copy gate held on for several steps.
9. **Get To The Point: Summarization with Pointer-Generator Networks** (See, 2017) https://arxiv.org/abs/1704.04368. Opened: abstract.
   - Shown: hybrid that copies words by pointing 'which aids accurate reproduction of information' while keeping a generator for novel words; coverage reduces repetition; +2 ROUGE over prior abstractive SOTA.
   - For us: supports that copy-by-pointing is what keeps factual details exact; the coverage vector is a ready trick for 'do not copy the same span twice' in multi-word copies. Word level here, not characters.
10. **Bidirectional Attention Flow for Machine Comprehension (BiDAF)** (Seo, 2016) https://arxiv.org/abs/1611.01603. Opened: abstract.
   - Shown: multi-stage hierarchical process with a character-aware, query-aware context representation; state of the art on SQuAD and CNN/DailyMail cloze (at that time). The abstract does not mention start/end pointers or character embeddings explicitly; that detail is from memory, not shown.
   - For us: standard reference for extractive QA with start/end positions as two softmaxes (from memory, not opened in the body). Used as the template for Q1, but we have no number for how reliably a 3M model copies exact spans; the abstract only reports SQuAD-level results.
11. **Adaptive Computation Time for Recurrent Neural Networks (ACT)** (Graves, 2016) https://arxiv.org/abs/1603.08983. Opened: abstract.
   - Shown: learns how many steps to take; minimal architecture change, deterministic, differentiable; large gains on parity, logic ops, addition, sorting. On Hutter-prize char LM, little gain, but 'more computation allocated to harder-to-predict transitions, such as spaces between words and ends of sentences', suggesting ACT 'could provide a generic method for inferring segment boundaries'.
   - For us: the one source linking Q-(a) and Q-(c): learned compute allocation tracks word boundaries. Could let a per-character halting signal double as a learned boundary signal. UNTESTED; ACT's gain on LM was small.
12. **PonderNet: Learning to Ponder** (Banino, 2021) https://arxiv.org/abs/2107.05407. Opened: abstract.
   - Shown: learns the number of steps end-to-end; on a complex synthetic problem 'dramatically improves' over earlier adaptive computation and 'succeeds at extrapolation tests where traditional neural networks fail'; matched SOTA on a QA dataset with less compute. The geometric-prior/KL detail is from the search snippet, not the abstract.
   - For us: swap B2's fixed 7 op-rounds for a halt probability per round with a prior; the output of the last-halted step is read. Our exact int64 executor makes every round's output a valid answer candidate, which fits PonderNet's per-step-loss setup well. UNTESTED at 3M params.
13. **Universal Transformers** (Dehghani, 2018) https://arxiv.org/abs/1807.03819. Opened: abstract.
   - Shown: weight-shared recurrent transformer with 'a dynamic per-position halting mechanism' that 'improves accuracy on several tasks'; fixes copying strings and simple logical inference at unseen lengths where the plain Transformer fails.
   - For us: our thinker is already a UT with a fixed count; UT's per-position halting is what we would replace the fixed 8 with. Abstract says halting helps 'several tasks' with no number.
14. **End-to-end Algorithm Synthesis with Recurrent Networks: Logical Extrapolation Without Overthinking** (Bansal, 2022) https://arxiv.org/abs/2202.05826. Opened: abstract.
   - Shown: when many iterations are applied, behavior degenerates ('overthinking'); fixes: a recall architecture that keeps an explicit copy of the problem instance, plus a progressive training routine that prevents iteration-number-specific behavior and pushes the model toward behaviors that can be repeated indefinitely.
   - For us: the most direct answer to Q3 (making extra rounds harmless). B2 already cross-attends to every reader output each round (a form of recall, per the task description), so the remaining trick is progressive/mixed-depth training and making the NOOP-after-done state a fixed point. UNTESTED.
15. **Looped Transformers for Length Generalization** (Fan, 2024) https://arxiv.org/abs/2409.15647. Opened: abstract.
   - Shown: looped Transformers with an adaptive number of steps 'significantly improve length generalization' on arithmetic/algorithmic tasks with a known iterative solution; trained with their proposed learning algorithm (details not in the abstract).
   - For us: tasks with a known per-step operation (RASP-L) match our ADD/SUB/... chains; supports varying loop count at train time and training with the number of steps given or inferred from the program length. I did not open the method details.
16. **Mixture-of-Recursions: Learning Dynamic Recursive Depths for Adaptive Token-Level Computation** (Bae, 2025) https://arxiv.org/abs/2507.10524. Opened: abstract.
   - Shown: lightweight routers assign recursion depth per token inside a shared-weight recursive Transformer; 135M to 1.7B params; lower validation perplexity and better few-shot accuracy at equal training FLOPs, higher throughput.
   - For us: learned per-token depth at 135M, the smallest scale in this list. Per-token (reader position) routing is a possible way to stop easy characters early; our regime (3M, tasks not LM) is untested.
17. **Scaling Latent Reasoning via Looped Language Models (Ouro)** (Zhu, 2025) https://arxiv.org/abs/2510.25741. Opened: abstract.
   - Shown: pretrained 1.4B and 2.6B looped LMs with 'an entropy-regularized objective for learned depth allocation', 7.7T tokens, matching up to 12B models; gain attributed to knowledge manipulation, not capacity.
   - For us: the entropy-regularized objective keeps the halting distribution from collapsing to one depth; relevant to avoiding a gate that always exits at round 1. Scale is far from ours.
18. **Scaling up Test-Time Compute with Latent Reasoning: A Recurrent Depth Approach** (Geiping, 2025) https://arxiv.org/abs/2502.05171. Opened: abstract.
   - Shown: recurrent block unrolled to arbitrary depth at test time; 3.5B params, 800B tokens; performance improves with more iterations up to a compute load equivalent to 50B params. The abstract does not describe the training schedule (random depth sampling is from memory, not shown).
   - For us: evidence that more rounds than seen at train time can be helpful at scale. For harmless extra rounds, the training-trick details are in the body, which I did not open.
19. **Adaptive Depth in Looped Transformers: Diagnosing Learned Halting Gates and Trajectory Readouts** (Popescu, 2026) https://arxiv.org/abs/2607.20519. Opened: abstract.
   - Shown: on modular arithmetic and binary parity (and Ouro 1.4B/2.6B), joint gate training distorts the trajectory; fixed-prior depth supervision gives difficulty-aware trajectories; simple post-hoc confidence readouts often match or beat learned linear/MLP gates; failure 'stems mainly from the trajectory induced by joint gate training rather than limited gate expressivity'.
   - For us: the most recent and most relevant small-task evidence for Q3. It argues against a jointly trained halt gate: supervise every round with a fixed prior and stop on a readout (e.g. executor result stable or confidence). Our executor's result confidence is a natural readout. Synthetic tasks, so scale is closer to ours.
20. **Adaptive Loops and Memory in Transformers: Think Harder or Know More?** (Frey, 2026) https://arxiv.org/abs/2603.08391. Opened: abstract.
   - Shown: per-layer adaptive looping with a learned halting mechanism plus gated memory banks; looping mainly helps math, memory banks recover commonsense; combined beats an iso-FLOP baseline with 3x layers on math; early layers loop minimally, later layers more.
   - For us: confirms learned halting can work in 2026 but at LM scale; abstract gives no scale in params.

**Takeaways (helper, ranked):**
- 1. (Most design-changing, Q3) For the fixed loop: do not add a jointly trained halt gate first. Popescu 2026 (abstract) found that joint gate training distorts the trajectory, and that fixed-prior per-depth supervision plus a post-hoc confidence readout matches or beats learned gates on modular arithmetic/parity. SUGGESTED for B2: supervise the answer at every round (the exact executor makes every round decodable), add a learned or fixed 'done' / NOOP target after the program ends so extra rounds are fixed points, and read out by stability of the result. Pass mark idea (untested): accuracy with 8, 10 and 12 rounds within 0.5 points of 8, plus program lengths longer than any seen in training.
- 2. (Q3) Harmless extra rounds come from two tricks in Bansal 2022 (abstract): keep the problem instance visible every round (B2 already cross-attends to all reader outputs and the workspace, SHOWN in your task description) and train with varied iteration counts so the model cannot learn round-index-specific behavior. B2's per-round op head is conditioned on which round it is? I did not check this in the code; check before acting. SUGGESTED: train with randomly truncated or padded programs.
- 3. (Q1, Q2) Replacing regex words with learned start/end pointers is the established pattern (Pointer Networks, CopyNet copying sub-sequences, pointer-generator), but NONE of the abstracts gives a span-copy accuracy for a small model on exact strings, so reliability on numbers and made-up words is UNTESTED. SUGGESTED test, one change: keep the regex as the training target only (teacher signal from the hand parser, no longer an input or an inference-time rule), add two pointers over the 208 characters (start, end), and measure exact-match on held-out made-up words and numbers, against the regex WORD mode. Pass marks to be fixed first; the result that proves it wrong is exact-match below the regex mode on the vocab split.
- 4. (a) Learned boundaries as INPUT: the place code is the one clearly hand-written feature on the input side (SHOWN in reader.py: index from the right end of each regex word). H-Net (abstract) and ACT (abstract: extra compute lands on spaces and sentence ends) say boundaries can emerge from training, but only at LM scale. SUGGESTED smaller step: a per-character boundary logit predicted by the conv reader, trained only by the final loss, with the place code computed from the soft boundary (cumulative sum from the right). Keep regex place as the baseline on the same splits, since SpaceByte (abstract) shows space-based heuristics are strong. Digits must not be merged or dropped (MrT5 deletes positions).
- 5. Feed the letters' information issue (Ben's concern): H-Net, AU-Net and MegaByte-style hierarchies (see thinker-absorb-papers.md for CANINE, Charformer, MegaByte) all keep the raw bytes AND add learned coarser units, which matches the EGE result (letters kept, EmbeddingGemma added, +1.6 / +2.1). SUGGESTED: if you want learned chunks, add them as extra channels beside the letters, not instead of them.
- 6. Do not bring in entropy patching (BLT) for number spans: it places boundaries by next-byte unpredictability, which is not tied to where a number ends. SUGGESTED, low priority.

**Gaps:** No paper I opened reports exact-match accuracy of learned start/end character pointers on made-up words or numbers at under 100M params; the abstracts for pointer/copy papers are word-level or large-scale, so Q1 and Q2 are unanswered for our size. H-Net, BLT, AU-Net, SpaceByte, MrT5 are LM-pretraining results (bits-per-byte, perplexity); none tests learned boundaries on numeric tokens or on tasks where one wrong character is a wrong answer. ## Learned legality and learned memory gates

1. **A Closer Look at Invalid Action Masking in Policy Gradient Algorithms** (Huang 2020) https://arxiv.org/abs/2006.14171. Opened: abstract.
   - Shown: gives theoretical justification for masking invalid actions, and shows empirically that masking matters more as the space of invalid actions grows. It also tests different masking regimes, such as removing the mask after training with it. The abstract gives no numbers.
   - For us: our 'only unused numbers' mask is the standard device, and this paper supports it when many choices are illegal. Our pick space is small (27 slots), so the harm of dropping the mask is probably small too. UNTESTED: that the 'train with mask, then remove it' regime is cheap to try in our setting.
2. **Overcoming Valid Action Suppression in Unmasked Policy Gradient Algorithms** (Zabounidis 2026) https://arxiv.org/abs/2603.09090. Opened: abstract.
   - Shown: masking consistently beats penalty-style handling of invalid actions. Unmasked training pushes down invalid actions at visited states, and through shared weights this suppresses valid actions at unvisited states (proved for softmax policies with shared features). The abstract says experiments on Craftax, Craftax-Classic and MiniHack confirm this, and that 'feasibility classification enables deployment without oracle masks'. No numbers in the abstract.
   - For us: this is the main warning against 'just penalise illegal picks and let it learn'. Our slots all share one pointer head, so the same suppression could hit a pick that is legal on a new puzzle. The workable learned replacement the abstract points to is a separate feasibility classifier, which can stand in for the hand mask. UNTESTED at our size and in supervised (teacher-forced) training; the paper is about RL.
3. **Learn What Not to Learn: Action Elimination with Deep Reinforcement Learning** (Zahavy 2018) https://arxiv.org/abs/1809.02121. Opened: abstract.
   - Shown: an Action Elimination Network (AEN) is trained to predict invalid actions, supervised by an elimination signal that the environment provides. It gives a considerable speedup and more robustness over vanilla DQN in text games with over a thousand discrete actions.
   - For us: the closest known design to 'the tool/executor says what was illegal, and a small learned head predicts it'. For us the executor already knows when a slot is used, so it can emit the label for free and train a legality head with a cross-entropy loss, with no hand mask at inference. Cost: one extra head and loss; the abstract shows no numbers for a small supervised setting.
4. **VAM: Verbalized Action Masking for Controllable Exploration in RL Post-Training, a Chess Case Study** (Zhang 2026) https://arxiv.org/abs/2602.16833. Opened: abstract.
   - Shown: the action mask is written as text in the prompt, and the model must output an action from that set. Iterative pruning re-samples under a smaller mask. In chess it improves learning efficiency and final performance over strong baselines. No numbers in the abstract.
   - For us: a text-visible mask fits Ben's rule that a rule lives outside the model and comes back as text the model reads. A 'used: 3, 7' line in the prompt is a learned-use version of our hand mask. Evidence is an LLM post-training chess setup, not a 3M model.
5. **Modeling Coverage for Neural Machine Translation** (Tu 2016) https://arxiv.org/abs/1601.04811. Opened: abstract.
   - Shown: a coverage vector tracks attention history and is fed into the attention model, so future attention considers untranslated words. It significantly improves translation and alignment quality. No numbers in the abstract.
   - For us: this is the learned 'used marker'. The usage is given to the network as input and the network learns how to use it, so there is no hard mask. For us: add a per-slot used/coverage feature to the pointer query and let the pointer learn to avoid used slots. Cost: nearly zero parameters. UNTESTED: whether it reaches 100% legality, since a soft input can still be ignored.
6. **Get To The Point: Summarization with Pointer-Generator Networks** (See 2017) https://arxiv.org/abs/1704.04368. Opened: abstract.
   - Shown: a pointer-generator copy mechanism plus a coverage mechanism that tracks what has been summarized and discourages repetition. It beats the then state of the art by at least 2 ROUGE points on CNN/Daily Mail.
   - For us: B2's GEN head is already this architecture, so adding a coverage term is a known, small, learned add-on for repeats in GEN and for reusing numbers in the pointer. Note that the coverage in this paper enters the attention and adds a loss penalty. It is not a hard mask.
7. **Pointer Networks** (Vinyals 2015) https://arxiv.org/abs/1506.03134. Opened: abstract.
   - Shown: attention is used as a pointer over input positions to select output tokens, for sorting and combinatorial problems where the output size depends on the input length.
   - For us: background for our slot pointers. The abstract says nothing about visited masks. In the TSP follow-up (Bello 2016, https://arxiv.org/abs/1611.09940, abstract opened) the abstract describes policy-gradient training with negative tour length as the reward and 'without much engineering and heuristic designing'. From memory, not shown by the abstract: that line of work masks visited cities.
8. **Generalization through Memorization: Nearest Neighbor Language Models (kNN-LM)** (Khandelwal 2019) https://arxiv.org/abs/1911.00172. Opened: abstract.
   - Shown: linearly interpolates a pre-trained LM with a kNN model in the LM embedding space, with no additional training. On Wikitext-103 it gets 15.79 perplexity, a 2.9 point gain. It helps most on rare patterns such as facts.
   - For us: our notebook (top-16 cosine vote, theta 0.9, 0.99-quantile gate) is a hard-threshold cousin of this fixed-lambda interpolation. Because the abstract says no training is needed, the interpolation weight can be left outside the model, which is exactly the hand-set rule Ben dislikes. Scale here is large (Wikitext-103, big LMs).
9. **You can't pick your neighbors, or can you? When and how to rely on retrieval in the kNN-LM** (Drozdov 2022) https://arxiv.org/abs/2210.15859. Opened: abstract.
   - Shown: kNN-LM helps most when retrieved items are semantically close to the query. The paper defines a formulation where retrieval quality sets the interpolation coefficient, giving nearly 4% perplexity improvement on Wikitext-103 test. It also finds that large overlapping n-grams between datastore and eval set drive the gain.
   - For us: the direct support for 'replace the fixed gate with one that reads the retrieval quality'. For the notebook that would be a small learned function of the top-k similarity scores and vote agreement, in place of a fixed 0.9 and a quantile cut. The abstract does not say whether the coefficient function is learned or hand-fit, so check the paper before copying it.
10. **Adaptive Nearest Neighbor Machine Translation** (Zheng 2021) https://arxiv.org/abs/2105.13022. Opened: abstract.
   - Shown: a light-weight Meta-k Network picks the number of neighbours k per target token, and is trained with only a few training samples. It filters noisy retrievals and significantly beats vanilla kNN-MT on four benchmarks. A Meta-k Network trained on one domain transferred to others with consistent gains.
   - For us: the best small-data evidence that a learned gate over retrieval can be trained from very little supervision and still transfer. For us this could be a small MLP over the top-16 similarity scores that outputs 'answer from notebook or not'. Cost: a tiny network plus labels (was the retrieved program correct?), which the executor can supply.
11. **Adaptive Semiparametric Language Models** (Yogatama 2021) https://arxiv.org/abs/2102.02557. Opened: abstract.
   - Shown: a learned gating function combines local context, a short-term cache of hidden states, and long-term kNN memory, per timestep. Gains over strong baselines on word-level and character-level language modelling. No numbers in the abstract.
   - For us: a learned three-way gate, trained end to end with the LM. It is a template for letting the model decide, per step, whether to use the notebook. Relevant: the character-level experiments. UNTESTED at 3M parameters.
12. **Memorizing Transformers** (Wu 2022) https://arxiv.org/abs/2203.08913. Opened: abstract.
   - Shown: approximate kNN lookup into a non-differentiable memory of past (key, value) pairs improves language modelling on C4, arXiv, PG-19, GitHub and Isabelle. Performance keeps improving as memory grows to 262K tokens, and the model can use newly defined functions and theorems at test time.
   - For us: the abstract does not describe the gate. My recollection (from memory, not shown) is that it is a learned per-head gate on a layer that mixes local attention with kNN attention. That is the learned-gate design we want, but check the paper before relying on it. Supports a non-differentiable store whose use is learned.
13. **Improving language models by retrieving from trillions of tokens (RETRO)** (Borgeaud 2021) https://arxiv.org/abs/2112.04426. Opened: abstract.
   - Shown: a frozen BERT retriever, a differentiable encoder and chunked cross-attention over retrieved chunks. With a 2 trillion token database RETRO matches GPT-3 and Jurassic-1 on the Pile with 25x fewer parameters. It can be trained from scratch or retrofitted onto pretrained transformers.
   - For us: in RETRO, there is no threshold at all. The model cross-attends to whatever is retrieved and learns how much to trust it. This is the cleanest 'no hand-set gate' design, and the retrofit result suggests it can be added on. Scale is far from ours; UNTESTED for a few thousand stored programs.
14. **Training Language Models with Memory Augmentation (TRIME)** (Zhong 2022) https://arxiv.org/abs/2205.12674. Opened: abstract.
   - Shown: a training objective that treats in-batch examples as the accessible memory, so the LM is trained to use memory rather than having memory bolted on at test time. Perplexity on Wikitext-103 falls from 18.70 to 15.37, with negligible extra training cost.
   - For us: matters for us because our notebook gate is set after training (0.99 quantile). TRIME says to train with the memory present so the model learns when to trust it. Cheap to try: put a batch-local notebook into training.
15. **Why do Nearest Neighbor Language Models Work?** (Xu 2023) https://arxiv.org/abs/2301.02828. Opened: abstract.
   - Shown: kNN-LM's advantage comes from a different input representation for prediction, approximate kNN search, and softmax temperature of the kNN distribution. The authors fold these insights back into the parametric LM and improve it without an explicit retrieval component.
   - For us: a caution that part of a retrieval gain may be obtainable by training the model differently, so test a no-notebook model with the same extra training before crediting the notebook. UNTESTED for our synthetic tasks.
16. **kNN-LM Does Not Improve Open-ended Text Generation** (Wang 2023) https://arxiv.org/abs/2305.14625. Opened: abstract.
   - Shown: interpolating with the retrieval distribution raises perplexity for most tokens, with the average gain coming from a small subset of tokens. In long generations retrieval entropy grows faster than the base LM's, so retrieval is less reliable with model-generated queries (exposure bias).
   - For us: for our multi-step programs, queries built from the model's own intermediate states are exactly the exposure-bias case. A single fixed threshold can pass on easy rows and fail on drifted ones; a learned gate with those drifted queries in training is the fix to test.
17. **Robust Tool Use via Fission-GRPO: Learning to Recover from Execution Errors** (Zhang 2026) https://arxiv.org/abs/2601.15625. Opened: abstract.
   - Shown: smaller models often fall into repetitive invalid re-invocations after a tool-call error instead of using the feedback. Fission-GRPO turns each failed trajectory into on-policy corrective training using feedback from a fine-tuned Error Simulator. On BFCL v4 Multi-Turn, Qwen3-8B recovery rate rises 5.7% absolute and accuracy goes from 42.75% to 46.75%.
   - For us: evidence on what tool-side rejection costs. A learner that only sees a sparse error signal repeats the illegal call, and a recovery loop needs its own training data. Scale is 8B and RL, so for a 3M model UNTESTED; teacher-forced error-and-repair rows from our own executor would be the cheap analogue.
18. **Failure Makes the Agent Stronger: Structured Reflection for Reliable Tool Interactions** (Su 2025) https://arxiv.org/abs/2509.18847. Opened: abstract.
   - Shown: after a tool failure, the agent learns an explicit Reflect, then Call, then Final sequence that diagnoses the error and issues a corrected call. The paper reports large gains in multi-turn tool-call success and error recovery and fewer redundant calls on BFCL v3 and its own Tool-Reflection-Bench. The abstract gives no numbers.
   - For us: same lesson as Fission-GRPO from a different method: error-to-repair needs to be a trained action with its own examples, not just a prompt. Shows the cost: extra training rows and extra steps per puzzle.
19. **Adaptive Loops and Memory in Transformers: Think Harder or Know More?** (Frey 2026) https://arxiv.org/abs/2603.08391. Opened: abstract.
   - Shown: per-layer looping with a learned halting mechanism plus gated memory banks with learned input-dependent scalars. Looping mainly helps math reasoning and memory banks help commonsense. The combination beats an iso-FLOP baseline with three times the layers on math benchmarks. Early layers loop minimally and use memory sparingly, later layers use both more.
   - For us: a recent example of learned gates, one for memory use and one for halting, in a looped transformer like our thinker. A learned halt would also remove our fixed 7-step cap and fixed 8 rounds. Abstract gives no model sizes.
20. **ToolRL: Reward is All Tool Learning Needs** (Qian 2025) https://arxiv.org/abs/2504.13958. Opened: abstract.
   - Shown: a study of reward design for tool selection and use under GRPO, covering reward type, scale, granularity and temporal dynamics. They propose a principled reward design and report that it beats SFT-only tool learning. The abstract text I read was cut off and gives no numbers.
   - For us: only relevant if we ever train the tool-calling decision with RL. Our training is teacher-forced, so its main use is as a pointer to the cost: reward design is a new hand-set object. UNTESTED.
21. **Toolformer: Language Models Can Teach Themselves to Use Tools** (Schick 2023) https://arxiv.org/abs/2302.04761. Opened: abstract.
   - Shown: a model trained, self-supervised with a handful of demonstrations per API, to decide which APIs to call, when, with which arguments, and how to use the result. Tools include a calculator, Q&A system, search engines, translation and calendar. Zero-shot gains, often competitive with much larger models. The abstract states that LMs struggle with arithmetic or factual lookup where simpler and smaller models excel.
   - For us: the standard recipe for 'memory as a tool the model calls', where the model writes the call and the result comes back as text. Selection criterion in the paper (from memory, not shown in the abstract) is whether the result lowers later-token loss, which is a learned gate with no threshold we set by hand. Evidence is on large LMs.
22. **Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection** (Asai 2023) https://arxiv.org/abs/2310.11511. Opened: abstract.
   - Shown: one LM is trained to decide on demand whether to retrieve and to critique retrieved passages and its own output via special reflection tokens. The abstract criticises retrieving a fixed number of passages regardless of need.
   - For us: 'retrieve or not' as a token the model emits. This is the learned replacement for our theta. The cost, from the abstract, is the training signal for the reflection tokens; the abstract does not give small-scale numbers.
23. **When Not to Trust Language Models: Parametric and Non-Parametric Memories** (Mallen 2022) https://arxiv.org/abs/2212.10511. Opened: abstract.
   - Shown: LMs struggle with low-popularity facts and scaling does not fix it. Retrieval-augmented LMs largely outperform much larger LMs, while unassisted LMs stay competitive on high-popularity questions. They propose retrieving only when needed. Evaluation is on PopQA (14k questions, 10 models).
   - For us: the gate here depends on a popularity signal, so it is a hand-built rule too (the abstract does not say how the retrieve-or-not rule is set; check). It suggests that retrieval should fire on rare cases and the parametric path on common ones, and the notebook should be judged per frequency band.
24. **Recurrent Relational Networks** (Palm 2017) https://arxiv.org/abs/1711.08028. Opened: abstract.
   - Shown: a many-step relational reasoning module on a graph representation of objects, solving 20/20 bAbI tasks and introducing Pretty-CLEVR where reasoning steps can be varied. The abstract text I have is cut before the puzzle results.
   - For us: UNTESTED: from memory (not shown in the abstract I read), this line of work also solves Sudoku by learned message passing without a hard rule engine. Treat that as a lead to open, not a result.

**Takeaways (helper, ranked):**
- 1. (Largest design impact) Do not replace the used-number mask with a bare penalty. SHOWN (Zabounidis 2026 abstract): unmasked training suppresses valid actions at unvisited states through shared weights, and masking beats penalties. SHOWN in the same abstract: a feasibility classifier lets it run without oracle masks. SUGGESTED change: train a separate legality head on the executor's own 'used / illegal' labels (the Zahavy 2018 AEN design) and give the used-state as an input feature (Tu 2016 / See 2017 coverage). Keep the hand mask only as the measuring stick to compare against, then drop it. Pass mark to fix in advance: legality head at or above 99.9% on held-out puzzles, answer accuracy within 0.5 of the masked model. Wrong if the head leaves any illegal pick that the mask would have blocked.
- 2. Tool-side rejection (executor says 'illegal' in text) is the version closest to Ben's rule, but the evidence says it costs training data and steps. SHOWN (Fission-GRPO 2026, Su 2025): small models repeat invalid calls after errors unless recovery itself is trained, with extra on-policy data or explicit reflect-then-call rows. SUGGESTED: if we want the model to learn from the error message, add teacher-forced rows 'bad pick, error text, corrected pick' made by our own executor. All the evidence is at 8B+ and RL; nothing is at 3M.
- 3. Replace the notebook's fixed gate (theta 0.9, 0.99 quantile) with a small learned gate over retrieval quality. SHOWN: Drozdov 2022 (retrieval quality sets the coefficient, nearly 4% perplexity gain), Zheng 2021 (Meta-k network, trained on few samples, transfers across domains), Yogatama 2021 (learned gate, including character-level LM). SUGGESTED design: a tiny MLP on the top-16 similarity scores and vote share, trained with the executor's check of whether the stored program was right as label. Fix pass marks in advance: no more wrong answers from the notebook than the current gate at equal coverage. Wrong if the learned gate admits more confident-wrong answers on a held-out frame split.
- 4. Train with the memory present, rather than adding it after training. SHOWN: TRIME 2022 (in-batch memory during training, 18.70 to 15.37 perplexity), RETRO (cross-attention to retrieved chunks with no threshold). SUGGESTED: make the notebook a cross-attended input (retrieved program as extra text/vectors the thinker reads) so the model learns trust. Cost: more compute per row and more care so training rows cannot retrieve themselves. UNTESTED at our size.
- 5. A reality check on retrieval gains. SHOWN: Xu 2023 (part of the kNN-LM gain comes from representation, search approximation and temperature, and can be folded into the base model) and Wang 2023 (the gain is concentrated on a few tokens and washes out in long self-generated text). SUGGESTED: compare against a no-notebook control, and test the gate on queries made from the model's own intermediate states, since that is where a fixed threshold is most likely to drift.
- 6. Learned halting and learned memory use already exist together in looped transformers (Frey 2026 abstract). SUGGESTED: this is the way to also remove the fixed 8 rounds / 7 steps, but it is a separate change, to be tried one at a time after the legality head.
