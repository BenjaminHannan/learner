The first bench run (round 1, D1, gold mode) reserved 14.98 GiB. That is above `learnlab.train.TrainConfig.memory_limit_bytes`
= 14 GiB, the run trainer's guard, which C0 applies since the sixth pass (item 1) so that the bench and the runs abort
alike. D1 is a required arm, so C0 stopped at once (eighth pass, item 7) and the box wrote STOP-AND-ASK.txt and a ledger
stop. The bench batches are drawn like the trains' stream (max_tokens 55,000, max_visits 48, label-free). So **the
registered D1 run (the flag-off baseline, not the swarm) would trip the same guard on this box**, and S0, with more rows
per question, very likely too.

## What this shows and does not show

- **Shown:** at the registered batch (55,000 tokens), D1's peak *reserved* memory on this box (torch 2.14.1, CUDA 12.6,
  Linux) exceeds 14 GiB in gold mode.
- **Not shown:** whether peak *allocated* memory exceeds 14 GiB (the guard reads reserved, which includes allocator
  cache and fragmentation), whether D1 fit under the guard in earlier full-size runs, or anything about the swarm.
- **Suggested, untested:** reserved can exceed allocated by fragmentation, so the allocator setting
  `expandable_segments` may bring the peak under 14 GiB with identical numerics. The 14 GiB guard is a Windows
  safeguard; on a 24 GB Linux card it is stricter than the hardware needs.
