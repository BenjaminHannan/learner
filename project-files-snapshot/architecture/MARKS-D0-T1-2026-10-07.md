## Definitions (suggested)
- **Inside** = plain B2 as it is today: the thinker writes (op, pointer, pointer) steps, an int64 executor writes the result into a workspace slot (exact 93-number code).
- **Outside (T1)** = the calculator is not part of the model. The talker writes the call as text from the thinker's state, copying the numbers from the question and any earlier results with its existing copy path (e.g. `add 12 5`). The calculator is a plain function over that text and returns a string (`17`). The string is appended to the context and read by the reader as ordinary characters. The thinker loops again and ends by writing the answer text. The thinker gets no exact value codes and no executor slots. Everything else (reader window, sizes, data, 24k updates, batch 256, lr 1e-3, bf16, rows, order) matches B2, so the size stays within +-3% of 3.24M. Whether the workspace slots stay for the prompt numbers only is the build thread's call, disclosed in the report; result slots must go.
- Same seeds as the inside runs: 200-205, paired. Inside = B2 checkpoints already on branch `claude/b2-confirm-checkpoints` (f41d0f7d5) and q33's scores; do not retrain them.

## D0: read and write check, no training (CPU, B2 checkpoints s200-s205)
- **Reading:** on dev prompts, fit a probe (linear, trained on a train split of prompts, scored on held-out prompts) from the reader output at each number's characters to each digit of that number (units to 9th place) and the digit count. Report per-digit accuracy.
- **Writing:** give the talker's copy path a result string of 1-9 digits and a place in the context and score exact string copy (all digits right) on held-out values, with the result appended as text exactly as T1 will. If that needs the T1 build, run it on the T1 screen instead and say so.
- **Marks (suggested):** reading per-digit accuracy >= 99% on every place, writing exact-copy >= 99%. Below that, the break is in that stage: report which, with per-place numbers, and stop T1 until it is fixed. If both pass, the chain is not broken at the digits and T1 goes ahead. D0 cannot prove the whole chain sound.

- **Pass** = marks 1-6 all hold.
- **Proved wrong:** outside is more than 2.0 below inside on the pooled-5 6-seed mean, or chain-5 mean below 95. Then T1's idea (the model does not work through a text calculator) stands as a finding, and the next step is the broken link, not a retreat inside.
- A shortfall that is not proved wrong (between -2.0 and the CI band) = **not shown**: find and fix the link the diagnosis names, one change, re-screen.

## Amendment 1 (11:50 AM ET, before any run): what the code shows about today's number input and output
Shown in `ledger.py` (read by the architecture thread, not run):
- **Input:** the number VALUES the thinker uses come from a hand-written regex (`pp.NUM_RE`) that turns each number into an int64 (first 16 numbers). The reader's output is only averaged over each number's digits and added to that slot; the value code itself is exact and comes from the regex. So the reader has never had to carry exact digits for the thinker to use a number.
- **Output:** in NUMBER mode the talker prints `str(vals[slot])` (Python), and in WORD mode it copies `prompt[start:end]` using hand-written word boundaries. Only the pointer (which slot or word) is learned. The only fully learned writer is GEN: 9 registers, up to 8 letters, with the copy gate.
- So "the talker copies the numbers with its existing copy path" in the definitions above is wrong for digits: the existing copy path is the 8-letter GEN path. T1 needs a learned digit writer, and the thinker needs a learned digit reader.
Consequences (suggested):
- D0 reading on the existing checkpoints will probably fail, because nothing trained them to read digits. That is not evidence that B2's reading is "broken"; it is a baseline. Report it as such, and add a D0 control: the same probe on a reader trained for digits only (build thread's call, one cheap run).
- T1's "chain-5 >= 99, parity with inside" marks stand unchanged, and are harder than they looked, because T1 replaces regex input, str() output and the executor at once. A miss should be diagnosed link by link: (a) input digits, (b) step choice, (c) call writing, (d) result reading. None of the marks above is loosened.

## Amendment 4 (about 6:10 PM ET, 10-07; sealed before any span-copy re-screen result is read): write_copy scores unambiguous operands only
Raised by the idea swarm via the coordinator (not rechecked here): in models/tool.py sources() (about lines 311-321 at 2b1cbd4d7) an operand is labelled "copied from earlier result k" whenever its text equals an earlier call result. A prompt number or constant that happens to equal an earlier result then gets labelled a copy; write_copy swaps that result for random digits, so the model's correct value scores as a miss. Plausible at 1-2 digits (it fits 1-digit 86% < 2-digit 93%), rare at 4+, so it does NOT explain the 4+ failure. Suggested, untested until the check runs.
Ruling: the concern is sound as a scoring defect, and it is fixed by changing WHICH operands are scored, not the 99% line.
1. **Disclosure check first (CPU, no GPU, no model):** count, per digit length 1-9, operands where the text label (equals an earlier result) and the progparse gold slot disagree. Print the table with n per length. This reads no re-screen result and no checkpoint output.
2. **Scoring rule, fixed now:** write_copy is scored only on UNAMBIGUOUS operands: the operand's text equals exactly one earlier result and equals no prompt number or constant (so gold source = that result by either method). Operands that match both a result and a prompt number/constant are reported separately as "ambiguous" with their exact-copy rate, and not counted in R1/R3. Answer-copy rows are filtered the same way (answer text equal to a prompt number is ambiguous).
3. **Marks do not move:** R1 stays >= 99% at EACH length 1-9, both operand and answer, both seeds, on the unambiguous set. R3's "1-3 digit cells not below now" compares to the CURRENT T1 checkpoints (40b-t1-s200/s201) re-scored with the same new scorer, run once, before the re-screen is read, and the old (unfiltered) numbers are printed next to them.
4. **Sample size:** each length cell needs n >= 200 unambiguous operands (answers too). A cell below that is reported with n and its rate, cannot pass or fail by itself, and the build thread adds rows of that length to the scorer's test set (test data, not training) until n >= 200. If 4-9 digit cells still cannot reach n, say so.
5. **Not allowed:** choosing the filter after seeing re-screen numbers; dropping rows because the model missed them. The filter depends only on the text and the gold slots.
6. Proved-wrong line (any 4-9 digit cell < 90%) is read on the unambiguous set too. Amendment 3 is otherwise unchanged. H1 still waits.
