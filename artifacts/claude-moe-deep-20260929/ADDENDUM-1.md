Selftest on the box: "ok"; seal 6 of 6 OK.
2. **The sealed smoke printed SMOKE-FAIL, and the cause is a bug in the check, not a device mismatch (shown).** The forward half passed: max logit difference 9.5e-7 (mark 1e-3), stop probability 1.8e-7 (mark 1e-3), routing agreement 1.0 in every layer (mark 0.99), strict fp32 flags true. The update half read `same_start: false` and `update_rel_diff_all: Infinity`. Cause: the driver's `cpu_state()` returns `v.detach().cpu()`, which for a tensor already on the CPU is the live parameter, not a copy (checked here: the snapshot equals the weights after they change). So the CPU half's "start state" moved with training, the CPU update was measured as zero, and the ratio divided by zero. `cpu_state` is used elsewhere only to save files, where aliasing does not matter.
3. **Fix, fixed now:** `scripts/claude_moe_deep_smoke2.py` (new file) runs the sealed smoke unchanged except that the snapshots are clones, with the same SMOKE_MARKS, on a separate short rental of the same GPU model and image. **Rule:** if SMOKE2 passes, PASSMARKS "Machine" is satisfied and the comparator stays L* = 51.29 (the recorded CPU loops). If SMOKE2 fails, PASSMARKS "Machine" applies as written: the verdict needs a same-GPU loop control and waits for one; nothing is claimed from the MoE scores alone.
4. **Loop control.** The qualified loop sources exist only on Ben's Mac, so the same-GPU loop control cannot run on this rental. As PASSMARKS says for that case, L* = 51.29 and the same-machine check is reported as untested (BensPC mxd-1 can still supply it later).
