**(a) Cross-arm branch, from a genuine failure.** Running the *unmodified* v1.2 driver on the

writes **no** `tierL/evaluation-L.json`, **no** `tierL/gate_table.json` and **no**
`tierL/predictions-L.json` — all three of which the v1.1 code *did* write on the same data. The

anywhere in the output tree is the configuration key name `"evaluator_E_key": "E_primary"`; no value.

**(b) Row-invariant branch, by deliberate tamper.** In scratch I monkeypatched the *imported module*
(no production file touched) to do three things at once: force `executed_cross_arm_check` to report
valid, so that branch cannot be what stops the run; inject a single
`rung_unused_reservation_ops = -1.0` into one rung-256 ledger row; and replace both `run_evaluator`
and `build_gate_table` with landmines that raise if ever called.

Result: **neither landmine fired.** The run stopped with
`final_verdict: "calibration-invalid/accounting"`, `H_permitted: False`, `evaluator_called: False`,
`accounting_stop: True`, `gate_table_written: False`, and `row_invariants.valid: False` naming the
single offending row out of 60 checked. **Scientific output files on disk: none.**

So the guard catches a one-op discrepancy — `>=`, exact, no tolerance — and it provably executes
before any code that could read truth or produce a score.

**(c) Positive control.** I confirmed the guard is not simply blocking everything: see §6(a).

## 6. The three flagged items

### 6(a) The fixture no longer reaches the gate — is coverage still adequate? **Yes, and I did not have to take it on faith.**

The concern is real: under v1.2 the published fixture stops at accounting, so the fixture run no
longer exercises the evaluator subprocess → adapter → gate → verdict path end to end. The builder's
"second path" is the test group that drives `build_gate_table` and `GATE.evaluate_tier` from synthetic
evaluator reports, including the null-`E_primary` case, missing-field cases and the complete-wave
check. That is good coverage of the adapter and the calculator, but it stubs out the real evaluator
**process**, which is the part that opens `private/` and joins truth.

So I restored the missing path myself. In scratch I ran the **v1.2 driver on the fixture** with the
cross-arm predicate — and only that predicate — forced valid, leaving the per-row invariant real
(it passed on its own merits, 60/60 rows). The run went all the way through: the evaluator
subprocess executed, `predictions-L.json`, `evaluation-L.json` and `gate_table.json` were all
written, and the gate block was reached with its full key set (`prerequisite`, `too_easy`, `learned`,
`advance`, `startup_labels`, `completeness`, `integrity`, `escalates_to_H`, `reasons`, `verdict`).

Then the decisive comparison: **all three files are byte-identical, modulo the version string, to the
frozen-v1.1-code fixture run.** The evaluator → gate → verdict path under v1.2 produces exactly what
it produced under v1.1.

*(I report structure only. I have not published, and will not publish, any E value, startup label or
gate verdict, even from the fixture.)*

**Does the fixture's stop indicate risk for the real calibration run? No.** The fixture fails the
cross-arm rule because fixture worlds publish far fewer audit keys than the schedule reserves, so the
G and T arms' executed non-fitting work diverges at rung 512 — a property of the toy data, not of the
amendment. On the real calibration shapes the dry run measures the worst gap at **0.014096** (tier L)
and **0.000557** (tier H), i.e. 3.5× and 90× inside the limit, and those numbers are deterministic
and identical across all worlds and seeds. Calibration is nowhere near the boundary.

**One residual recommendation, non-blocking:** the fixture is now a *guard* smoke test rather than a
*gate* smoke test. Post-launch, the fixture should either be regenerated with audit-key counts that
match the reservation, or the project should accept that the gate path is covered by the synthetic
tests plus this audit's demonstration. That is a v1.3-or-later question, not a launch blocker.

### 6(b) `checkpoint_hash` moves in every ledger row — **acceptable.**

The `.pt` payload embeds `experiment_version`, so every checkpoint's byte hash changes even though
the tensors do not. I verified the tensors are bit-identical (§3), so this is a labelling change.

I also checked the consequences rather than assuming them: **`checkpoint_hash` has no consumer in the
driver at all** — a repo search finds zero reads. It is provenance metadata written into the ledger.
Resume integrity uses a separate mechanism: the driver recomputes `sha256_file` over the checkpoint
and compares against a `state.json` record written **by the same wave**, so there is no cross-version
comparison to break. And the v1.2 wave writes to a fresh `registered-v1.2` directory and is refused
outright if pointed at the quarantined v1.1 tree, so a v1.1 `state.json` can never be consulted.

Acceptable, and arguably desirable: it makes v1.1 and v1.2 artefacts non-interchangeable at the byte
level, which is what "v1.1 is closed" should mean in practice.

### 6(c) The latent `KeyError` on the `resource-infeasible` branch — **acceptable unfixed, with a caveat the coordinator should record.**

I characterised it empirically rather than by reading. Forcing `preflight` to report `fits: False`
(and landmining `run_shard` to prove no fitting occurs):

- The branch sets `verdict["tiers"][tier] = {"preflight": check}` only. It writes `verdict.json`
  successfully, then calls `text_report(verdict)`, which indexes `block['n_shards']` at driver line
  1157 and raises **`KeyError: 'n_shards'`**.
- `main()` catches only `ValueError` and `FileExistsError`, so the `KeyError` propagates: the process
  dies with a traceback and **exit code 1**, not the intended exit code 3, and `report.txt` is never
  written.
- Files on disk afterwards: **`verdict.json` and nothing else**, carrying the correct
  `final_verdict: "resource-infeasible"`. The `run_shard` landmine never fired.

**Can the registered run reach it?** Yes, in principle. The preflight is a measured timing
extrapolation run before tier L and again before tier H; if the machine is loaded or slow enough that
the remaining schedule with its margin exceeds the usable window, the branch fires. It is not
unreachable dead code.

**Is it fail-safe?** Yes, on every dimension that matters. It triggers strictly *before* any fitting,
so there is no ledger, no checkpoint, no prediction, no evaluator call, no gate table and no
accuracy value anywhere. The machine-readable verdict is written correctly before the crash. The
crash is loud and the exit status is non-zero, so no wrapper can mistake it for a pass. There is no
path by which this defect can manufacture, corrupt or conceal a scientific result.

**Pre-existing, not introduced.** The same `block['n_shards']` index is at line 1087 of the frozen
v1.1 driver. v1.2 adds a second unguarded index (`block['row_invariants']`) two lines further down,
but `n_shards` already raises first, so v1.2's behaviour on this branch is identical to v1.1's.
Carrying it unfixed is exactly what condition 9 ("nothing else changes") requires, and fixing it now
would be an out-of-scope edit to the driver after the fix was scoped.

**Judgement: launch with it unfixed. Do not escalate to v1.3.** Two things should be recorded so a
crash is not misread at 2 a.m.: (i) if the wave dies with `KeyError: 'n_shards'`, that is the
registered resource-infeasible stop, and `verdict.json` in the output directory states it — it is
**not** a bug to patch-and-rerun, and re-running after such a stop needs the same launch discipline
as any other launch; (ii) the exit code in that case is 1, not the documented 3. Both belong in the
v1.2 manifest disclosures alongside the other carried-over items, and the fix belongs in the second
freeze.
