# Retention isolation audit (read-only, 2026-09-27)

**Conclusion.** Preserve an entire *serving function* per released skill, including preprocessing, embeddings, attention, normalization, recurrent state and stop rule, output head, adapter or weights, and routing policy. A frozen expert alone is insufficient. Task-level dispatch to immutable snapshots can give an engineering guarantee for registered tasks with correct dispatch and unchanged dependencies. It is not a general continual-learning guarantee, nor evidence that a fixed-size model can acquire indefinitely many skills.

## Avoidable code/measurement hazards

1. **Shared paths and denominator.** `scripts/claude_rsn358e_moe.py:68-79` computes softmax over *all active* experts and scales the chosen expert by that probability. `scripts/claude_rsn358e2_arms.py:50-60` adds zero-initialized router rows and new experts; old routing probabilities therefore change even if the winning old expert does not. `scripts/claude_rsn358e3_replay.py:63-75` freezes every old parameter, including attention, embeddings, norms, output and stop heads. `scripts/claude_rsn358a_run.py:62-68,71-108` shows these are shared parts of the recurrent function. Freeze tests should compare old-task output and stopping over full rollouts, not just tensor hashes or expert identity. If using a fixed old skill, evaluate its *original, closed* router and denominator; do not append new logits to its softmax.
2. **New-path starvation and limited capacity.** e3's new router groups start at zero and use top-1 routing (`scripts/claude_rsn358e3_replay.py:42-60`); e4 seed 4 sent zero sums cells to the new group in both blocks (`artifacts/claude-rsn358e4-20260927/DIAG-new-group-share.md`). e5's forced warm training (`scripts/claude_rsn358e5_warm.py:41-79`) addresses this specific training dead zone, but inference still routes freely. e6 reopens attention/norms (`scripts/claude_rsn358e6_sharedtrain.py:37-56`), which removes exact functional isolation. At equal total size only 352,944/1,654,446 weights train after growth, and each new expert is width 85; e6 raises the trainable count to 882,640, so any improvement would confound trainable capacity with which layers were opened.
3. **Metric timing and mutable state.** The score hook grows immediately after the phase score, then `expert_share` is read (`scripts/claude_rsn358e3_replay.py:110-120`; `scripts/claude_rsn358e_moe.py:178-179`). Some early reports described these shares as pre-grow; the correction is recorded in `artifacts/claude-rsn358e3-20260926/RESULTS.md`. e4 originally stored a mutable replay-count dictionary in result rows; the snapshot copy at `scripts/claude_rsn358e4_replayall.py:57-60` fixes it. The runners also use module-global `ST` and monkey-patch imported functions (`scripts/claude_rsn358e4_replayall.py:30,81-95`) and DL9 changes global prompt text (`scripts/claude_dl9_experts.py:149-155,269-283`). These are isolation hazards for reused processes/concurrent tests; make run state instance-local, restore every temporary override with `try/finally`, and test order independence.
4. **Evaluation selection.** The same generated dev panels and seed 48000 recur across rsn358e variants (`scripts/claude_rsn358e_moe.py:54,108-121`), and later interventions were selected after reading earlier scores. Those are useful development comparisons, not independent confirmation. DL1's fixed 300-item HARM panel mixes capitals, word forms, sequence, counts, and 100+ bigger-number items (`scripts/claude_dl1_nights.py:59-141`); `net_harm = lost - gained` (`:319-322`) can mask catastrophic gross losses in one kind. The reply scorer accepts a gold phrase anywhere in the first eight words (`:154-161`), so use exact or human-adjudicated answers for a release gate and report per-kind gross losses/gains. Record base-right denominators and paired item transitions, not just mean total accuracy or KL.
5. **DL9 router comparison.** The classifier sees one fixed puzzle frame as positives and filtered base-written quiz questions as negatives (`scripts/claude_dl9_experts.py:23-31,69-90,175-185`). A good held-negative score may reflect prompt/source cues rather than skill recognition; reworded puzzles and hard negatives are essential. Its random gate matches only the combined on-count across 100 puzzle and 300 panel items (`:140-146,192-197`), so its low puzzle coverage is expected if the learned switch routes puzzles on and panel off. Report separate per-domain on-rates and include simple prompt-rule, reworded, adversarial, and calibrated-abstention baselines. A learned router can still misroute and cannot guarantee retention.

## Review of the proposed solution

**Small typed reasoner:** give the external task ID once per problem, pin one immutable `(model/snapshot, preprocessing, solver/stop rule)` to that ID, and keep the choice fixed across all recurrent rounds and cells. If a new skill needs earlier computation, train a *whole clone* of the previous complete function; a base plus a new expert does not inherit a modified shared trunk safely. Test an unknown/mislabelled ID explicitly. Existing `env` embeddings (`scripts/claude_rsn358a_run.py:76-97`) do not themselves provide isolation because downstream weights are shared.

**1B:** freeze the base and each released adapter, and serve a task with a pinned base revision plus exactly its adapter and prompt template. Train a new adapter from an immutable base, or train a whole clone if the new skill depends on an earlier adapted function; never continue the released adapter in place. A learned classifier on frozen base features may route when IDs are unavailable, but expose its confidence and abstain to the base for unknown tasks. Version the classifier too. Put routing at the *request/task* level before generation, not per answer token; reset model/KV/cache/LoRA scales between requests and test alternating tasks in the same process. The existing scale-zero comparisons (`scripts/claude_dl1_nights.py:285-308`, `scripts/claude_dl4_anchor.py:51-66`) restore state only on normal exit; production serving should use scoped restoration even on exceptions. DL9's switch is a useful prototype, pending its results and hard-negative tests.

**Release gate and falsifiers:** register independent, untouched release panels per skill before training; keep a separate development panel for router/threshold selection. After adding skill B (and again after C, restart, save/load, and alternating A/B requests), compare every old task's exact outputs, stopping decisions and per-item score to its previously released artifact under the same deterministic settings. Hash all weights, tokenizer/prompt code and router mapping. For known IDs, any old-task output change falsifies the scoped isolation claim; a wrong route, shared mutable state, changed softmax normalization or dependency/version drift explains it. For learned routing, report confusion, calibration, OOD abstention, per-kind old-task losses, and the joint rate of correct route **and** correct answer; a frozen branch with poor routing fails end-to-end retention. Require new-skill gain versus a frozen baseline and storage/latency budgets as separate gates. A one-puzzle or one-panel success, a net-harm PASS, and an old-weight hash alone are insufficient.

**Scope:** immutable full snapshots plus correct deterministic task IDs can preserve an old implementation's outputs by construction, at growing storage cost. They do not prove transfer, open-world task recognition, compositional use of skills, or continual learning at fixed total capacity. The independent learned router offers a measured reliability claim only, never an exact one.

## Review of the new request-scoped 1B bypass

`premonition/retention.py:24-38` preserves the B2 LoRA arithmetic and state-dict parameter names while returning `self.base(x)` directly when disabled. The toy tests establish exact equality for one layer, and the poisoned-A test proves that layer's disabled path does not evaluate adapter tensors (`tests/test_retention.py:45-55`). The `finally` reset and default-off choice are sensible. The following remain concrete release risks:

1. **Base freeze is incomplete as an invariant (high).** The constructor verifies only each wrapped projection's `mod.base.parameters()` (`premonition/retention.py:56-62`). It does not reject or freeze other trainable model parameters: embeddings, layer norms, heads, or unwrapped projections can be re-enabled after `add_lora`, and training them changes the disabled route. B2's `add_lora` initially freezes every existing parameter (`scripts/claude_blurt2.py:263-268`), so the current toy passes, but the controller does not enforce that condition at installation or later. `tests/test_retention.py:78-88` trains only a model freshly frozen by B2. Add a test that makes an unwrapped parameter trainable and require construction/training to fail or verify *all* non-A/B parameters stay frozen; train candidate adapters away from the published serving instance. The digest is an audit readout, not a write barrier.
2. **Cache guard covers one entry point (high).** `generate()` rejects top-level `past_key_values` and `cache` kwargs (`premonition/retention.py:87-94`), but public `scope()` permits `model.forward`/`model.generate` directly and leaves cache lifecycle to callers. A prefill under one route followed by continuation under another within separate scopes would mix KV states despite every LoRA layer obeying its flag. A normal `generate()` should construct/use its own cache during a single call; the toy `Toy.generate()` ignores caching entirely (`tests/test_retention.py:18-28`), so the eight tests do not verify this. Keep cache ownership inside one routed request; reject externally supplied `Cache`/legacy KV objects at every exposed inference path, or restrict `scope()` to internal use. Test a real B2-compatible causal model with prefill + multi-token decode, `on -> off -> on` requests in one process, and an attempted cross-route KV reuse.
3. **Context propagation can outlive a scope (medium).** `ContextVar` isolates concurrent threads/tasks, but an `asyncio` task created inside `scope(True)` inherits that context and may run after the parent exits (`premonition/retention.py:73-85`). That child can still see `enabled=True`; the thread-only test (`tests/test_retention.py:66-76`) cannot catch it. Do not spawn detached work inside a route scope; route and finish each asynchronous generation inside its own scope, with a test that creates a child task during an enabled scope and checks its behavior after parent exit. The current synchronous `generate()` avoids this when used exclusively.
4. **Published artifact identity is broader than `base_digest` (medium).** It excludes A/B but hashes only `state_dict` tensors (`premonition/retention.py:96-106`). Changing LoRA `scale`, dropout configuration, tokenizer/prompt template, generation settings, or route mapping can change outputs without changing that digest. Version and verify those fields and the adapter A/B tensors separately. Also test exact base/adapter output parity after save/load on the actual 1B, not only the single-linear toy (`tests/test_retention.py:90-101`).

The eight tests support the local bypass mechanism; they do not yet establish end-to-end exact retention for a real autoregressive request or immutability of every base path.

**Audit limits:** only code and aggregate completed results in this checkout were inspected; no sealed TEST-ONLY dataset, training, GPU run, or original-file edit. e4 is partial here; e5, e6, DL8, and DL9 outcomes remain unknown.
