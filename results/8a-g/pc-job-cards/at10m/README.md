# at10m: the agent model (B3AT, arm AT) at 10M, seed 400, gated on AT-1a/c/d/f

One run, queue 8aAT10M, job 8aAT10M-10M-s400: the agent-turn model at its 10M shape S (7 blocks, width 256, 4 heads, mlp 4.8, small plug; 9,824,546 trained parameters, the plain partner PTS / PTC at 10M has 9,814,442), same pool, caps and readout as AT-1. Code is `src-at10m` = a copy of `src-at` (custom_io at 6e72a5fae5, AT-1's code, which stays untouched) plus ONE changed file, `train.py` (periodic checkpoint + resume, see below), and one new test. Marks A10-1 to A10-4 and the gate lines are sealed in big-run PLAN.md, eighteenth Addendum 10-12 (the AT-1 marks in the sixth Addendum 10-11); spec addendum AG's M3 fixes the size read.

The gate (`15-at10mgate`, runs just before `16-at10m`) reads AT-1's RESULT.json against G2f's and g2c3s's and turns `16-at10m.txt` into a no-op (`cmd: at10m_skipped.cmd`, original kept as `16-at10m.txt.gated-<stamp>`) if any of these is proved wrong or cannot be read:
- AT-1a: pooled-5 more than 6.0 below G2f, or below g2c3s.
- AT-1c: calculator-off within 10 points of the full score (program questions).
- AT-1d: chain-5 more than 5 below G2f, or thinker-off (`loops:0`) above 60% of the full score.
- AT-1f: any cap counter above 0 in the end-of-training `cap_hits` line (the last one without `"final"`) of `AT\stdout.txt` beside RESULT.json. RESULT.json's own `cap_hits` is taken after the final evaluations, so it is only printed as a report line. If the file or line cannot be read: "not gated, reported later".

AT-1b (reply swap) and AT-1e (stop and long input) are not gated: reported after the run.

Accum AT=64 is a **memory guess** (it is what the 10M B3G2 queue uses; the agent model runs up to 17 turns per row and may need more; the card doubles it on a spill).

## Checkpoint and resume (what changed, and what it does not do)
Why: on 10-11 a PC restart killed two multi-day 10M runs (spec addendum AC, design/8a-g-gemma-growth-2026-10-08.md section 34); this run is 100 to 200 hours, and 6e72a5fae5's `train.py` wrote `checkpoint.pt` once, after the last update, with no optimizer state and no resume.

What changed: `overlay/train.py` replaces `custom_io/train.py` (the original's sha256 is pinned in the installer, the box script and this README; the changes are additions: two flags, helper functions, a few lines in the loop), and `overlay/tests/test_ckpt.py` is new. `local_runner.py`, `g8a/job.py` and everything else are byte-identical to 6e72a5fae5. The queue line adds `--train-extra '--ckpt-every 500 --resume'` (job.py appends those words to the train.py command).

- `--ckpt-every N` (default 0 = off): every N updates and after the last one, `AT\ckpt\step-<k>.pt` + `step-<k>.json` (sidecar: sha256, size, config hash, data id, code id). Written to a temp file in the same folder, fsynced, renamed; the sidecar the same way; only then are older ones deleted (newest 2 kept). The final `checkpoint.pt` is unchanged. Contents: model, AdamW state, python / numpy / torch CPU / torch CUDA (all devices) random states, the model's own `random.Random` streams (b3 `_gap_rng`, tool `_drill_rng`; found by scanning the model, so any other stream of that kind is caught too), the data-order position (the batch count; data.py's per-epoch permutation is replayed, nothing is collated), the loss window of the log line, the cap counters and the model's `*_stats` counters, the elapsed clock and the eval time. The learning rate is a function of the step (and of the elapsed clock under `--minutes`), both restored.
- `--resume`: takes the newest checkpoint whose sidecar parses and whose sha256 and size match (a truncated or corrupt one is skipped with a `ckpt_skipped` line, falling back to the one before). Refuses with `--resume refused: ...` and exit code 1 if the config hash (model, cfg, steps, batch, lr, warmup, grad-clip, seed, order, bf16, max-ans, minutes, caps file content) or the data id (MANIFEST.json sha256, train.jsonl size, row count, vocab) differs, or if every checkpoint in the folder is corrupt (move `ckpt` aside to start over). `--accum` is deliberately not in the hash (memory only; the card's out-of-memory relaunch doubles it). With no checkpoint it starts at step 0, so the same command line serves the first start and every restart. It prints one line `{"event": "resumed", "step": k, "from": "step-k.pt", "msg": "RESUMED step=k from=step-k.pt", ...}` and RESULT.json gets `resumed_from` (list of steps) and `ckpt` (writes, write seconds); with both flags off RESULT.json has exactly the old keys.
- Wall time: `train_s` and `steps_per_s` are the sum of the segments (the elapsed clock is restored; the time the PC was down and the time spent writing checkpoints are left out). The train lines' `elapsed` goes on from the first segment.
- `AT\events.jsonl` (new, only with the flags): every event line of every segment. `AT\stdout.txt` is rewritten by a restarted job and holds only the last segment (the gate's end-of-training `cap_hits` line is in the last segment).

local_runner and a restart (read from `local_runner.py` and `g8a/job.py` at 6e72a5fae5): a run is skipped only if the job-level `RESULT.json` exists; otherwise the same queue file started again runs the job again. **A rerun does not wipe the run's folder**: `run()` does `out.mkdir(parents=True, exist_ok=True)` (local_runner.py line 275), job.py does `os.makedirs(out, exist_ok=True)` (line 292), and nothing in either calls rmtree or deletes files there (job.py removes only its own `.lock` files). A rerun rewrites `stdout.txt`, `cmd.txt`, `rc.txt`, `box.json`, `pool_MANIFEST.json`; `AT\ckpt` is not touched, so no change to local_runner was needed. A leftover `WORK\g8a\pools\*.lock` from the killed job makes the rerun print "waiting for another job" for up to 4 hours: rename it to `<name>.stale-<stamp>` first (the card's step 4). The frozen code copy `WORK\code\8aAT10M-pc-<hash>` is reused when the code is the same; the code folder must stay `src-at10m`. (The vast box's `run_job` did `rm -rf $O/AT` before each launch; it now keeps `AT/ckpt`.)

After a PC restart: start the same queue again, the way the card's step 8 does but with `src-at10m`: `cd /d C:\Users\benja\custom-io\src-at10m`, then `python -m custom_io.local_runner run --work C:\Users\benja\custom-io\work --queue custom_io\queue_local\8aAT10M-pc.txt --device cuda --par 1 --busy C:\Users\benja\GPU-BUSY.txt`. AT\stdout.txt then shows `RESUMED step=<k> from=step-<k>.pt`. The card's out-of-memory relaunch (`8aAT10Mb`) writes to a new results folder, so its step 5b copies `AT\ckpt` over first.

Size and time. Measured at tiny size on the CPU: plain_tf with 23,392 parameters: 0.3 MiB per checkpoint, 0.01 s to write; b3at (agent model) with 88,758 parameters: 1.1 MiB, 0.02 s (12 bytes per parameter: weights plus the two AdamW moments). A synthetic checkpoint of the 10M size (9,824,546 fp32 parameters plus two moments, written with the real save routine, fsync and sha256 included) measured 117.9 MB (112.4 MiB) and 1.1 to 1.2 s on this sandbox's disk, 0.35 s to read back and hash, 0.09 s to load. At 10M: the AT model has 9,824,546 trained parameters = 39.3 MB in fp32, AdamW keeps two moments per parameter = 78.6 MB, plus small scalars: **about 118 MB per checkpoint** (the arm's final `checkpoint.pt` is about 40 MB; Gemma is not in the state dict). Two are kept, plus the final `checkpoint.pt`: **about 280 MB at most** per run. Writing 118 MB takes a few seconds on an SSD (fsync at 100 to 500 MB/s, sha256 about 0.4 s) every 500 updates (about 1 to 2 hours): well under 0.1% of the run, and it is not counted in `train_s`. These 10M figures are estimates; no 10M model was built.

Tested (CPU, tiny models; `python -m custom_io.tests.test_ckpt`, run by the installer):
- shown: with both flags off, the 40-update loss trace, every event line, the RESULT.json keys and the final state_dict are bit-identical to the unmodified train.py of 6e72a5fae5, for the plain model (plain_tf) and the agent model (b3at, arm AT).
- shown: 60 updates straight == 30 updates, a hard kill (os._exit) right after the step-30 checkpoint, `--resume`, 30 more: identical loss trace, final weights, optimizer state and RNG states, bit for bit, for plain_tf (with `--eval-every` and a log window that does not line up with the checkpoint) and for b3at with `ans_drill` 0.5 and `gap_p` 0.5, so the model's `_drill_rng` and `_gap_rng` are drawn. Random sources found: python `random` (global), numpy global, torch CPU global (b3at draws R, the carry rounds and the stop coin from it), torch CUDA (all devices; code present, untested: no GPU here), `B3._gap_rng` and `Tool._drill_rng` (random.Random objects owned by the model), the data order (a seeded RandomState inside data.train_batches, replayed from the seed and the batch count). No other stream exists in train.py, data.py, evalx.py or the models (grep for Random / np.random / torch.Generator / dropout / randperm).
- shown: a corrupt, truncated, sidecar-less or garbled-sidecar newest checkpoint falls back to the previous and reproduces the straight run; a changed lr, steps or data refuses (rc 1, nothing written); a changed `--accum` resumes with a warning; every checkpoint corrupt refuses; `--resume` with no checkpoint starts at step 0 with the same weights as a run without it; a kill between the temp write and `os.replace` leaves no step file and the previous checkpoint intact, and the next save sweeps the temp file.
- not exact after a resume (the loss and the weights are not affected): counters kept once per distinct row in a cache that starts empty again. `capcount` hits and b3's `trace_stats` count a row once per cache entry, so a row already counted before the restart is counted once more if it shows up again (a zero count stays zero, so a check "every cap counter 0" is unaffected). b3's `drill_stats`, `plan_stats` and `free_stats` are exact.
- suggested, untested: the CUDA path (CUDA RNG restore, fused AdamW state load, bf16 autocast) and Windows file handling (os.replace over an existing file, fsync). A resume on a different GPU, driver or torch build is correct but not bit-identical to the uninterrupted run (GPU kernels are not deterministic across machines). The 10M speed is unmeasured.

## Install (Mac -> PC), after `INSTALL AGENT DONE` and before G2f ends
The waiter lists WORK\insert once, at its first check point right after G2f, so this has to be on the PC before G2f ends. The installer refuses if the waiter has logged any later `inserted job ` or `8aB3G2s400 ended` line.
```
scp -r results/8a-g/pc-job-cards/at10m benja@<pc>:C:/Users/benja/custom-io/in-at10m
ssh benja@<pc> powershell -ExecutionPolicy Bypass -File C:\Users\benja\custom-io\in-at10m\install_at10m.ps1
```
(Copy the folder as `C:\Users\benja\custom-io\in-at10m`; its README.md and the `vast` folder can stay; `overlay\` must come with it.) It takes several minutes: after the 10M count check it runs the checkpoint test (tiny models on the CPU). Expected output: the line `src-at (6e72a5fae5) and its pinned files match (train.py included); the overlay files match their pins; waiter v3e (pid ...) is running and has not reached its first insert check point; 11-at.txt is present`; `src-at10m (new): N files of src-at\custom_io copied with equal hashes; overlay train.py and tests\test_ckpt.py applied; queue_local\8aAT10M-pc.txt added; src-at itself untouched`; the at10mcheck lines (`AT 10M trained parameters: 9,824,546 ...`, `PTS 10M trained parameters (g2c10s; PTC equals it): 9,814,442 ...`, `overlay applied: train.py sha256 ...`, `AT10M CPU CHECK OK`); the last test_ckpt lines ending in `ALL OK`; `gate self-test: at10m_gate self-test OK`; the list of WORK\insert files (`15-at10mgate.txt: cmd: at10m_gate.cmd | hours: 1` and `16-at10m.txt: queue: 8aAT10M | src: src-at10m | caps: 433475...62D3 | card: at10m.template.md`); last line `INSTALL AT10M DONE`. Run again: `already installed ...` and `INSTALL AT10M DONE`. ## Seconds per update at 10M
`train.py` prints a `train` step line every 500 steps (`elapsed` in seconds, in `AT\stdout.txt`), and RESULT.json holds `steps_per_s`, `train_s`, `steps` and `peak_mem_mib`. With checkpointing on, `elapsed` and `train_s` are the sum over the segments of a restarted run (downtime and checkpoint writes left out). The only change to the training code is the checkpoint / resume overlay described above.
