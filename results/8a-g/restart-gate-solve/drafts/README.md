## What changed and why

**A. Probe checkpoint guard (bug fix).** `probe-resume` never checked that the checkpoint in `--keep` belongs to the job. The pack's README documents `--keep ...\work\g2fa4\ckpt-keep`, which holds g2fa4's accum-4 step 200, but without `--job` the probe picks the first job that is not skipped, which is g2fa8 (accum 8); `train.py` only emits a `resume_warning` on an accum mismatch (the config hash does not include `--accum`, so the hash cannot catch it either), so the probe would resume an accum-4 checkpoint under accum 8 and report a false FAIL. Now, after the cheap file checks and before anything is started or written, `probe_resume` reads `keep/step-<k>.json` and refuses (exit 2, message, no probe queue or folder created) if: its `step` is not `--step`; its `accum` differs from the job's accum (the `--accum B3G2=<n>` of the job's queue file, parsed by the new `queue_accum`; falls back to `accum` in plan.json; refuses if the two disagree, or if neither exists, or if the sidecar has no `accum`); its `config_hash` differs from the main run's own (full hashes of the sidecars in the run's `ckpt\`, else the 12-character prefix of the `resumed` events; if the main run has neither, the comparison is skipped and a line says so in supervisor.log). After each probe run, an `accum` `resume_warning` in the probe's events (new `Events.warnings`) makes the report FAIL with the reason and no statistics (other warnings, e.g. a code-id change, are only recorded in `resume_warnings` and shown in the .md). New pure functions: `queue_accum`, `main_run_hashes`, `keep_guard`.

**B. Mean-form reading and first-update diagnostic (additive).** `resume_probe_verdict` keeps the registered rule exactly (`verdict`, `n`, `d`, `limit`, `mean_abs_*`, `diff_*` are computed by the unchanged lines) and returns nine more keys: `first_r1_c`, `first_r2_c`, `first_r1_r2`, `Dbar`, `Nbar`, `ratio` (inf if Nbar = 0 and Dbar > 0; 1.0 if both 0), `mean_form_limit = max(0.02, 2 Nbar)`, `mean_form_verdict`, `lag1_autocorr` (of the signed R1 - R2 series; `None` for under 3 points or no variance; new stdlib `lag1_autocorr`, plain biased estimator). `Sup.md_probe` shows them under the heading "recorded beside (pre-registered mean form, not the registered gate)", after the table; a report in the old format still renders. The exit code and `verdict` are still the registered rule's.

**C. Trace-A mean item can be soft.** In `trace_a` the `resume_mean_abs` miss now goes through `miss('resume_mean_abs', ...)` like `resume_max_abs`, so listing it in `rules['soft']` records it in `soft_misses` instead of stopping the run. No default changed: with no soft list, or with today's soft list `['peak', 'resume_max_abs']`, `trace_a` returns exactly what the original returns (tested). Installer: new `--soft-trace-a-mean`, valid only together with `--soft-trace-a` (argparse error otherwise), which writes `soft = ['peak', 'resume_max_abs', 'resume_mean_abs']` (`SOFT_TRACE_A_MEAN`). Idempotency needed no new logic: `added_plan` compares the whole existing g2fa8 entry with the expected one, so the three variants (strict, soft, soft + mean) are mutually "differs from the expected entry" refusals in every order (tested both ways). The first redone update (0.01), NaN/Inf and the loss falling remain hard in every variant (tested with the most permissive list).

**D. `rejudge_probe.py` (new, stdlib only).** `python rejudge_probe.py PROBE-RESUME-<job>.json [--trace-a-mean 0.0282] [--trace-a-json TRACE-A-<job>.json|state.json]`. It recomputes everything from C, R1, R2 in the file (it does not need the new fields, so it also reads a probe made by the old supervisor), applies the pre-registered reading (text copied verbatim in the docstring, the output and the JSON), prints a plain-words paragraph plus the numbers and writes `REJUDGE-<job>.json` next to the input. The value v is `--trace-a-mean`, else `resume.mean_abs` of `--trace-a-json`, else 0.0282. Verdicts: INSIDE healthy noise (exit 0), UNRESOLVED (1), OUTSIDE (2); exit 3 for an unreadable file or a probe that did not judge (`why_fail` set, e.g. the accum refusal of change A). The restore check is exact equality with 0, so any nonzero first-update gap is OUTSIDE ("restore differs at the first update: ... do not read").

## Amendment 1 (PREREG-trace-a2.md, "Amendment 1", written ~22:05 UTC, after the CPU positive controls)

DRAFT, same status as everything above: nothing installed, committed or pushed; the pack is untouched; every new behaviour is opt-in or only recorded, so a plan.json written by the current installer behaves as before.

**Why.** The positive controls showed that the first redone update's loss is a forward pass before the optimizer step, so lost AdamW state and an off-by-one lr schedule give exactly 0 there and first show at the 2nd and 3rd redone updates (A1.1); and that a single ratio failure of the two-resume mean form is a heavy-tail draw, not proof of a fault (A1.3). So: two start-of-redo items in the running gate, the same early window in the reading gate, and a reading that says "measure more" instead of "broken" when only the ratio or the mean form fails.

**1. `trace_a` (running gate), opt-in rule keys in the job's `trace_a` dict.**
- `resume_early_abs` (float): hard item: max |dL| over the 2nd and 3rd redone updates (`d[1:3]`) must be <= it. The failure message names the two updates and the one that is largest ("early redone updates 102 and 103 ... differ by up to 0.0071, at update 103 (limit 0.005)"). It is a `why_fail` item, never released by `rules.soft` (tested with the key named in soft).
- `resume_exact_fields` (list): hard item: at the FIRST redone update, every listed field present in BOTH the earlier segment's train line and the resumed line must be equal (exact `==`; NaN equals NaN). An entry ending in `_` is a prefix (`plan_` matches `plan_rows`, `plan_gapped`, ...); any other entry is a field name (`rounds` does not match `rounds_total`). `loss`, `step`, `elapsed`, `seg` are never compared this way. Mismatches go to `r['resume']['exact_mismatch']` (field, earlier value, resumed value) and to `why_fail`; the fields actually compared go to `r['resume']['exact_checked']`. If none of the listed fields is in both lines, nothing is compared, `why_fail` is not touched and a note says so (the item must not pass silently without anyone seeing that it compared nothing; whether the real `train` lines carry `rounds` / `plan_*` depends on the model's aux dict, see below). **Superseded by the code-review fix round below (item 4): a listed field that is missing is now a hard failure.**
- `r['resume']['early_max']` is recorded ALWAYS when at least 2 redone updates exist (rule or not). This is the one change to the default output of `trace_a`: one extra key in `resume`. Verdict, `why_fail`, `soft_misses` and every other key are identical to the original function's for rules without the new keys (tested against the original function; the comparison helper `strip_early` drops only `early_max`).
- `resume_first_diff` and its default 0.01 are untouched (A1.2 is Ben's bar). The losses are compared exactly as before (the full train-line dicts are kept in addition, for the first redone step only).
- What a `train` event carries: `overlay/train.py` writes `jprint(event='train', step, loss, lr, elapsed, cap_hits, **aux)`. So `lr` is always logged; `rounds` and `plan_*` are logged only if the model returns them in its aux dict (the positive controls' `rounds`, `plan_rows`, `plan_gapped`, `drill_share` come from there; I did not check the real b3g2 model). The fake runner logs `lr` only. `elapsed` is a clock, which is why it is excluded.

## Item 7 (ruling Q95): the early window is refused when it cannot be computed

Ruling (coordinator, Q95): "Item 7 is decided: refusal wins - when the early window cannot be computed as defined, both tools refuse (exit 3); a gate tool never prints a check it did not compute. Align the supervisor to rejudge_probe.py, with a regression test."

Definition: the early window is the 2nd AND 3rd update after the checkpoint (probe: updates step+2 and step+3; trace A: the 2nd and 3rd redone updates). It is computable only with at least 3 updates. `rejudge_probe.py` already refused a probe with under 3 updates (exit 3); it is the reference and its verdict logic is not changed. Before this change the supervisor computed and printed the "early window" from 2 updates (the 2nd alone), which is a check that is not the defined one. What changed, in `g2fa4_supervisor.py` only (`rejudge_probe.py` is untouched; the pack is untouched):

1. **`probe_resume`**: with `--upto - --step < 3` it refuses first thing, before the plan is even read: no probe is started, nothing is written, renamed aside or logged. It prints `refused (exit 3): the early window (updates <step+2> and <step+3>) cannot be computed with --upto <n> < step+3 = <step+3>; use --upto <step+3> or more. Nothing was run or written.` and returns **3**. Exit codes of the command are now: 0 PASS, 1 FAIL, 2 refused for the existing reasons (job skipped, run armed, card busy, missing files, checkpoint guard), **3 = early window not computable**. Documented in the module docstring (usage line of `probe-resume`), in the `probe_resume` docstring, and here. The exit-3 check precedes the exit-2 reasons: a call that has both a bad `--upto` and, say, an armed run answers 3 (the arguments are wrong whatever the state).
2. **`resume_probe_verdict`**: `early_max`, `early_limit` and `early_verdict` are computed and returned only for lists of at least 3 updates (max over indices 1 and 2). With fewer the three keys are **absent** (not None, not computed). `verdict` (P2) and every other key are unchanged: the 1000-random-trace comparison with the original pack function still passes (the allowed new keys are the 9 mean-form keys, plus the 3 early keys when there are 3 or more updates). `md_probe` prints the early-window line only when `early_max` is present, so a result without it (or a report from before Amendment 1) prints none.
3. **`trace_a`**: `r['resume']['early_max']` is recorded only when at least 3 redone updates exist (it was recorded from 2). With 1 or 2 redone updates nothing about the early window is recorded or printed, and for rules without the opt-in keys the result is now identical to the original pack function's in those cases too (the `strip_early` helper is only needed for 3 or more redone updates). The opt-in hard item `resume_early_abs` is unchanged in outcome: with fewer than 3 redone updates it is a hard failure ("early window cannot be checked: only N redone update(s) ..."), never released by `rules.soft`. One consequence: with exactly 2 redone updates the old extra message about the 2nd update alone being over the bar is gone (that was a check of a window that is not the defined one); only the "cannot be checked" failure remains.

Tests (4 new in `tests/test_gatefix.py`, 34 in all): `t_early_not_computable_probe` (a: `--upto` step+2, step+1, step and below: exit 3, message, a full snapshot of the temp tree before and after is equal, `probe_run` and `spawn_detached` never called, an earlier report is not moved aside, 3 comes before the exit-2 "armed" reason, `--upto step+3` runs), `t_early_not_computable_verdict` (b: 1- and 2-update lists: no early keys, `verdict` and all old keys equal the original's, `md_probe` prints no early line; 3 updates computed and printed), `t_early_not_computable_trace_a` (c: 1 and 2 redone updates record no `early_max`, the result equals the original's; with the opt-in rule still the hard failure; 3 redone updates record it), `t_early_agreement` (d: the same 1- and 2-update data from a real probe run is refused by both `probe-resume` and `rejudge_probe.py` with exit 3 and writes nothing; for 3, 4, 10 and 50 updates and for a real `--upto step+3` probe both give the same `early_max`). Four older tests changed to the new rule (`t_verdict_early`, `t_trace_a_early_optin`, `t_trace_a_early_needs_three`, `t_verdict_identical_to_original`).

`gatefix.patch` is regenerated; `patch -p1` on a fresh copy of the pack reproduces `g2fa4_supervisor.py`, `install_g2fa4.py` and `tests/test_probe.py` byte for byte (checked with `cmp`). Test results are in `tests/logs/` and in the commit's report.

Untested: Windows and the real runner (as before). A probe with `--upto` below step+3 was possible before and produced a (2-update) report; any such old PROBE-RESUME json is still read by `rejudge_probe.py`, which refuses it with exit 3 as before.

## Ruling B2 (coordinator, confirmed by the user): an early window the running gate cannot compute is deferred to probe P1b, not a stop

Why (review verdict B2): `trace_a` judges the first resume that has redone updates. An unplanned crash 1 or 2 updates after a checkpoint makes that resume the judged one, and it suppresses the planned kill (`not ev.resumed`), so no later resume can supply the window. With `--trace-a-early` the old hard failure "early window cannot be checked" then stopped a healthy run. The running gate is not where the early window is read; the probe's P1b is. Ruling: option (a).

What `trace_a` does now, with the opt-in key `resume_early_abs` set and the judged resume having fewer than 3 redone updates (k = 1 or 2):
- the early window is NOT computed and NOT a failure: `r['resume']['early_window'] = {'computed': False, 'redone': k, 'deferred_to': 'probe P1b'}`; no `early_max` is written (nor anything else with a window value);
- the verdict is decided by the other items exactly as before: `resume_first_diff` (0.01), the exact fields, `resume_mean_abs`, `resume_max_abs`, the loss, the peak. A first-update gap above 0.01 or an exact-field mismatch still FAILs and stops the run;
- this line is printed verbatim in the TRACE-A md (`TRACE-A-<job>.md`), in `status.md` (under the trace A line) and in the finish message (the `DONE-<job>.txt` file and the `DONE` line of `supervisor.log`): `early window not checked by the running gate; do not read this result until the probe's P1b passes.` (constant `EARLY_DEFERRED` in the supervisor). The deferral is also kept in `state.json` under `jobs.<job>.traceA.early_window`, only when deferred, so `status.md` and the finish message can read it;
- with 3 or more redone updates nothing changes: the window is computed, `early_max` is recorded, and `early_max > 0.005` (`EARLY_LIMIT`) is a hard FAIL that stops the run. With the opt-in key set a computed window also records `early_window = {'computed': True, 'steps': [..]}` beside `early_max` (new, optional; no deferral line is printed).
Without the opt-in keys the result is the original pack function's as before (plus `early_max` where it was already recorded; no `early_window` key). Unchanged: 0.005, 0.01, the exact fields, probe P1b, `rejudge_probe.py` (its `git diff` across the B2 commit is empty), the planned-kill rule. The stop message of a run that fails for another reason does not carry the deferral line; the TRACE-A md of that run does.

Consequence to know: a deferred run PASSes trace A, so the supervisor goes on to the end and the baseline starts; the result of that run must not be read until the probe's P1b passes (the line says so in three places).

Tests (2 new in `tests/test_gatefix.py`, 36 after B2; three older ones changed from "hard failure" to "deferred": `t_trace_a_early_optin`, `t_trace_a_early_needs_three`, `t_early_not_computable_trace_a`): `t_b2_deferral_unit` (trace_a / md_trace_a with 1 and 2 redone updates and the full early rules: PASS, `early_window` deferred, no `early_max`, the verbatim line once in the md; first-update gap > 0.01 and an exact-field mismatch still FAIL; 3 or more redone updates: computed, 0.004 PASS, 0.006 FAIL), `t_b2_running_gate` (the supervisor against the fake runner with the early rules: unplanned crash at update 102 and at 103, i.e. 1 and 2 updates after the save at 100, before the planned kill: not stopped, trace A PASS, the line in the TRACE-A md, `status.md`, `DONE-g2fa4.txt` and `supervisor.log`, the string `early_max` in no file of the state folder; the same two crashes with `--seg2-offset 0.02` (first-update gap) or `--seg2-lr 0.002` (exact-field mismatch): FAIL and stopped; a planned resume with `--seg2-offset 0.007`: `early_max` 0.007 FAILs and stops; a healthy planned resume PASSes with the window computed and no deferral line). The end-to-end test was checked to fail on the previous supervisor (it stops the healthy 102 run with "early window cannot be checked: only 1 redone update").

## Ruling B3 (coordinator): a window that is not contiguous is "not computable"; a missing first redone update fails closed

Why (review verdict B3): the early window was `common[1:3]` of the step intersection with nothing checking that `common[0] = rstep+1` and `common[1:3] = [rstep+2, rstep+3]` (rstep = the resumed step, common = the redone steps present in both segments). A hole in a train line shifted both the "first redone update" and the early window, and the message still named them as the defined updates. The probe checks contiguity; trace A now does too.

What `trace_a` does now:
1. **Early window.** It is computed (and `early_max` recorded, rule or not) only when `common[:3] == [rstep+1, rstep+2, rstep+3]`. Otherwise `early_max` is NOT recorded. With `resume_early_abs` set that is the B2 deferral, not a failure: `early_window = {'computed': False, 'redone': len(common), 'deferred_to': 'probe P1b'}` plus, when 3 or more updates were redone (a gap at rstep+2 or rstep+3), `'reason'` naming the steps ("the 2nd and 3rd redone updates after the restore at 100 must be updates 102 and 103, contiguous after update 101; the redone updates start [101, 103, 104, 105]"). The verbatim B2 line is printed in the TRACE-A md, `status.md` and the finish message; the reason is in the `resume` record the md prints. Without `resume_early_abs` there is no `early_window` key and nothing is printed. A hole beyond the window (update 104 or later) changes nothing.
2. **Missing rstep+1 (first redone update): a hard failure, in the opt-in variant only.** If `common[0] != rstep+1` and `resume_early_abs` and/or `resume_exact_fields` is present (the `--trace-a-early` variant), `why_fail` gets "the first redone update <rstep+1> (the first update after the restore at <rstep>) is missing from <the earlier segment | the resumed segment | the earlier segment and the resumed segment>; the first redone update present is <common[0]>: the first-update check cannot be computed as defined". It is hard (never released by `rules.soft`; it is the restore detector). `r['resume']['first_diff']` is then `None` (the first-update bar and the exact fields are not run on another update, which would be a check on the wrong step), and the early window is deferred as above. The other items (mean, max, loss, peak) still judge.
3. **Without the opt-in keys (coordinator correction)** the missing-rstep+1 failure does NOT apply: `trace_a` stays what it was, the original pack function's result (the existing equality tests against the original function keep passing). The only difference to the original is the always-recorded `early_max`, which is now also not recorded for a non-contiguous window.

Unchanged: 0.005, 0.01, the exact fields on a present first update, P1b, `rejudge_probe.py` (its `git diff` across the B3 commit is empty), the planned-kill rule.

Tests (2 new in `tests/test_gatefix.py`, 38 in all): `t_b3_contiguity_unit` (update 101 missing from the resumed segment, the earlier one or both, with `resume_early_abs`, with both opt-in keys, with `resume_exact_fields` alone, and with every soft list: FAIL, one exact message, `first_diff` None, no `early_max`; no opt-in key: the result equals the original function's, PASS; update 104 missing: named; a gap at 102 or at 103, in either segment: PASS, deferral with the reason, no `early_max`, the verbatim line in the md, the exact fields still compared, a first-update gap still FAILs; a gap at 104 or 110 and a contiguous trace: computed as before; two redone updates with a gap: plain B2 deferral), `t_b3_running_gate` (fake runner with `--skip-log-seg2-at`: update 101 not logged by the resumed segment after an unplanned crash at 103 and after the planned kill: FAIL and stopped; update 102 or 103 not logged after the planned kill: PASS, deferral in the TRACE-A md, `status.md`, `DONE-g2fa4.txt` and `supervisor.log`, `early_max` in no file).
