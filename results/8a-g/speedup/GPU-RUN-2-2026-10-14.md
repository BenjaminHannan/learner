# Speed study, second GPU run: bigger micro-batches (rented RTX 4090, 10-14 6:13 to 8:33 AM ET)

Marks were fixed before the run in `PREREG-b3g2-accum.md`; its Result log 1 has the unedited table. Raw outputs: `gpu-run-2/`. Cost about $1.06 (2.33 h at $0.456/h all-in, computed; the account credit fell $1.31 over the same hours because another thread's box was running), box destroyed, my instance not listed.

## Plain version
- **G2f and every B3G2 job are slow because the GPU waits for the CPU.** The model does about 505 small steps per update (32 micro-batches of 8 rows, about 16 thinker rounds each). Giving each step more rows leaves the number of rounds almost unchanged, so the same update needs far fewer steps.
- **Measured on one 4090, same box for all rows (B3G2 3M):** accum 32 (today's G2f) 11.57 s per update; accum 16 5.95 s (1.9x); accum 8 3.18 s (3.6x); accum 4 2.12 s (**5.5x**, peak memory 8.8 GB). All pass the three marks I fixed first.
- **Same maths as far as one update shows:** with the loop length pinned the gradient points the same way (cosine 0.9999999 in fp32, 0.999998 in bf16). What is not shown: the loop length is drawn once per micro-batch, so a smaller accum means fewer independent draws per update; its effect over a whole training run is untested. So this is a new recipe and gets a new name, never "G2f".
- **AT-1 (the agent-turn model):** 26.2 s per update at accum 32 (2.26x B3G2) and **5.7 s at accum 4** (4.6x faster). Early losses at steps 20 to 80 are close between the two accums (5.28 vs 5.31, 4.42 vs 4.45, 3.70 vs 3.70, 3.09 vs 3.15; one seed, not a test).
