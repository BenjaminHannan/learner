## What is measured (one rented RTX 4090, one session)

Free-running seconds per update, median over at least 40 timed updates after 10 warm-up, **3 interleaved rounds (A, B, A, B, A, B)** so box drift cancels; peak allocated GB; mean thinker rounds per micro-batch. Reference **A = accum 4** (the recipe G2f-a4 runs on the PC).

| group | arms (each run against A in the same box) |
|---|---|
| accum rows | accum 8, accum 16; accum 2 as a timing-only extra (128 rows per micro-batch, about 17 GB: fits a 4090, NOT the PC's 16 GB card; reported, never recommended) |
| cheap wins, ONE change on top of accum 4, never combined | `tf32` (matmul + cudnn TF32 on); `pad64` (the padded width of the per-micro-batch inputs rounded up to a multiple of 64 instead of the batch's widest); `unfused` (AdamW with fused=False: the train.py of G2f-a4 already uses fused AdamW on CUDA, so this is a control that measures what the fused optimizer is already worth, not a new win); `nosync` (the biggest host-device syncs per round removed where the same values are already on the CPU: `writer.py:138`, `b3g2.py:350`, `writer.py:121` in the profile of 10-14 AM; the exact sites are re-measured first with the harness's `syncs` section at accum 4) |

All variants live in the harness (monkeypatch or a patched copy of the tree on the box). **Nothing under the PC's `src-b3g2`, `G2f-a4`'s queue or its code is touched.**

## Marks (fixed now, not changed after seeing numbers)
**Accum rows** (this morning's marks, unchanged except that the reference is now accum 4):
1. Speed counts only if the median s/update is at least 1.3 times lower than the reference.
2. Memory fits only if peak allocated is at most 10 GB.
3. Prediction (suggested, untested): **neither accum 8 nor accum 16 passes mark 1 against accum 4** (this morning's ratios: 0.67x and 0.36x). It is proved wrong if either one is at least 1.3x faster than accum 4. Accum 2 is a free extra with the same mark 1; it needs more than 10 GB, so it fails mark 2 by design on the PC's card.
4. If the mean thinker rounds per micro-batch rise by more than 25 % against the reference, the speed is reported together with that rise.

**Cheap wins** (paired against A, same box, interleaved):
5. A win **counts** only if all three rounds have B below A, the median of B is at least 5 % lower than the median of A (speed at least 1.05x), peak allocated is at most 10 GB, and mark 6 holds.
6. **Same maths** (the equivalence check, one update on the same 256 rows with the loop length K and the stochastic parts pinned, as `accumcmp` does): relative loss difference at most 1e-4 and gradient cosine at least 0.9999 in bf16 autocast, beside the harness's own rerun noise floor; for `pad64`, `nosync` and `unfused` also bit-exact on CPU in fp32 where the CPU can run the change (stated if it cannot). A variant that fails mark 6 is reported as NOT EXACT, and its speed is not a recommendation. `tf32` is allowed to differ in the last bits (it changes the fp32 islands only); it has to meet the same 1e-4 / 0.9999 bar.
7. **Noise floor**: A's three round medians are reported with their spread (largest / smallest). A difference smaller than twice that spread is "inside noise" whatever its sign; below 2 % it is "does nothing"; 2 % to 5 % is "small, reported, not recommended".
8. Predictions (suggested, untested): `tf32` changes the speed by under 2 % (bf16 autocast already puts nearly every matmul in bf16): **proved wrong if it counts under mark 5**. `unfused` is at least 2 % slower than A (fused is already on): proved wrong if it is faster or equal within noise. `pad64` under 3 %: proved wrong if it counts under mark 5. `nosync` at least 5 % faster (the GPU idled 79 % of the time at accum 32; its busy share at accum 4 is measured first with the harness's `profiler` section and printed beside the table): proved wrong if it comes in below 2 %.

## Amendment 1 (10-14 about 5:55 PM ET; written BEFORE any run of this sweep; the original marks above stay as written)
The builder's CPU check found that `pad64` is not bit-identical in the gradient in fp32 (relative difference about 1e-8): zero-padding lengthens the reductions, and floating-point sums change in the last bits when terms are added in a different grouping. Mark 6's wording "bit-exact on CPU in fp32" was over-strict for `pad64` (my error in the specification, not a property of the variant). Reading used for `pad64` only: mark 6's bf16 bar (relative loss difference at most 1e-4, gradient cosine at least 0.9999) stays, and the fp32 CPU check becomes "equal to rounding: relative gradient difference at most 1e-6 and a loss difference at most 1e-6 relative". `nosync` and `unfused` keep the bit-exact requirement on CPU fp32 (`nosync` reads the same values from the CPU; `unfused` only changes the optimizer kernel; an optimizer-kernel change is checked on the GPU by the bf16 bar, since fused and unfused AdamW round differently, CPU has no fused kernel). The CPU checks are the builder's tests on a tiny config; the rental cannot repeat them (`bit_exact_cpu_fp32` is None on a GPU box), so on the rental only the bf16 bar is checked.

## Amendment 2 (10-14 about 6:30 PM ET; written BEFORE any run of this sweep; the original marks and Amendment 1 stay as written)
An independent review of the harness and box plan (done before renting) found places where the code and plan did not match the text above. Fixes are in the code; nothing below changes a mark or a threshold.
1. **Arm order.** The A/B arms run in this order: `nosync`, `pad64p`, `pad64`, `tf32`, `unfused`, THEN accum 8, accum 16, accum 2 (the cheap wins first, so a time cap can only cut the accum rows, which were already timed this morning). Each arm is compared with an accum-4 reference measured in the same round (A,B,A,B,A,B).
2. **New arm `pad64p`.** `pad64` as written above ("the padded width of the per-micro-batch inputs rounded up") changes three widths at once: the prompt width, the Gemma input width and the tape width. Only the prompt width is the "per-micro-batch input" of the first reading, and the other two were already exact, so rounding them up adds work. `pad64p` rounds up ONLY the prompt width; `pad64` stays as defined (all three). Both are reported, each with its own mark 6 check. No prediction is registered for `pad64p`; the `pad64` prediction (under 3 %) stands.
3. **Mark 6 on the rental.** On a GPU box the CPU fp32 check cannot be repeated, so mark 6 there is evaluated on the bf16 bar only (relative loss difference at most 1e-4, gradient cosine at least 0.9999, beside the rerun noise floor) and is labelled `bf16_bar_only`, with the sentence "CPU fp32 exactness is checked by test_prof.py off the box (Amendment 1)". The CPU checks (Amendment 1 thresholds: `pad64`/`pad64p` equal to rounding, `nosync` bit-exact) are the unit tests in `results/8a-g/speedup/prof/test_prof.py`, which I run before the rental and quote in the results. A variant whose bf16 bar fails is NOT EXACT and mark 5 cannot count it.
4. **Mark 5 reading.** "At least 5 % lower" is applied as median B at most 0.95 times median A, slightly stricter than speed at least 1.05x (which would allow B at most 0.9524 A). An arm that completes fewer than 3 rounds is reported "incomplete, cannot count".
5. **Package tree.** The harness runs on the PTC assembly of custom_io (`--pkg-root`: commit 74d6e92c75 plus the PTC overlay), not the PC's src-b3g2 named in the measurement section. This morning's sweep used the same tree and A and B match inside the same box; the PTC overlay's file list (capcount.py, plain_tf_steps.py, plain_lm.py, configs.py, job.py, test_ptc.py) does not include b3g2.py or writer.py, so the B3G2 model code is the PC's (suggested, not diffed byte for byte). The new accum-4-versus-32 pair stage (below) does use the PC's own src-b3g2 files and the pack's queue lines.
6. **Profiler share.** Mark 8's busy share at accum 4 comes from the harness's `profiler` section (2 profiled updates; profiler overhead inflates the wall time, so the share is a lower bound), printed beside the table.
7. **Added stage (not a mark of this sweep): accum 4 against accum 32 on the same card.** The same rental runs B3G2 3M seed 400 for 300 updates at accum 4 and then at accum 32 with the pack's own commands (unmodified train.py, no checkpoint overlay, `--log-every 1`), each stopped by the box at update 300; loss traces are compared offline afterwards by the rule in `TRACE-A-READING-2026-10-14.md` (gate 3). It is the only part of this rental that is not a speed measurement.
8. **Money.** Box timeouts: smoke 50 updates, profile 20 min, equivalence 20 min, bench 125 min (no new arm after minute 100), pair 25 + 80 min, all inside MAXH 5.5 h. The box refuses to start without the offer's hourly price and refuses MAXH x price above $3.00. Expected total about $1.9 at $0.43/h; worst case about $2.4.

## Amendment 4 (10-14 about 10:35 PM ET [date corrected from "10-15", a typo]; written AFTER reading boxes 1 and 2 and BEFORE box 3 exists; marks unchanged)
1. **What happened on box 1 (read from its `chunk_values` and wall times; shown).** For about 65 minutes of the 113-minute bench every run took about 2.5 times longer than before and after: A medians 5.49 s/update instead of 2.22 (arms `nosync` round 3, all of `pad64p`, all of `pad64`, `tf32` rounds 1 and 2); then the box went back to 2.22 s/update by itself. Inside the slow stretch A and B were each stable (A spread 1.001 to 1.003), so the ratios there are real measurements of a slow host, not noise, but they say nothing about the normal speed. Fast-stretch pairs: `nosync` rounds 1 and 2, `tf32` round 3, and all of `unfused`. Box 2 (a different host) ran fast the whole time (A 2.22 to 2.24).
2. **What this does to the registered marks.** The marks are applied as written. The harness (which cannot know about regimes) printed `pad64p` as "counts under mark 5" from slow-stretch data only; that print is not a recommendation. Rule fixed now: a cheap-win arm is read only from rounds whose A median lies within 10 % of the arm's fastest A round (the "normal speed" regime); an arm with fewer than 3 such rounds is reported "regime-confounded, repeated" and its mark 5 is decided by the repeat. Arms read from box 1 as they stand: `unfused` (3 of 3 fast rounds). Arms repeated: `nosync`, `pad64p`, `pad64`, `tf32`.
3. **Box 3 (one more 4090, same plan, short).** `PROF_AB_VARIANTS=nosync,pad64p,pad64,tf32`, no accum rows (box 2 has them), 3 rounds, same warm-up and update counts. New this time: a host monitor writes GPU clocks, power, temperature, throttle reasons, load and CPU steal every 10 seconds, so a slow stretch can be explained (suggested cause of the slow stretch on box 1: CPU or GPU throttling or a busy neighbour on the host; untested). If box 3 also has a slow stretch, only its fast-stretch rounds are read, by the same rule, and the arm stays open if fewer than 3 remain.
4. **Gate-3 compare and two controls on box 3.** The registered compare (accum 4 against accum 32, 300 updates, big-run's rule) ran on box 1 in its fast stretch and is reported by its own rule, unedited. Box 3 adds two 300-update control runs with the pack's own command, each alone on the card: accum 8 (seed 400) and accum 4 with seed 401. They are not part of any registered gate; they are for reading the compare: (a) how far accum 4 moves just from a different seed (the noise the compare's thresholds sit on), (b) how accum 8 stands against the box-1 accum-32 curve (the registered fallback's first step; a different host from box 1, said so). Nothing from them changes the gate-3 verdict.

## Amendment 5 (10-14 about 11:20 PM ET; written while box 3 is still running and BEFORE any result file of it was read; marks unchanged)
Amendment 4 point 2 says a round is read if its A median lies within 10 % of "the arm's fastest A round". That wording has a hole: an arm that ran entirely inside a slow stretch (box 1: `pad64p`, `pad64`, A 5.5 s/update in all three rounds) would count as normal against its own fastest round. What was meant, and what Amendment 4 point 1 already did by hand for box 1, is the fastest A round of the same box over ALL arms. Rule as it stands from now: **the reference is the fastest A round on the same box over all arms (box 1: 2.215 s/update; box 3: read from its own file); a round is "normal speed" if its A median is at most 10 % above that reference; an arm needs 3 normal-speed rounds to be decided, otherwise it stays "regime-confounded".** For box 1 this gives exactly the classification of Amendment 4 point 1 (unchanged by this amendment). Accum rows and the controls are not read through this rule. All dollar figures: wall time x the billed rate $0.4563/h.
