# Attack A, the deferred batched writer: CPU results (2026-10-16)

Variant `defer` (`launch/defer.py`), runner `launch/prof_launch.py`, tests `launch/test_defer.py` (log: `launch/test_defer.log`).
Trainer code: `custom_io` at 74d6e92c75, the exact code of the PC mainline 8aB3G2A4 and of GPU-RUN-3. Nothing outside `launch/` was edited. torch 2.11.0+cpu, fp32, stub Gemma, synthetic rows, no GPU.

Labels: **shown** = I ran it and the number is in `test_defer.log`; **suggested** = arithmetic or reasoning on shown numbers plus the GPU-RUN-3 record; **untested** = nothing here can say.

## 1. What the variant does, and the numerics label

In teacher-forced training the writer feeds nothing back into the thinker (which tape entries are visible comes from the schedule; Z_t depends on the thinker only; the G2f writer reads Z alone). So the original per-round work

- a `call_pass` on a row subset every round t >= 1 (12 host-sync call sites a round: 3 `.tolist()`, `torch.tensor(sel, device=)`, `ok.tolist()`, `call.nonzero()`, and `answer_teacher`'s 2 `.cpu()` and 4 blocking `.to(dev)`), and
- an `ans_pass` every round (3 more sites a round: `ok.any()`, `ok.nonzero()`, `bool(ok.all())`; a gradient checkpoint from round 8)

becomes one thinker-only loop, then ONE batched call pass over all (round, row) call/EOS pairs and ONE batched answer pass over all (round, row) answer pairs. Every host list (who calls when, who has a target, who may answer, `int(last.max())`) comes from the numpy schedule that `plan()` builds. Targets are built once with numpy (equal to `ByteWriter.teacher`'s for the empty context). All host arrays go over in one packed int64 copy (pinned + non_blocking on CUDA, plain on CPU). The call loss is summed in the original round order. The hit counters come from one `.tolist()` at the end. Used only in training with autograd on, `talk_rounds == 'last'`, writer `copy` False; eval, `no_grad`, `rec=True` (`call_evals`), `talk_rounds='all'`, free run and `talk` run the untouched original methods (`defer` replaces only the instance attribute `_loss` and adds `_defer_plan`; `loop` is not touched).

**NUMERICS-CHANGING ('near').** The per-row maths is the same, the floating-point rounding is not: batched GEMMs, a longer padded call width (all pairs are padded to the longest call in the micro-batch, 16 here), and one-shot parameter-gradient reductions. The thinker is bit-identical (shown, every Z_t compared). The label is in the docstrings, in `stats()['defer']['numerics']`, and here. It is NOT a "same maths bit for bit" arm like `nosync`.

### T3: coverage (shown; all pass the T1 marks)

Nine scenarios, baseline vs defer each: K = 4 (n = 7); K = 32 (n = 32, so rounds past CKPT_FROM = 8 and past n_loops = 12); a 4-row micro-batch (K 16); gap_p = 1 (every call row gapped); ans_drill = 1; both at K 32; only rows with calls; only rows without calls (EOS-only targets every round); writer cap 7 (calls and answers over the cap get no target: 16 over-cap targets). Reached over the nine: 104 full-row and 22 subset call passes, 155 full and 41 subset answer passes (counted in the baseline), 24 gapped rows, 27 drilled rows, 58 no-call rows. Loss rel diff 0 in all nine (8.5e-08 in the forced n = 3 case below), grad cosine 1.000000000, grad rel L2 7e-08 to 1e-07 in every scenario.

The "last round has no ok rows (share None)" case is **not constructible through `_loss`**: n = max(K, last+2) makes round n-1 an ok round for every row, so `share` is never None (shown by a 200-case property test on the answer-pair rule). It is reachable only with a forced short n. The variant has a test-only `n_override`, the original `_loss` is rebuilt with the same edit by `patched_fn`, and both are run for n = 2, 3 (share None, no answer pair at all) and n = 4, 5 (share 0.0): identical in both arms (shown). I also added the guard that skips the answer pass when there are no answer pairs.

### T5: counts per micro-batch, forward + backward (shown, CPU)

### T6: teardown (shown)

`setup()` adds exactly `_loss` and `_defer_plan` to the instance dict; `teardown()` leaves the instance dict identical (every key, identity of every value) and the class methods untouched; idempotent; after `Trainer.close()` with `nosync`, `pad64p`, `pad64` composed the instance dict has the keys of a fresh model. A setup refused for a changed source hash or for a plain arm raises `Skip` and leaves nothing behind. `defer + nosync` gives a loss and gradient bit-equal to `defer` alone (nosync only changes the original paths).

### T8: the runner (shown)

`python prof_launch.py --arm B3G2 --tiny --data synthetic --eg stub --device cpu --sections abequiv --ab-variants defer ...` completes. Mark 6 on the tiny CPU: relative loss diff 0, grad cosine 1.000000000000, relative L2 7.4e-08, step cosine 0.99999999997, bit-exact False, verdict holds, label `bar_only_by_rule`; the harness's own rerun floor is bit-exact. CPU rule chosen: `AB_CPU_RULE['defer'] = 'bar_only'`. The arm is numerics-changing by construction, so `bit_exact` is false; `equal_to_rounding` (relative gradient and loss difference <= 1e-6) is a claim about CPU rounding that these tests do measure (7e-08 to 1e-07 here, so it would hold at the tiny and the real shape on the CPU) but that says nothing about bf16 on the GPU, where the bar (loss rel diff <= 1e-4, grad cosine >= 0.9999) is the real test. So the registered rule is the bar alone, and the CPU numbers are shown beside it. `prof_launch.py` also imports `exact_arms.NEW_VARIANTS` if `exact_arms.py` sits in `launch/` (tested with a fake file, a missing file and a broken file) and registers each class: `SETUP_ORDER` after `nosync`, `AB_ARM_ORDER` after `unfused`, `AB_CPU_RULE` from the class's `ab_cpu_rule` (default `bar_only`).

## 3. Expected effect on CUDA syncs per round (suggested, from shown counts and the GPU-RUN-3 record)

Per round the original writer path makes about 14.8 call sites that wait on a GPU (12 in the call round, 3 in the answer round, plus 9 once): each `.tolist()`, `.item()`, `bool(tensor)`, `.nonzero()` and `.cpu()` is a device-to-host copy followed by a stream wait, and each pageable `.to(cuda)` / `torch.tensor(list, device=cuda)` is a stream-ordered blocking copy. `defer` has 1 per micro-batch, so about 0.06 a round at n = 16 and falling with n.

Against GPU-RUN-3 (RTX 4090, accum 4, 17.28 rounds a micro-batch, 1,305 cudaStreamSynchronize and 745 DtoH copies an update):

- stream syncs from this path: 12 x 16.28 + 3 x 17.28 + 9 = 256 per micro-batch, about 1,025 of the 1,305 an update (78 %). After: 1 per micro-batch, so about 285 an update (-78 %). The other ~70 a micro-batch are from code `defer` does not touch (reader, tape, Gemma front); the CPU run cannot size those on the real front.
- DtoH copies: 7 x 16.28 + 3 x 17.28 + 3 = 169 per micro-batch, about 675 of 745 (91 %). After: about 75 an update (-90 %).
- ATen device ops per micro-batch: 8,502 to 3,346 (-61 %) at the real shape. If kernel launches fall in the same proportion (they need not: some ops are several kernels), the 75,966 launches an update would fall to roughly 30,000 to 35,000. The optimizer and Gemma front are in the update's count but not in my micro-batch count, so the true remainder is somewhat higher.
- Time: the unprofiled 2.24 s an update against 1.415 s of real kernel time. With the writer's waits gone the CPU can run ahead, so the update should approach the larger of the kernel time and the remaining launch time. A guess is 1.5 to 1.7 s an update (1.3x to 1.5x), with 1.58x (2.24 / 1.415) as a ceiling unless the kernels themselves get faster. This is a prediction, not a measurement; the cost side is that the batched call pass runs every pair at width 16 where the original ran EOS-only rounds at width 1 (about 3x the writer positions: 941 x 16 = 15k against roughly 5k, my estimate, not measured; tiny kernels, but real).

## 4. Where the spec was wrong or impossible

- "Share None when the last round has no ok rows, if constructible": not constructible through `_loss` (n >= last + 2). Reached only by forcing n; handled and tested that way (section T3).
- "~10 host syncs a round": the counted figure is 12 in the call round plus 3 in the answer round, 14.8 averaged over the micro-batch.
- Spec e) asks for `cnt = cnt + ok_t.float()` and `acc = acc + zeros(B).index_add(...)` in round order. I send `cnt` as exact integer counts in the pack (a sum of 0/1 floats up to 34 is exact in any order) and use `acc.index_add(0, rows, nll)` (acc[i] + nll equals acc[i] + (0 + nll) bit for bit). Same values, fewer kernels; the loss order for `lcall` and the order of the `acc` rounds are the original's.
- The answer teacher is built on the numpy fast path too (not `answer_teacher`), tensors equal to `ByteWriter.teacher`'s (asserted, including None, [] and over-cap rows). `fb` is not built: it is all zero and unused with `copy=False`.
- The spec's "g is not None, rec False, lesion None" cannot occur inside `_loss`; those cases are the untouched `loop` and are bitwise the original. The guard that matters is `training and grad enabled and talk_rounds == 'last' and not writer.copy`.
- Added without being asked: a source-hash guard (a sha1 of each original method this file re-implements; a different source makes `setup()` raise `Skip`, like `patched_fn`), `n_override` for tests, a skip of the answer pass when there is no answer pair.
- A bit-equality test between two arms needs one CPU thread: with 2 threads even baseline against baseline can differ in the last bit. `test_defer.py` runs on 1 thread except the real-shape test.
