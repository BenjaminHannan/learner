## 1. What the variant does, and the numerics label

In teacher-forced training the writer feeds nothing back into the thinker (which tape entries are visible comes from the schedule; Z_t depends on the thinker only; the G2f writer reads Z alone). So the original per-round work

- a `call_pass` on a row subset every round t >= 1 (12 host-sync call sites a round: 3 `.tolist()`, `torch.tensor(sel, device=)`, `ok.tolist()`, `call.nonzero()`, and `answer_teacher`'s 2 `.cpu()` and 4 blocking `.to(dev)`), and
- an `ans_pass` every round (3 more sites a round: `ok.any()`, `ok.nonzero()`, `bool(ok.all())`; a gradient checkpoint from round 8)

becomes one thinker-only loop, then batched passes over all (round, row) pairs: the call pass in TWO buckets (the pairs that write a call, padded to the longest call of the micro-batch, and the EOS-only pairs of rows past their last call, width 1, put back into round order by a permutation before the loss is summed) and the answer pass in TWO parts (rounds < 8 as one pass, rounds >= 8 as one gradient-checkpointed pass, as the original checkpoints those rounds). Every host list (who calls when, who has a target, who may answer, `int(last.max())`) comes from the numpy schedule that `plan()` builds. Targets are built once with numpy (equal to `ByteWriter.teacher`'s for the empty context). All host arrays go over in one packed int64 copy (pinned + non_blocking on CUDA, plain on CPU). The call loss is summed in the original round order. The hit counters come from one `.tolist()` at the end. Used only in training with autograd on, `talk_rounds == 'last'`, writer `copy` False; eval, `no_grad`, `rec=True` (`call_evals`), `talk_rounds='all'`, free run and `talk` run the untouched original methods (`defer` replaces only the instance attribute `_loss` and adds `_defer_plan`; `loop` is not touched).

**NUMERICS-CHANGING ('near').** The per-row maths is the same, the floating-point rounding is not: batched GEMMs, a longer padded call width (every call-writing pair is padded to the longest call in the micro-batch, 16 here; EOS-only pairs are width 1), and one-shot parameter-gradient reductions. The thinker is bit-identical (shown, every Z_t compared). The label is in the docstrings, in `stats()['defer']['numerics']`, and here. It is NOT a "same maths bit for bit" arm like `nosync`.

### T4: fallbacks (shown)

Eval-mode loss, training-mode `no_grad` loss and `talk_rounds='all'` loss plus gradient are the real fallbacks (they enter defer's `_loss` and go back to the original): bitwise identical to the original model's (`torch.equal` on every tensor, equality on every record), counted as 3 fallback losses and 0 deferred. `applicable()` is False for each condition separately. Two further checks, `loop(rec=True)` (the `call_evals` path) and a free run (`run`, `talk`, `loops:3`, `generate`), are **not fallbacks**: defer replaces neither method, so they compare the original methods with themselves and only show that `setup()` left them alone (the test labels them UNTOUCHED; review defect 10). New: the fallback is the `_loss` the instance had when defer was set up, not the class's (a wrapper set before defer is called on the eval path and is put back by `teardown()`; review defect 8). A variant that wraps `_loss` and is set up before defer therefore only ever sees the fallback paths: on the deferred path defer replaces the whole loss.

## 3. Expected effect on CUDA syncs per round (suggested, from shown counts and the GPU-RUN-3 record)

Per round the original writer path makes about 14.8 call sites that wait on a GPU (12 in the call round, 3 in the answer round, plus 9 once): each `.tolist()`, `.item()`, `bool(tensor)`, `.nonzero()` and `.cpu()` is a device-to-host copy followed by a stream wait, and each pageable `.to(cuda)` / `torch.tensor(list, device=cuda)` is a stream-ordered blocking copy. `defer` has 1 per micro-batch, so about 0.06 a round at n = 16 and falling with n.

Against GPU-RUN-3 (RTX 4090, accum 4, 17.28 rounds a micro-batch, 1,305 cudaStreamSynchronize and 745 DtoH copies an update):

- stream syncs from this path: 12 x 16.28 + 3 x 17.28 + 9 = 256 per micro-batch, about 1,025 of the 1,305 an update (78 %). After: 1 per micro-batch, so about 285 an update (-78 %). The other ~70 a micro-batch are from code `defer` does not touch (reader, tape, Gemma front); the CPU run cannot size those on the real front.
- DtoH copies: 7 x 16.28 + 3 x 17.28 + 3 = 169 per micro-batch, about 675 of 745 (91 %). After: about 75 an update (-90 %).
- ATen device ops per micro-batch: 8,502 to 3,705 (-56 %) at the real shape (shown). Turning that into launches needs the share of the 75,966 launches that sit in the counted code, and the counts cannot give it (review defect 7). The counted ops are from the STUB Gemma; GPU-RUN-3's 75,966 launches are about 19,000 a micro-batch against 8,502 counted ops, and they include the real Gemma front, the reader, the optimizer and the backward kernels of ops that are several kernels. Let f be the share of launches in the counted code. After = 75,966 x (1 - f + 0.436 f). With f = 1 (every counted op one launch, nothing outside it) that is about 33,000; with f = 0.45 (4 x 8,502 = 34,000 counted ops against 75,966 launches, one launch per op, the rest outside) about 57,000. So a launch count between roughly 33,000 and 57,000 is what this arithmetic allows, and the first version's "30,000 to 35,000" was the optimistic end of it. Suggested only; the profiler run on the box gives the number.
- Time: the unprofiled 2.24 s an update against 1.415 s of real kernel time. With the writer's waits gone the CPU can run ahead, so the update should approach the larger of the kernel time and the remaining launch time. A guess is 1.5 to 1.7 s an update (1.3x to 1.5x), with 1.58x (2.24 / 1.415) as a ceiling unless the kernels themselves get faster. This is a prediction, not a measurement; the first version's cost side (every call pair at width 16, about 3x the writer positions) is gone: the EOS-only pairs now run at width 1, so the call positions per micro-batch are 68 x 16 + 873 x 1 = about 2,000 here (synthetic rows; counted from the pair counts, not measured as time), close to the original's. The price of the memory fix is the extra ops above and one recompute of the checkpointed answer part in backward.

## 4. Where the spec was wrong or impossible

- "Share None when the last round has no ok rows, if constructible": not constructible through `_loss` (n >= last + 2). Reached only by forcing n; handled and tested that way (section T3).
- "~10 host syncs a round": the counted figure is 12 in the call round plus 3 in the answer round, 14.8 averaged over the micro-batch.
- Spec e) asks for `cnt = cnt + ok_t.float()` and `acc = acc + zeros(B).index_add(...)` in round order. I send `cnt` as exact integer counts in the pack (a sum of 0/1 floats up to 34 is exact in any order) and use `acc.index_add(0, rows, nll)` (acc[i] + nll equals acc[i] + (0 + nll) bit for bit). Same values, fewer kernels; the loss order for `lcall` and the order of the `acc` rounds are the original's.
- The answer teacher is built on the numpy fast path too (not `answer_teacher`), tensors equal to `ByteWriter.teacher`'s (asserted, including None, [] and over-cap rows). `fb` is not built: it is all zero and unused with `copy=False`.
- The spec's "g is not None, rec False, lesion None" cannot occur inside `_loss`; those cases are the untouched `loop` and are bitwise the original. The guard that matters is `training and grad enabled and talk_rounds == 'last' and not writer.copy`.
- Added without being asked: a source-hash guard (a sha1 of each original method this file re-implements; a different source makes `setup()` raise `Skip`, like `patched_fn`), `n_override` for tests, a skip of the answer pass when there is no answer pair, the call buckets and the checkpointed answer part (memory).
- A bit-equality test between two arms needs one CPU thread: with 2 threads even baseline against baseline can differ in the last bit. `test_defer.py` runs on 1 thread except the real-shape test.
