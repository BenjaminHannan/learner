# Speed study, first GPU run (rented RTX 4090, 10-14 1:36 to 3:00 AM ET)

Ben asked at 9:47 PM ET 10-13: "profile where the run time actually goes and find speedups where you can." Marks were fixed before any GPU number in `PREREG-eg-once.md`; the line-by-line results are its Result log 3. Raw outputs: `gpu-run-1/`. Cost about $0.70 (credit $50.21 to $49.51), box destroyed, 0 instances listed.

## Plain version
- **Plain arms (PTS / PTC, accum 16): the frozen Gemma reader is the cost.** It is 79 % of an update on the 4090 (75 % on the PC). The reader is called 16 times per update with 16 different rows each, so most of its time is call overhead. Running it once per update on all 256 rows (`eg_once`) made updates **1.8x faster** (1.5x to 2.2x depending on which baseline round you compare to).
- **But it failed its own accuracy gate (E1), so it is not adopted.** Its reader vectors differ slightly from the old path in a few places (119 of about 45,000 positions below the registered cosine 0.998). Changing only the micro-batch size of the old path already makes 205 positions fail that rule, so my rule was too strict for bf16, but the rule tied to the old path's own spread also fails (2.2x against 1.5x allowed). The 300-update loss trace and the loss/gradient check pass. A different rule would be decided after seeing these numbers, so it needs big-run's four conditions and fresh rows.
- **B3G2 (G2f) is a different animal.** Gemma is only 22 % of an update, and `eg_once` gives 1.09x (fails the 1.3x mark). One update takes 7.2 s on the 4090 (12.1 s on the PC). Forward 56 %, backward 43 %; the model makes about 505 small sequential passes per update (32 micro-batches of 8 rows, about 16 thinker rounds each) and about 8,000 host-device sync calls per update. The GPU on the PC is idle 79 % of the time.
- **Production smoke on the 4090:** 8aPTC3S ran 1.132 updates/s (0.883 s/update) for 300 updates, so a full 24,000 updates would take about 5.9 h (PC: 7.2 h), about $2.7 on Vast. With `eg_once` it would be about 1.8x faster, but see above.

## What I think, labelled
- **Shown:** the numbers above; E1 failed as registered; B3G2 is not Gemma-bound.
- **Suggested, untested:** the next lever for B3G2 is fewer, bigger micro-batches (accum 8: 32 rows per pass, about 126 sequential passes per update instead of 505) and fewer host syncs. If launch overhead is the limit, accum 8 could give 2x to 3x, but I have no B3G2 number for any accum except 32. Memory is not the obstacle (1.5 GB on the 4090 at 8 rows).
- **It is not same-maths.** `b3g2.py` `_loss` draws one loop length K per micro-batch, sets the round count to max(K, longest call chain in the batch + 2), and averages the stop loss over rounds x rows. Changing accum changes how many rows share a K and slightly the weights (read from the code, not run). So an accum change on B3G2 is a recipe change, labelled as such.

## Options for G2f and the B3G2 inserts (pros and cons)
| option | pros | cons |

Verdict: do not touch G2f. Measure the accum sweep for B3G2 first (about $0.45 on a 4090 with the existing box, or free on the PC the moment its card is free), with marks written before the run.
